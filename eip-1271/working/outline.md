# Outline — eip-1271

주제: EIP-1271(Standard Signature Validation Method for Contracts)을 명세
원문·개정 이력·구현·후속 표준·실제 사고를 근거로 상세 분석한다. 기준 시점은
2026-09-18.

기존 리포트와의 관계: 본 사이트의 아홉 개 리포트가 EIP-1271을 언급하지만
전부 의존물로 스쳐 간다(최다 `x402-siwx` 6회, `eip-4361-siwe` 5회). 표준
자체를 다룬 리포트는 없다. 본 리포트는 1271 자체와 그것을 둘러싼
ERC-6492·ERC-7739·EIP-7702 계열을 다루고, SIWE·SIWX·x402 쪽 응용은 해당
리포트로 넘긴다.

## 1. 초록

본문 완성 후 마지막에 작성.

## 2. 표준이 규정한 것과 규정하지 않은 것

- `isValidSignature(bytes32,bytes) view returns (bytes4)`와 매직값 `0x1626ba7e`
- `view` 강제의 이유(GasToken), 가스 한도 하드코딩 금지
- bool 대신 bytes4를 고른 근거
- 명세가 침묵한 항목: 실패 반환값, 해시 도출 방식, 계정 바인딩, 미배포 계정,
  검증자가 EOA와 컨트랙트를 구분하는 방법, 시간에 따른 결과 변동
- 다섯 문장짜리 Security Considerations의 내용과 범위

## 3. 이력 — 매직값이 바뀐 날

- 2018-07-25 생성, 2022-01-28 Final까지 3년 반
- 2020-07-09 `isValidSignature(bytes,bytes)`/`0x20c13b0b` →
  `(bytes32,bytes)`/`0x1626ba7e`로 교체된 커밋과 그 제목
- Safe v1.3.0이 두 함수를 모두 들고 있는 현실, 같은 상수명이 버전마다 다른 값
- Final 이후에도 예제가 두 번 고쳐진 사실

## 4. 교차 계정 재사용과 ERC-7739

- 2023-10-27 공개된 취약점, 영향받은 계정 구현과 애플리케이션 목록
- 명세의 참조 구현과 ERC-7739가 "안전하지 않다"고 제시한 예제의 관계
- 방어적 재해싱(defensive rehashing)과 가독성의 상충
- Safe가 애초에 영향받지 않은 이유 — `SafeMessage` 도메인 바인딩
- ERC-7739의 지원 탐지 방식과 조건부 생략

## 5. 미배포 계정과 ERC-6492

- 카운터팩추얼 계정에서 1271이 구조적으로 불가능한 이유
- `0x6492…6492` 접미사 래퍼와 검증자 측 4단계 순서
- 배포를 수반하는 검증이 `view`라는 1271의 전제와 어떻게 공존하는가

## 6. 검증자의 딜레마 — `code.length`, EIP-7702, 프로토콜로 내려간 문제

- OpenZeppelin `SignatureChecker`의 두 가지 형태와 2024-03-14의 전환
- `||` 형태가 키 폐기를 불가능하게 만드는 이유
- `code.length` 분기가 EIP-7702 위임 계정에서 깨지는 방식
- EIP-8151·EIP-8298과 Hegotá에서의 실제 지위
- 응용 계층에서 풀 수 없어 프로토콜로 내려간 문제라는 해석

## 7. 세 표준의 속도 차이

- 1271(3.5년), 6492(6개월), 7739(2년 이상 Draft)의 대비
- 보안 공백을 메우는 표준이 가장 느리게 움직인 사실과 그 함의
- 구현이 명세를 앞서 달리는 현재 상태

## 8. Limitations

- 미해결 갭, 단일 출처 항목, 검증하지 못한 범위
