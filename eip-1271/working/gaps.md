# Gaps — eip-1271

2026-09-18, 게더 3회차 종료 시점. 남은 항목은 Limitations로 그대로 옮긴다.

## 해소된 갭

| # | 갭 | 처리 |
|---|----|------|
| G1 | 명세와 SDK가 주석으로 적어 둔 매직값·타입해시를 그대로 옮기면 오타나 구식 값을 그대로 물려받는다 | 여섯 개 상수를 전부 원문(preimage)에서 다시 계산해 대조했다. `working/verify/verify_magic.mjs`, 6/6 일치. Solady의 `~signature.length / 0xffff * 0x7739` 산식이 실제로 `0x7739…7739`를 내는지도 함께 확인 |
| G2 | 교차 계정 재사용이 실제로 성립하는지 코드로 보이지 않고 서술만 하면 독자가 확인할 방법이 없다 | 검증 로직을 JS로 재현해 실행했다. 같은 서명이 두 계정에서 모두 통과하고, Safe식 도메인 바인딩을 넣으면 두 번째 계정에서 거부된다. `working/verify/verify_replay.mjs` |
| G3 | Alchemy 공개 글 단일 출처 위험 | 독립 확인 두 건 확보. Trail of Bits(2026-03-11)가 같은 결함을 ERC-4337 계정의 여섯 가지 실수 중 하나로 다루고, ERC-7739 명세 자체가 같은 문제를 Motivation으로 기술한다 |
| G4 | Safe가 왜 영향을 받지 않았는지 | Alchemy의 비영향 서술에 더해 Safe 소스에서 `SafeMessage` 재해싱 코드를 직접 확인하고, 그 타입해시를 재계산해 대조했다 |
| G5 | EIP-7702가 검증자 분기를 깨뜨린다는 서술의 근거 | 추측으로 두지 않고 OpenZeppelin 이슈 #6773 본문에서 유지보수자 자신의 설명을 확보했다. 전환 시점과 이유(PR #4951, 키 폐기 문제)까지 1차 자료로 확인 |
| G6 | EIP-8151·8298이 실제로 채택될 전망인지 | Hegotá 메타(EIP-8081)를 직접 읽어 두 건이 "Proposed for Inclusion"에만 있고 Scheduled·Considered에는 없음을 확인했다. OZ 이슈도 `on hold` 라벨이 붙어 있다 |
| G13 | **2020년 매직값 변경을 "심의 없이 흘러 들어갔다"는 쪽으로 서술할 뻔했다.** 커밋 제목만 보고 판단한 것이었다 | **해소, 초안 수정.** PR #2776을 확인하니 제목이 "Change ERC1271 to bytes32 hash"로 내용을 그대로 적고 있고, 본문에 근거가 있으며, 반대 의견이 기록되어 있고, 자동 병합 봇이 저자 승인을 요구하며 거절했다. 주장을 "심의는 PR에 있고 커밋 이력에는 없다"로 좁혔다. 덤으로 그 논의에서 "추가 검증 체계는 별도로 표준화되어야 한다"는 방침이 확정된 사실을 확보해 §4·§5의 인과로 연결했다 |
| G14 | **"어느 명세도 참조 구현과 위험 예제의 관계를 명시하지 않는다"고 썼으나 사실이 아니었다** | **해소, 초안 수정.** ERC-7739가 자기 참조 구현을 설명하며 "최소주의 참조 구현이 프로덕션에 안전하다고 잘못 받아들여진 ERC-1271의 실수를 반복하지 않기 위해서"라고 명시한다. 필자의 대조보다 원문이 더 강한 서술이었다. 초록과 §3.3을 모두 고쳤다 |
| G15 | OpenZeppelin이 EIP-7702 위임 계정에 대한 1271 분기 문제를 이미 문서로 안내하고 있는지 | 확인했고, 해당 문서에서 이 상호작용에 대한 안내를 찾지 못했다. 다만 문서 전체를 읽은 것이 아니므로 "없다"로 단정하지 않고 본문에서 이를 주장하지 않는다 |
| G16 | ERC-7739가 최근에 상태를 바꿨을 가능성 | 라이브 명세 파일에서 `status: Draft`를 재확인하고, ERCs 저장소에 7739를 대상으로 하는 열린 PR이 없음을 확인했다 |
