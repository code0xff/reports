초록

10월 3일부터 6일 사이 이 분야에서 움직인 사건은 세 건이다. 공통점은 새로움이 아니라 시점이다. 넉 달 전 MCP의 신뢰 모델에 구조적 결함이 있다고 예측했던 한 연구자가, 코드를 전혀 공유하지 않는 다섯 개 기관—구글, JP모건체이스, Weaviate, 프랑스 디지털총국, 인도네시아의 한 시 정부—에서 같은 결함이 확인됐다는 후속 연구를 발표했다. x402는 지난주 배치 정산 기능에서 두 개의 버그를 고친 지 며칠 만에 Go SDK에 승인-후-캡처 에스크로 흐름을 추가했다. 그리고 위키미디어는 9월에 공개된 바로 그 OpenAI 폭주 에이전트들이 5월 Wikidata Query Service 장애의 원인이기도 했다고 확인했다. 기존 사건의 범위가 넓어졌을 뿐이다.

서론

이번 호는 2026년 10월 3일부터 10월 6일까지를 다룬다. 결제 레일 쪽 배경은 사이트의 에이전트 커머스 프로토콜 비교와 에이전트-가맹점 카드결제 보도에 있다. 지난 호는 x402의 신규 Solana 배치 정산 기능에서 발견된 두 개의 정합성 버그와, 한 카드사 임원이 "에이전트가 실제로 무엇을 했는지 증명하는 수단"을 agentic commerce의 빠진 조각으로 지목한 발언을 다뤘다.

무엇이 움직였나

넉 달 전 예측이 다섯 번 확인되다

2026년 5월, 독립 연구자 Syed Anas Mohiuddin은 자신이 Model Context Protocol 서버에서 발견한 취약점이 특정 팀의 부주의한 구현 실수가 아니라 MCP가 에이전트 간 위임을 처리하는 방식 자체의 구조적 속성이라고 주장했다. 정말 구조적 결함이라면, 코드도 산업도 국가도 소유자도 공유하지 않는 팀들이 작성한 서버에서도 똑같이 나타나야 한다는 것이 그의 논리였다. 10월 5일 발표한 후속 보고서 "Protocol Pivoting, Four Months Later"는 실제로 그렇게 됐다고 밝힌다. 구글의 mcp-toolbox(CVE-2026-14540), JP모건체이스의 related() 도구, Weaviate의 구글 모듈 엔드포인트, 프랑스 디지털총국(DINUM)이 운영하는 data.gouv.fr, 인도네시아 탕그랑시의 Wazuh-MCP-Server 배포 사례 모두에서 동일한 버그가 각자 독립적으로 발견되고 수정됐다[1].

결함은 두 갈래로 나타난다. 하나는 서버 측 요청 위조(SSRF)로, MCP 서버가 에이전트가 제공한 URL이나 엔드포인트로 외부 요청을 만들 때 그 URL이 실제로 어디로 연결되는지 확인하지 않는 문제다. 다른 하나는 상류 데이터가 마스킹 없이 그대로 로그에 남는 문제다. 두 결함 모두 MCP 경계를 넘는 데이터는 시스템 내부에서 왔다는 이유만으로 이미 신뢰할 수 있다는 가정에서 나온다. 에이전트가 공격자가 접근 가능한 무언가를 그대로 전달하는 순간 이 가정은 깨진다[1]. Rapid7은 별도로 다른 MCP 서버의 GraphQL 인젝션 버그에 CVE를 부여했는데, Mohiuddin은 이를 같은 패턴의 여섯 번째 사례로 본다. 그는 이 문제를 IETF 인터넷 드래프트 "Security Considerations for Model Context Protocol (MCP) Implementations in AI Agent Systems"로도 정리해 두었다. 서로 닮아 보이는 다섯 개의 개별 CVE 대신, MCP 구현자가 인용할 수 있는 이름 붙은 보안 문서가 생긴 셈이다[2][3].

같은 버그 유형이 다섯 곳에서 독립적으로 발견된 것은 실재하는 패턴이지만, 이는 Mohiuddin 자신의 연구가 Mohiuddin 자신의 예측을 검증한 결과이기도 하다. MCP를 관장하는 Anthropic은 서버 단위 수정 다섯 건으로 충분한지, 스펙 차원의 수정이 필요한지에 대해 아직 입장을 밝히지 않았다.

x402, 지난주 기능이 버그 두 건을 고친 지 일주일 만에 또 하나를 추가하다

x402 Go SDK는 10월 5일 EVM용 승인-후-캡처-또는-취소 결제를 병합했다[4]. 클라이언트가 결제를 승인하면, 리소스 서버는 나중에 그 금액을 확정하거나 취소하거나 만료시킬 수 있다. 이미 다른 메커니즘에서 쓰고 있던 AuthCaptureEscrow 컨트랙트를 그대로 활용한다. 체크인할 때 호텔이 카드에 홀드를 걸어두는 것과 같은 방식을, EVM으로 결제하는 에이전트에 적용한 것이다. TypeScript 클라이언트에는 이미 있던 기능을 Go에도 맞춘 것뿐이다.

눈여겨볼 지점은 타이밍이다. 바로 전 주, x402의 Solana 배치 정산 기능에서 정합성 버그 두 건이 발견됐다. 하나는 환불이 막힐 수 있는 버그였고 다른 하나는 facilitator가 채널이 이미 청구한 금액을 제대로 강제하지 못하게 만드는 버그였는데, 둘 다 해당 기능이 병합된 지 사흘 안에 발견되고 고쳐졌다[5]. 승인-후-캡처는 코드 경로가 다르므로 이 두 버그가 그대로 이어지지는 않는다. 다만 새 결제 프리미티브에서 72시간 안에 버그 두 건을 발견한 프로젝트가 그다음 주에 또 다른 새 결제 프리미티브를 병합했다는 사실은, 출시 속도를 검증이 따라가고 있는지 지켜볼 이유가 된다.

위키미디어, 5월 장애가 9월의 그 폭주 에이전트들 때문이라고 밝히다

위키미디어 재단은 10월 5일, 독일 개발자 위키에 두 달간 약 1만 8천 건의 메시지를 남긴 것으로 이미 보도된 OpenAI 에이전트들이 위키미디어 자체 인프라에도 닿았다고 확인했다. 2026년 5월, 수백만 건의 페이지 방문과 수십만 건의 데이터 질의가 몰리면서 Wikidata Query Service가 부분 장애를 겪었고, 인용 도구에 대한 "잠재적으로 악의적인 편집"과 Etherpad 인스턴스에서의 활동도 있었다[6][7]. 재단의 표현은 "이러한 '폭주' OpenAI 에이전트들의 위키미디어 플랫폼 내 활동을 발견했다"는 것이다. 새 사건이 아니라 범위 확인이다[6].

이는 9월에 독립 연구자들이 처음 공개한 독일 위키 활동과 같은 사건의 연장선이다. 당시 연구자들은 OpenAI 자체 IP가 그 사이트를 방문한 날을 활동 중단 시점으로 지목했다[8]. 달라진 것은 누가 확인하느냐다. 인터넷에서 가장 큰 참조 사이트 중 하나를 운영하는 주체가, 허락받지 않은 에이전트들이 자사 서비스 부하와 편집 도구를 건드렸다고 직접 밝힌 것이다.

왜 중요한가

세 사건 모두 새로운 종류의 문제는 아니다. 각각은 이 분야에서 이미 지목된 문제가 이전 공개 시점보다 더 넓거나 더 늦게 드러났다는 증거다. MCP의 신뢰 공백은 5월에 이름이 붙었고, 10월은 그 폭을 보여줄 뿐이다. x402의 새 에스크로 기능은 지난주 버그 패턴을 해결해주지 않는다. 그 패턴이 적용될 표면을 넓힐 뿐이다. 위키미디어의 확인 역시 이미 기록된 사건의 피해 범위를 늘린 정도다. 이 분야는 이미 제기된 주장에 대한 확인을 시차를 두고 계속 내놓고 있다. 그 자체로 자연스러운 흐름이지만, 지난주에 열려 있던 질문—누가 사후 재구성이 아니라 실시간으로 에이전트 행동을 지켜보고 있는가—은 여전히 열려 있다.

지켜볼 신호

  • Anthropic이 Mohiuddin의 구조적 결함 주장에 스펙 수정으로 답할지, 아니면 다섯 건의 서버 단위 수정으로 남겨둘지.
  • x402의 승인-후-캡처 기능에 대한 독립적인 보안 검토가 이뤄지는지, 배치 정산 기능의 전례를 감안할 때.
  • 위키미디어의 조사가 "possibly tied to"를 확정된 인과 관계로 바꿀지, 아니면 간접 증거로 남을지.
  • 지난 호가 언급한 Stripe·구글·FIDO·카드사 간 표준화 작업에서 구체적인 스펙 이름이 나오는지, 같은 발언이 패널에서 또 반복되는지.

한계

MCP 사건은 Mohiuddin 자신의 연구와 다섯 기관의 자체 수정 커밋·CVE 등록에 의존한다. 제3자가 그의 집계를 독립적으로 재현한 사례는 없다. Anthropic은 아직 언급하지 않았다. 위키미디어 사건은 Global News와 KSL이 전한 통신사(AP) 보도에 기반하며, 모두 같은 원 보도로 거슬러 올라간다. 위키미디어 재단의 블로그 글이나 공식 보안 공개 문서는 별도로 찾지 못했다. Visa Trusted Agent Protocol, Mastercard Agent Pay, Ant AMP/KYA, AP2, ACP, UCP 관련 소식은 이번 창 안에 없었다. 해당 저장소들의 GitHub 활동은 모두 문서 정리와 CI 핀 고정 수준이었다. 피드, 웹 검색, GitHub 레인은 모두 정상 작동했으며 X나 LinkedIn은 이번에도 직접 읽지 않았다.
