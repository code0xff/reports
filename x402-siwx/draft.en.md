# The x402 Sign-In with X (SIWX) Extension: Mechanism, Implementation, and Operation

## Abstract

Sign-In-With-X (SIWX) is an official extension of the x402 payment protocol that attaches CAIP-122-based, chain-agnostic wallet authentication to x402-protected resources. Starting from the SIWX documentation at docs.x402.org, this report reconstructs the mechanism and behavior at the code level by reading the CAIP-122, EIP-4361, and Sign-In-With-Solana standards in the original alongside the TypeScript implementation in the x402-foundation/x402 monorepo. Key findings: (1) SIWX is a server↔client extension in which the server embeds a challenge (fresh nonce, issuedAt, domain, supported chains) in the 402 response and the client returns a wallet-signed message in the `SIGN-IN-WITH-X` header; the facilitator plays no role in authentication. (2) Signatures are handled as EIP-4361 messages with EIP-191/1271/6492 verification on EVM and SIWS messages with Ed25519 verification on Solana; upon success, auth-only routes grant access immediately while paid routes additionally consult `SIWxStorage.hasPaid`. (3) Payment history accumulates via a post-settlement hook that records the payer address returned by the facilitator. (4) Domain binding, a 5-minute freshness window, and per-chain signature separation are built in, but nonce-reuse tracking is optional — under default settings a captured header can be replayed within the time window. This is a miniature of the signature-reuse risks demonstrated by real incidents such as the ERC-1271 cross-account replay, and production deployments must implement persistent storage together with nonce tracking. SIWX signals x402's expansion from a one-shot payment protocol toward an identity layer where "payment history is the session," but the extension is new (2026) and has no independent security review or adoption metrics yet.

## Introduction

x402 is a protocol that revives the HTTP 402 Payment Required status code to embed per-request stablecoin payments into the web request flow; Coinbase released it in May 2025[^s12]. The protocol's basic unit is "one request = one payment." That simplicity suits machine-to-machine payments by AI agents, but it collides with a natural expectation of human-facing services — content you bought once should remain viewable. A second gap is payment-free wallet authentication: when a resource server wants to respond only to "the owner of this wallet," x402 core offered no mechanism.

The Sign-In-With-X (SIWX) extension fills both gaps. In the official definition, it "implements CAIP-122 for chain-agnostic wallet authentication. It allows clients to prove control of a wallet that previously paid for a resource, enabling access without requiring repurchase"[^s01]. This report does not merely summarize that page. It (a) verifies the standards lineage SIWX stands on (EIP-4361 → CAIP-122 → SIWS) against the original texts, (b) reads the entire TypeScript implementation in the x402-foundation/x402 monorepo (server challenge generation, message formatting, verification, storage, hooks) to reconstruct how it is implemented and how it behaves, and (c) assesses how the signature-reuse risks already reported in the SIWE/ERC-1271 family are reflected in SIWX's design — and what remains.

## Background: the x402 Extension Model and the Wallet-Authentication Standards Lineage

**x402 and its extension mechanism.** x402 is a three-party structure: the resource server declares payment requirements (`accepts`) in a 402 response, the client re-presents a signed payment payload in a header, and the server verifies and settles through a facilitator[^s12]. In September 2025 Cloudflare and Coinbase announced the x402 Foundation[^s13], and in 2026 the protocol moved under the Linux Foundation as a vendor-neutral standard with participants including Google, Stripe, Visa, and Mastercard[^s14]. The x402 V2 402 response carries an `extensions` field for declaring add-on capabilities that do not disturb the core payment flow; SIWX is one of the official extensions registered there[^s01].

**The wallet-authentication lineage.** SIWX stands on three layers of standards. First, EIP-4361 (Sign-In with Ethereum) defines a structured plaintext message with fields such as domain, address, statement, uri, version, chain-id, nonce, and issued-at, mandating ERC-191 (personal_sign) verification for EOAs (MUST) and ERC-1271 for contract accounts (SHOULD)[^s03]. Second, CAIP-122 generalizes this chain-agnostically — describing itself as work "meant to generalize and abstract the Sign in With Ethereum specification, thereby making EIP-4361 a specific implementation of this specification" — and requires each chain namespace (CAIP-104) to define a profile with its signing algorithm, `type` string, and signing-input procedure[^s02]. Third, Sign-In-With-Solana (SIWS) is Phantom's Solana counterpart, "modeled after EIP-4361 ... but extends beyond its capabilities," with Ed25519 as the default signature type[^s09]. The SIWS repository itself does not mention CAIP-122[^s09], while the x402 documentation treats SIWS as the solana-namespace implementation under the CAIP-122 umbrella[^s01] — a small genealogical discrepancy we record as a source conflict.

A separate implementation shares the "SIWX" name. Reown (successor to WalletConnect) provides its own CAIP-122-conformant SIWX interface in AppKit (the successor to SIWE support; Ethereum, Solana, Bitcoin)[^s15]. x402's SIWX extension and Reown's SIWX are independent artifacts on the same CAIP-122 base, operating at different protocol surfaces (HTTP 402 extension vs. wallet-connection SDK)[^s15][^s01].

## Mechanism Analysis

### Overall flow

The documentation summarizes the operation in four steps: (1) the server returns 402 with challenge parameters in the `sign-in-with-x` extension; (2) the client signs the CAIP-122 message with its wallet; (3) the client sends the signed proof in the `SIGN-IN-WITH-X` HTTP header; (4) the server verifies the signature and grants access either because the route is auth-only or because the wallet previously paid for the resource. It is a server↔client extension: "The Facilitator is not involved in the authentication flow"[^s01]. Unlike x402 core, which delegates payment verification and settlement to the facilitator, SIWX verification completes inside the resource-server process (the only exception being RPC calls for smart-wallet verification)[^s01][^s08].

### Challenge generation (server)

In the TypeScript implementation, `enrichSIWxPaymentRequiredResponse` is the challenge generator. If the route does not declare a fixed domain/URI, they are derived from the request URL; supported networks, absent an explicit option, are derived (deduplicated) from the route's payment requirements (`accepts[].network`). The nonce is a fresh value per response — 16 bytes from `crypto.getRandomValues`, hex-encoded — `issuedAt` is refreshed to the response time, and an `expirationTime` is added when `expirationSeconds` is configured[^s05]. The challenge carries a `supportedChains` array with per-chain signature types (e.g., `{chainId: "eip155:8453", type: "eip191"}`) and a field schema[^s05][^s01]. The extension registers `dynamicInfoFields: ["nonce", "issuedAt", "expirationTime"]`, marking at the protocol level that these three fields are refreshed per response rather than cacheable[^s05].

### Message construction and signing (client)

When the client extension detects the SIWX extension in a 402 response, it picks the first chain in `supportedChains` whose signature type matches its registered signers (`eip191` for EVM, `ed25519` for Solana) and builds the message[^s04]. Formatting routes by chain namespace: `eip155:*` produces the EIP-4361 format via the `@signinwithethereum/siwe` library's `SiweMessage.prepareMessage()` (extracting numeric 8453 from CAIP-2 `eip155:8453`), and `solana:*` produces the SIWS format[^s07][^s08]. The signed payload (message fields + address + signature + chainId + type) is JSON-serialized and Base64-encoded into the `SIGN-IN-WITH-X` header[^s01]. If signing fails, the client hook returns silently and the normal payment flow proceeds — in the documentation's words, the client "falls back to payment if SIWX auth fails"[^s04][^s01].

### Verification pipeline (server)

Inbound verification is two-stage. Stage 1, `validateSIWxMessage`, validates fields before any cryptography; per the code[^s06]:

- **Domain binding**: the payload `domain` must exactly match the server's hostname (port excluded, per EIP-4361 convention).
- **URI**: the payload `uri` must start with the expected resource's origin.
- **Temporal bounds**: `issuedAt` must be in the past within a default 5 minutes (`DEFAULT_MAX_AGE_MS = 5 * 60 * 1000`) and rejected if in the future; `expirationTime` must be in the future; `notBefore` must be in the past.
- **Nonce**: reuse checking runs only when the optional `checkNonce` callback is supplied.

Stage 2, `verifySIWxSignature`, is chain-routed cryptographic verification. The EVM path reconstructs the SIWE message server-side from the payload fields and then verifies: without a verifier option it uses viem's `verifyMessage` (EOA-only, no RPC); with a verifier (e.g., `publicClient.verifyMessage`) it also covers EIP-1271 (deployed smart-contract wallets) and EIP-6492 (counterfactual, not-yet-deployed wallets) via RPC[^s07][^s08]. The Solana path reconstructs the SIWS message and verifies Ed25519 via tweetnacl over the Base58-decoded signature (64 bytes) and public key (32 bytes)[^s08]. Server-side message reconstruction matters: the server never trusts a client-supplied signed string as-is — the signature must hold over a message derived from the validated field set, structurally preventing mismatch between fields and the signed target[^s08].

### Access grant and payment history

The request hook's final decision reduces to one line: `shouldGrant = isAuthOnly || storage.hasPaid(path, address)`[^s04]. Routes declared with `accepts: []` are auth-only and grant access on a valid signature alone (no payment machinery is involved); paid routes consult the verified wallet address's payment history[^s01][^s04]. History is written by the `onAfterSettle` hook from `createSIWxSettleHook`: only when settlement succeeded, it records the `payer` address returned in the facilitator's settlement result against the resource path (pathname) via `storage.recordPayment`[^s04]. Payer identification is thus an output of the settlement layer, not client self-attestation; subsequent SIWX authentication matches a signature-proven address against that record.

The `SIWxStorage` interface has two required methods (`hasPaid`/`recordPayment`) and two optional ones (`hasUsedNonce`/`recordNonce`). The optional pair must be implemented together; implementing only one throws at hook-creation time[^s04]. The bundled `InMemorySIWxStorage` is a Map of resource → set of lowercased addresses, intended for development and single-instance deployments; production multi-instance deployments require persistent storage (database, Redis, etc.)[^s01][^s04].

## Implementation and Operation (Code Level)

**Repository layout.** SIWX is implemented in three languages in the x402-foundation/x402 monorepo: TypeScript (`typescript/packages/extensions/src/sign-in-with-x/` — client/declare/encode/evm/fetch/hooks/message/parse/schema/server/sign/solana/storage/types/validate/verify), Python (`python/x402/extensions/sign_in_with_x/`, same layout), Go (`go/v2/extensions/signinwithx`), plus per-language client/server examples under `examples/`[^s04][^s05]. Code citations in this report are from the TypeScript implementation; Go/Python were confirmed to exist via the file tree and documentation examples _(vendor-stated — behavioral parity not audited)_[^s01].

**Server integration.** The recommended path is the extension factory. `createSIWxResourceServerExtension({ storage })` returns a `ResourceServerExtension` bundling challenge generation (`enrichPaymentRequiredResponse`), post-settlement recording (`hooks.onAfterSettle`), and HTTP request validation (`transportHooks.http.onProtectedRequest`); routes declare support via `declareSIWxExtension({ statement, expirationSeconds, ... })`[^s05][^s01]. Auth-only routes combine the declaration with `accepts: []` — and because no payment requirements exist to infer from, the `network` option is mandatory there[^s01]. For finer control, `createSIWxSettleHook`/`createSIWxRequestHook` attach to existing hook points, and a fully manual path (`parseSIWxHeader` → `validateSIWxMessage` → `verifySIWxSignature`) is public API[^s01].

**Client integration.** `createSIWxClientExtension({ signers: [...] })` builds one hook per signer and tries them in order, adopting the first successful header[^s04]. Signer-type detection is duck-typed: a plural `signMessages` method or a Base58-shaped publicKey classifies as Solana; a `0x`-prefixed address classifies as EVM[^s07]. Multi-chain clients register EVM and Solana signers together and cross-match against the server's `supportedChains`[^s01]. The documentation notes that in multi-chain challenges "the same nonce is shared across all chains, preventing replay attacks when authenticating with different wallets"[^s01].

**Operational scenarios.** Two scenarios follow. (a) *Repeat access after payment*: first request → 402 + SIWX challenge → client chooses payment → settlement succeeds → settle hook records payer → on later requests the client presents the SIWX header → validation + `hasPaid` pass → 200 without repayment. (b) *Auth-only*: 402 + challenge (`accepts: []`) → signature presented → 200 on verification alone. In both paths the client extension automatically falls back to payment when SIWX fails, so SIWX operates as a purely additive layer that never breaks the core flow[^s01][^s04].

## Security Analysis

**Defenses built into the design.** SIWX inherits most of the defenses the SIWE family accumulated. Domain binding implements EIP-4361's core requirement ("Wallet implementers MUST prevent phishing attacks by verifying the origin of the request against the scheme and domain fields") as a server-side hostname equality check[^s03][^s06]; temporal bounds (5-minute maxAge plus expiration/notBefore) and a fresh nonce per response enforce freshness[^s05][^s06]; per-chain signature algorithms prevent cross-chain reuse[^s01][^s08].

**The remaining window: optional nonce tracking.** Per the code, however, nonce-reuse checking runs only when the storage implements `hasUsedNonce`/`recordNonce`[^s04]. The default `InMemorySIWxStorage` does not, so on a default-configured server a captured `SIGN-IN-WITH-X` header can be replayed within the 5-minute `issuedAt` window. The documentation acknowledges this, advising implementers to add both methods "to prevent replay attacks where an intercepted SIWX header could be reused"[^s01]. With TLS protecting transport in typical deployments, the practical risk of this window depends on the environment (logs, proxies), but compared with EIP-4361's stance that a nonce "SHOULD be selected per session initiation with enough entropy to prevent replay attacks"[^s03], SIWX's default sits looser than the spec's recommendation.

**Signature reuse is not a theoretical risk.** Real incidents in adjacent standards demonstrate it. In the ERC-1271 signature replay vulnerability disclosed in 2023, when one owner controls multiple smart contract accounts (SCAs) and an application omits the account address from the signed data, "the same signature would be valid across both accounts" — one permit signature could be replayed across all of the owner's SCAs. Affected parties included LightAccount, OKX SmartAccount, Kernel, Safe (EIP4337Fallback), and Argent among wallets, and Permit2, Cowswap, and OpenSea among applications[^s10]. SIWX's EIP-1271/6492 verification path stands on the same standards, so the lesson — bind full context (domain, account, nonce) into the signed payload and enforce it at the verifier — carries over directly to SIWX deployers. The ERC-1271 specification itself warns that "each contract implementing this method is responsible to ensure that the signature passed is indeed valid, otherwise catastrophic outcomes are to be expected," and separately flags the absence of a gas ceiling on `isValidSignature` calls[^s11]. EIP-6492 verification adds deployment simulation on top, inheriting the reentrancy concerns of requiring `CALL` rather than `STATICCALL`[^s16].

**Trust-model shift.** SIWX's access decision rests on the equation "wallet-key possession = payer = access holder." This is a property of cryptocurrency wallet authentication in general; as the wallet-authentication-factor taxonomy formalizes, factors verified against the blockchain concentrate security in key management[^s17]. If a wallet key leaks or is transferred, the access rights bound to its payment history transfer with it, and the server cannot tell the difference. Moreover, the payment-history store is a resource-server-local contract (the storage interface is keyed by resource path strings), so cross-server history sharing, restart durability, and history expiry policies are entirely the implementer's responsibility[^s01][^s04]. Deploying with the in-memory default means a server restart erases every customer's "purchase record" — an operational trap[^s04].

## Discussion

**Comparison with session alternatives.** The traditional remedies for repeat access are server-issued tokens (API keys, JWT sessions, signed receipts). SIWX's differentiator is that the server issues and stores no secret — the wallet key the client already holds is the re-authentication credential, and the payer (from settlement results) and the accessor (the signature-verified address) are bound to the same identifier[^s01][^s04]. This aligns with the "wallet as self-sovereign authenticator" direction pursued by academic work bridging Web3 identifiers with established authentication protocols such as OpenID Connect[^s18][^s17]. The costs are equally clear: there is no revocation concept — payment history remains valid until deleted — wallet-signing UX is required per session, and smart-wallet verification pulls an RPC dependency into the server[^s01].

**Position in the x402 ecosystem.** x402 reports processing over 100 million payments within six months of launch _(vendor-stated)_[^s12], and with the V2 overhaul and the move to the Linux Foundation (Google, Stripe, Visa, and others participating) it has entered vendor-neutral standardization[^s14][^s13]. SIWX emerged from that maturation and is significant as an official signal of the protocol expanding from one-shot payments toward a session/identity layer whose state is payment history. The interpretation has limits: there are no public metrics for production services with SIWX enabled, and no independent security review of the extension has been identified _(early signal)_[^s01].

At the x402 level, external security analyses already exist and bear directly on SIWX. Halborn's 2026 analysis warns that "if the server isn't configured to make these proofs single-use, then an attacker might be able to access a resource multiple times with the same payment," recommending per-transaction unique nonces and short expiration windows[^s19] — exactly the family of risk this report identifies in SIWX's optional nonce tracking. GoPlus's November 2025 audit empirically reported risks across x402-ecosystem projects including excessive authorization, signature replay, and honeypots, and the 402bridge bridge lost over 17,000 USDC to a private-key leak[^s20]. The pattern already visible in the x402 ecosystem — a sound protocol specification with individual implementations and operations as the weak link — applies with particular force to an extension like SIWX that delegates final responsibility for security properties to resource-server implementers.

**Assessing the design trade-offs.** The most striking choice in SIWX is facilitator non-involvement. Externalizing payment verification while keeping authentication verification server-local reads as motivated by the fact that authentication needs no on-chain settlement and is latency-sensitive — but the price is that final responsibility for security properties like replay prevention and history durability shifts to each resource-server implementer. From a safe-defaults perspective — optional nonce tracking, in-memory storage as the bundled default — today's SIWX is less a library that is easy to use correctly than one that can be used correctly, and that gap remains a risk for deployers who skip the documentation's recommendations[^s01][^s04].

## Limitations

- **Code-reading scope**: only the TypeScript implementation was read closely. The Go/Python implementations were confirmed to exist via the file tree and documentation examples, but parity of their validation rules was not audited.
- **Snapshot staleness**: code citations are from the main branch as of 2026-07-06. SIWX is a new surface consolidated alongside x402 V2, and fields/APIs may still change.
- **No adoption data**: no public list or metrics of production resource servers with SIWX enabled could be found. Ecosystem statements rely on protocol-wide x402 figures (vendor-reported, not independently audited).
- **Access-limited literature**: the ACM DLT paper on bridging Web3 identifiers (10.1145/3719661) returned 403 and was cited at abstract level only. The arXiv/Semantic Scholar APIs were partly rate-limited (429), with fallback to domain-restricted web search.
- **Nature of the security analysis**: no public vulnerability reports or audits of SIWX itself exist yet. The security analysis here is an extrapolation from spec/code reading and known incidents in adjacent standards (SIWE, ERC-1271); actual exploitability depends on deployment environments.
