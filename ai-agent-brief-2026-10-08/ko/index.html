초록

10월 5일부터 8일 사이 이 분야에서 세 가지 움직임이 있었다. x402는 확장 기능의 검증 로직이 오류를 던질 때 결제를 그냥 통과시켜버리는 "열린 게이트" 버그를 공개하고 수정안을 올렸으며, 며칠 뒤에는 배치 정산(batch-settlement) 기능에 새로운 보관 방식을 추가하자는 제안을 냈다. 2주 사이 x402 결제 프리미티브에서 발견된 세 번째 정합성 문제인데, 그렇다고 새 기능 제안 속도가 줄지는 않았다. 별도로 x402 내부의 한 워킹그룹은 신용·체크카드를 auth-capture 스킴에 결합하는 초안을 좁혀나갔고, 리뷰어 명단에 아메리칸 엑스프레스 소속 인사가 이름을 올렸다. 카드 네트워크가 실제로 x402에 발을 들이는 첫 구체적 스케치다. 그리고 구글은 MCP 관련 발표를 두 건 냈는데, 공교롭게도 독립 연구자들이 서로 코드를 공유하지 않는 다섯 개 조직에서 MCP의 신뢰 모델에 구조적 결함이 반복된다는 것을 확인한 지 이틀 뒤였다.

서론

이번 호는 2026년 10월 5일부터 10월 8일까지를 다룬다. 결제 레일 쪽 배경지식은 사이트의 에이전트 커머스 프로토콜 비교와 x402 프로토콜 심층 분석에 있다. 지난 호는 x402의 솔라나 배치 정산 기능에서 발견된 두 건의 버그와, 한 연구자가 5월에 예측한 MCP 신뢰 모델 결함이 서로 무관한 다섯 조직에서 독립적으로 재현됐다는 소식을 다뤘다.

무엇이 움직였나

x402, 열린 채로 새던 결제 게이트의 수정안을 내고, 자금 보관 방식도 새로 제안하다

10월 4일 한 확장 기능 개발자가 이슈 #3689를 올렸다. x402의 beforeVerify와 beforeSettle 훅은 확장 기능이 { abort: true }를 반환해 결제를 막을 수 있도록 만든 장치인데, 훅이 그 값을 반환하는 대신 오류를 던지면 로그만 남기고 결제는 그대로 진행돼버렸다. 서명 검증이든 디코딩이든 커밋먼트 조회든, 검사를 끝내지 못한 확장 기능은 닫혀야 할 게이트를 열어둔 채 지나가버린 셈이다. 10월 5일 올라온 수정 PR #3702는 아직 병합 전이지만, 두 단계 어느 쪽이든 오류를 던지면 extension_hook_error라는 이유로 결제를 멈추도록 고친다[1][2].

이틀 뒤에는 Go SDK의 EVM 배치 정산 기능에 새로운 보관 모드를 추가하자는 PR이 올라왔다. 지금은 리소스 서버가 결제 채널의 바우처를 직접 보관하지만, 새 모드에서는 퍼실리테이터가 바우처를 보관·청구·정산까지 대신 처리할 수 있게 된다. 기존 서버 관리 방식은 그대로 기본값으로 남는다[3][4].

주목할 점은 버그 하나하나가 아니라 패턴이다. 2주 사이 x402 결제 프리미티브에서 발견된 세 번째 정합성 문제다 — 지난주 배치 정산 버그 두 건에 이은 "열린 게이트" 버그인데, 프로젝트는 그 때문에 기능 출시 속도를 늦추지 않았다. 열린 채로 새는 인가 게이트는 배치 정산 버그들보다 더 심각한 종류의 결함이다. 확장 기능 개발자가 그 훅을 넣은 이유 자체를 무력화하기 때문이다.

카드 결제 워킹그룹, 신용카드를 x402에 결합하는 안을 다듬다

x402가 지금 지원하는 모든 네트워크 바인딩은 크립토 레일이라서, 지갑에 자금이 없는 에이전트는 이 프로토콜로 결제할 방법이 없다. 10월 6일 올라온 이슈 #3706은 이 공백을 기존 auth-capture 스킴의 새로운 바인딩으로 채우자고 제안한다. 클라이언트 페이로드에는 불투명한 PSP 토큰과 card:visa 같은 카드 네트워크 식별자, ISO 4217 소단위 금액이 담기고, 카드 데이터 자체는 네트워크를 타지 않는다. 퍼실리테이터가 리소스 실행 전에 홀드를 걸고, 이후 캡처하거나 취소한다[5].

같은 날 올라온 PR #3707은 x402의 #wg-card-acceptance 워킹그룹 리뷰를 거쳐 그 제안을 기본 케이스로 좁혔다. 리뷰어 명단에는 아메리칸 엑스프레스의 Adam Krochak이 올라 있다[6]. 초안 맨 위에는 아직 풀리지 않은 질문 다섯 개가 적혀 있다: v1이 에이전트가 시작한 결제만 다루는지, PSP 토큰이 보통 발급 계정에 묶여 있는데 에이전트가 실제로 어떤 토큰을 쓸 수 있는지, 카드 네트워크가 x402 결제를 카드 소유자 발생이나 가맹점 발생 거래와 어떻게 구분하는지, 홀드와 최종 청구를 묶는 식별자는 무엇인지, 카드 네트워크 수수료보다 싼 요청은 어떻게 결제하는지.

이 중 어느 것도 아직 정해지지 않았다. 지금 존재하는 것은 카드 네트워크 소속 리뷰어가 이 바인딩이 쓰이는 자리에 실제로 앉아 있다는 사실이다. 이 분야에서 "제안"이라는 말이 지금껏 뜻했던 것보다 한 걸음 더 나간 상태다.

구글, MCP 신뢰 문제가 보안 언론에 오른 이틀 뒤 MCP 도구 두 건을 내놓다

10월 5일 Ars Technica는 한 연구자가 5월에 예측한 MCP 신뢰 모델의 구조적 결함이, 서로 코드를 공유하지 않는 다섯 조직(구글, JP모건체이스, Weaviate, 프랑스 디지털 총국, 인도네시아의 한 지방정부)에서 독립적으로 재현됐다고 보도했다[7]. 지난 호가 머릿기사로 다룬 바로 그 이야기다.

이틀 뒤 구글은 구글 클라우드·파이어베이스·안드로이드 문서로 가는 공식 경로를 에이전트에게 제공하는 Developer Knowledge API와 그 MCP 서버를 퍼블릭 프리뷰로 발표했고, 별도로 MCP Toolbox Java SDK가 v1.0에 도달했다고 밝혔다. 이 버전에는 민감한 서버 측 값을 모델이 건드리지 못하게 막는 파라미터 프루닝과 자격증명 처리 기능이 추가됐다[8][9].

두 발표 어디에도 Ars Technica가 짚은 신뢰 경계 문제를 다룬다는 말은 없고, 다루지 않는다는 말도 없다. 시점이 자연스레 연결을 유도하지만, 출처들 자신은 그 연결을 짓지 않는다.

왜 중요한가

이번 창에서 세 항목 중 둘은 x402가 같은 주에 자기 실수를 고치면서 동시에 영역을 넓히는 모습이다. 열린 게이트 버그가 조용히 그냥 나갔거나 배치 정산 버그들이 검토 없이 넘어갔을 경우와는 다른 결과다. 카드 바인딩 쪽은 더 구조적인 변화다. 특정하고 인용 가능한 초안에 카드 네트워크 소속 리뷰어가 실명으로 붙은 것은 이 분야에서 처음이다. "카드 네트워크와 협업 중"이라던 그 흔한 보도자료식 표현과는 무게가 다르다. 구글의 MCP 발표들은 이 두 이야기 밖에 있지만 인접성은 무시하기 어렵다. 구조적 신뢰 문제가 수요일에 공개된 프로토콜이 금요일에 엔터프라이즈급 도구 두 건을 새로 받았는데, 어느 쪽도 그 공개 내용을 건드리지 않았다.

지켜볼 신호

  • PR #3707의 다섯 가지 미해결 질문: 다음 리뷰 사이클에서 풀릴 수도, 앞선 x402 카드 시도들처럼 멈춰 설 수도 있다.
  • PR #3702가 지금 형태로 병합될지, 병합 이후 독립적인 보안 검토가 따라올지.
  • x402 프리미티브에서 이 속도가 꺾이기 전에 네 번째 정합성 문제가 나올 수 있다.
  • 아메리칸 엑스프레스의 #wg-card-acceptance 참여, 다른 카드 네트워크를 끌어들일까 아니면 단일 리뷰어로 남을까.
  • MCP의 관리 주체인 Anthropic은 아직 아무 반응도 내지 않았다. 이번 주 도구 발표들과 10월 5일 보도된 신뢰 모델 문제를 연결할지 지켜볼 일이다.

한계

카드 바인딩과 게이트 버그 이야기는 전적으로 x402 깃허브 저장소에만 기대고 있다. 아직 독립 언론 보도가 없고, PR #3707은 병합된 변경이 아니라 열린 초안이라 최종 형태는 여기 기술한 것과 달라질 수 있다. 게이트 버그 수정안도 x402 코어 팀 자체 테스트로만 검증됐을 뿐, CVE가 등록되지 않았고 제3자 검토도 없었다. 구글의 두 발표는 벤더 발표 그대로이며, Developer Knowledge API의 프리뷰 품질이나 Java SDK의 보안 주장을 독립적으로 평가한 자료는 없다. EMVCo 자체의 에이전트 결제 프레임워크는 이번 창이 시작되기 사흘 전인 10월 2일 공개 의견수렴을 마감했는데, 창 밖이라 뉴스로는 다루지 않고 인접 사안으로만 적어둔다. 비자, 마스터카드, 스트라이프 자체 채널에서 나온 소식은 이번 창에 없었다. 피드, 웹 검색, 깃허브는 모두 접근 가능했고, X나 링크드인은 직접 읽지 않았다.
