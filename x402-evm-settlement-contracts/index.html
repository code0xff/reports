x402 EVM Settlement Contracts and Payment Schemes: Permit2 Proxies and Batch Settlement

A code-level analysis of the x402 Permit2 proxy contracts and the now-shipped x402BatchSettlement payment-channel contract serving the exact, upto, and batch-settlement schemes.

Abstract

x402 is an HTTP-native payment protocol in which a resource server answers a request with HTTP 402, a client returns a cryptographically signed payment authorization, and a facilitator broadcasts the resulting on-chain settlement while paying the gas.[1][2] On EVM chains, settlement for ERC-20 tokens that lack native transferWithAuthorization is handled by a family of x402-authored contracts. This report analyzes the four artifacts named in the request — x402BasePermit2Proxy.sol, x402ExactPermit2Proxy.sol, x402UptoPermit2Proxy.sol, and x402BatchSettlement.sol — and corrects a finding from an earlier revision of this report. All four contracts now exist. An earlier read pinned to coinbase/x402 at commit dd927a2 (2026-04-21) found only the three Permit2 proxies and reported x402BatchSettlement.sol as absent; since then the canonical repository moved to x402-foundation/x402 (coinbase/x402 is now a development fork frozen at dd927a2), and the foundation tree at commit dc656bb (2026-06-09) ships a real x402BatchSettlement.sol — a stateless unidirectional payment-channel contract — plus an ERC3009DepositCollector and a Permit2DepositCollector, all three deployed to canonical CREATE2 addresses on Base, Arbitrum, World Chain, and Polygon mainnets.[3][4][5][6] The three Permit2 proxies share one design: the proxy — not the facilitator — is the authorized Permit2 spender, and Uniswap Permit2's "witness" pattern cryptographically binds the payment destination into the payer's signature so a facilitator can broadcast but cannot redirect funds.[7][1][8] The exact proxy always transfers the full permitted amount; the upto proxy lets an authorized facilitator transfer any amount up to the signed maximum and adds a facilitator field to the witness for caller authorization.[9][10] x402BatchSettlement realizes the capital-backed batch-settlement binding: clients deposit once into an on-chain escrow channel, sign off-chain cumulative vouchers, and servers claim them on-chain in batches and sweep settled funds in a single transfer.[4][5] The Permit2 proxies hold no custody and are immutable; the batch contract custodies escrowed deposits under per-channel accounting with a timed-withdrawal escape hatch. All are designed to deploy to the same address on every EVM chain via CREATE2.[11][4][6]

1. Introduction

x402 revives the long-dormant HTTP 402 Payment Required status code as the basis for machine-payable web resources, a use case sharpened by autonomous agents that must pay per request. The protocol's division of labor is consistent across its scheme documents: the client signs an authorization, the resource server decides what is owed, and the facilitator verifies the authorization and broadcasts the settlement transaction, paying gas so the flow is gasless for the payer.[1][2] The facilitator is explicitly a broadcaster, not a trusted custodian: "the Facilitator cannot modify the amount or destination. They serve only as the transaction broadcaster."[1]

That guarantee is trivial for tokens such as USDC that implement EIP-3009 transferWithAuthorization, because the signed authorization itself names the recipient and amount. The harder case is an arbitrary ERC-20 with no such hook. x402's answer is to route those payments through Uniswap's Permit2 and a thin x402-authored proxy that occupies the "spender" slot.[1] The four files named in this request are exactly that machinery — three Permit2 proxies plus the batch-settlement contract.

A note on sourcing and the repository move. An earlier revision of this report read these contracts at coinbase/x402@dd927a2 (2026-04-21) and reported, correctly for that commit, that x402BatchSettlement.sol did not exist — batch-settlement then shipped only as a scheme spec with a credit-backed Cloudflare binding. Since then the project relocated: coinbase/x402's own README states "We've moved the x402 repo under the x402 Foundation repo… [coinbase/x402] is now a development fork," and that fork's main remains frozen at dd927a2.[3] The canonical tree is now x402-foundation/x402, whose commit dc656bb (2026-06-09) adds the batch-settlement contract, two deposit collectors, a dedicated EVM scheme binding, tests, and deployments.[4][5][6] This report therefore reads the three Permit2 proxies at the original dd927a2 pin (their code is unchanged in substance) and the batch-settlement machinery at x402-foundation/x402@dc656bb, cross-checking the Permit2 mechanism against Uniswap's own documentation.[7][8][9][10][11][12][13][14][4][5][15] Where a canonical address changed between the two pins, the change is flagged explicitly (§6).

Scope note: the exact scheme on EVM also defines EIP-3009 and ERC-7710 (smart-account delegation) transfer methods. Those paths do not touch the contracts under study and are discussed only as context for why the Permit2 proxy path exists.[1]

2. Background: Permit2 and the witness pattern

Permit2 is Uniswap's standalone approval/transfer contract deployed at a single canonical address. Its SignatureTransfer module performs one-time, signature-authorized token movements without a standing ERC-20 allowance to the spender: the token owner approves Permit2 once, then signs per-transfer messages that Permit2 verifies and executes.[13][14] Two features matter for x402.

Unordered nonces. Permit2 uses non-monotonic, bitmap-based nonces: a nonce encodes a word position and a bit, so signatures can be spent or invalidated in any order rather than in sequence.[16][13] x402's upto scheme leans on exactly this for its single-use guarantee — "On EVM, Permit2's nonce mechanism enforces this" — meaning the proxy does not need its own replay bookkeeping.[17]

The witness. The function x402 uses is permitWitnessTransferFrom, which extends a signature transfer with arbitrary caller-supplied data — the witness — plus a witnessTypeString that declares its EIP-712 type. The signer commits to that extra data, and the call reverts if the requested transfer amount exceeds the signed maximum.[16][14] Uniswap describes the witness as "arbitrary signed data used to reconstruct signature data and optionally validate additional context," and notes the type string "must follow EIP712 ordering of nested structs and must include the TokenPermissions type definition."[13][14]

x402 exploits the witness to solve its core trust problem. The payer signs a Permit2 message whose spender is the x402 proxy, not the facilitator, and whose witness contains the destination address. Because the destination is inside the signed witness, the facilitator who broadcasts the transaction cannot change where the money goes: "The spender in the signature is the x402ExactPermit2Proxy, not the Facilitator. This Proxy enforces that funds are only sent to the witness.to address."[1] The proxy's job is therefore narrow: be a fixed, well-known spender, reconstruct the witness hash exactly as the payer signed it, and hand everything to Permit2. The batch-settlement contract reuses the same witness-bound Permit2 transfer for its deposit path (§4.5).[18]

3. The payment schemes: exact, upto, batch-settlement

The three schemes differ in when and how much value moves.

exact transfers a specific amount the resource server knows in advance — paying to view an article, buying credits, an LLM paying for a tool call.[19] On EVM it can be realized three ways, ranked by the spec: EIP-3009 (recommended, simplest, for tokens like USDC), Permit2 + proxy (the universal fallback for any ERC-20), and ERC-7710 (smart-account delegation). If no method is specified, implementations prefer EIP-3009 then Permit2.[1] Only the Permit2 path uses x402ExactPermit2Proxy.

upto authorizes a maximum and settles the actual amount, determined at settlement time from resource consumption — pay-per-token LLM output, metered bandwidth, dynamic compute.[17] It is Permit2-only by construction: EIP-3009 "is not supported for the upto scheme because it requires exact amounts at signature time."[2] Two properties of upto are worth isolating:

  • Phase-dependent amount. The same PaymentRequirements.amount field means the maximum at verification time and the actual amount to settle at settlement time; the settled amount must be ≤ the authorized maximum and may be 0 (an unused authorization simply expires with no on-chain transaction).[17][2]
  • Facilitator binding. The server advertises its address; the client must place it in witness.facilitator, "which binds the authorization to a specific facilitator, preventing unauthorized settlement by other parties."[2]

batch-settlement is categorically different: "the commitment is accepted, access is granted immediately, and financial settlement occurs later through a process defined by the network binding."[20] Unlike exact/upto, the synchronous settlement step "stores [the commitment] rather than executing a transfer," returning a commitment identifier instead of a transaction hash; value moves later via the binding's redemption process.[20] The spec defines two trust models, and both now ship:

  • Credit-backed — the cloudflare:402 binding authenticates commitments with HTTP Message Signatures (RFC 9421), grants access immediately, and has Cloudflare act as Merchant of Record, billing the signature agent's identity and settling off-chain on a periodic cycle. It needs no EVM contract.[21]
  • Capital-backed — the EVM binding uses "stateless unidirectional payment channels for high-throughput, low-cost payments. Clients deposit funds into onchain channels once and sign off-chain cumulative vouchers per request. Servers verify vouchers with fast signature checks and claim them onchain periodically in batches." This binding is implemented by the x402BatchSettlement contract.[5]

So the scheme→contract mapping, asymmetric in the earlier revision, is now uniform: exact → x402ExactPermit2Proxy, upto → x402UptoPermit2Proxy, and batch-settlement → x402BatchSettlement (for the capital-backed EVM binding) or off-chain infrastructure (for the credit-backed Cloudflare binding).[1][2][4][5]

4. Contract code analysis

4.1 x402BasePermit2Proxy — the shared proxy base

x402BasePermit2Proxy is an abstract contract inheriting OpenZeppelin's ReentrancyGuard. It stores the Permit2 address as an immutable set once in the constructor, reverting with InvalidPermit2Address on the zero address. The NatSpec explains the immutability is deliberate — it "eliminat[es] any post-deployment initialization race," and using the same canonical Permit2 argument on every chain "keeps the initCode identical, preserving CREATE2 address determinism."[7]

The base provides two internal helpers that the children compose:

  • _settle(...) performs the common validation and the actual Permit2 call. It reverts if settlementAmount == 0 (InvalidAmount), owner == address(0) (InvalidOwner), to == address(0) (InvalidDestination), or block.timestamp < validAfter (PaymentTooEarly). It then builds SignatureTransferDetails{to, requestedAmount: settlementAmount} and calls PERMIT2.permitWitnessTransferFrom(permit, transferDetails, owner, witnessHash, witnessTypeString, signature). Crucially, the child computes its own witnessHash and witnessTypeString — the base is agnostic to the witness shape.[7] The upper time bound is not re-checked here; it is delegated to Permit2's deadline, as the test suite notes ("validBefore was removed - upper time bound is enforced by Permit2's deadline").[11]
  • _executePermit(...) supports the fully gasless EIP-2612 flow. It first requires the EIP-2612 value to equal the Permit2 permitted amount, reverting Permit2612AmountMismatch otherwise — preventing a mismatch between the approval the payer grants Permit2 and the amount Permit2 is told it may move.[7] It then calls IERC20Permit(token).permit(owner, address(PERMIT2), ...) inside a try/catch that catches Error(string), Panic(uint256), and raw bytes, emitting EIP2612PermitFailedWith{Reason,Panic,Data} rather than reverting. The design rationale is explicit: "The actual permit call does not revert on failure because the approval might already exist or the token might not support EIP-2612."[7] The Foundry tests confirm both halves — settlement still succeeds when the permit reverts (test_settleWithPermit_succeedsWhenPermitFails), and the matching failure event is emitted for each revert flavor.[11]

The base also defines the EIP2612Permit struct (value, deadline, r, s, v) and the Settled / SettledWithPermit events.[7]

4.2 x402ExactPermit2Proxy — fixed-amount transfers

The exact proxy is a thin concrete child. Its witness is Witness{address to; uint256 validAfter} and its type string is "Witness witness)TokenPermissions(address token,uint256 amount)Witness(address to,uint256 validAfter)".[8] Its settle(permit, owner, witness, signature) computes witnessHash = keccak256(abi.encode(WITNESS_TYPEHASH, witness.to, witness.validAfter)) and calls _settle with the settlement amount hard-wired to permit.permitted.amount — i.e., it always transfers the entire permitted amount, "similar to EIP-3009's transferWithAuthorization behavior."[8] The test test_settle_transfersExactPermittedAmount and the bare Witness{to, validAfter} constructor in the test harness confirm both the exact-amount behavior and the absence of any facilitator field.[12] settleWithPermit(...) is identical except it first calls _executePermit to submit the EIP-2612 approval. Both functions are nonReentrant.[8]

Notably, the exact proxy imposes no caller restriction: any address can broadcast a valid settle. This is safe against fund theft — destination and amount are fixed by the signature, so an arbitrary caller cannot redirect or inflate the payment. It is not, however, safe against settlement preemption: because anyone holding the signed authorization can submit it, an attacker can front-run the legitimate facilitator and consume the Permit2 nonce, which independent security research frames as a structural flaw ("the settlement path does not bind the facilitator identity to authorization").[22] The upto proxy's facilitator field is precisely the mitigation for this class of attack (§4.3, §5); the exact proxy has no equivalent and is therefore preemptable. _(This is an independent researchers' framing of a design gap, discussed further in §6.)_

4.3 x402UptoPermit2Proxy — flexible-amount transfers

The upto proxy is structurally similar but adds variability and access control. Its witness is Witness{address to; address facilitator; uint256 validAfter}, with type string "...Witness(address to,address facilitator,uint256 validAfter)".[9] Its settle takes an extra caller-supplied amount and enforces two new guards before settling:

if (amount > permit.permitted.amount) revert AmountExceedsPermitted();
if (msg.sender != witness.facilitator) revert UnauthorizedFacilitator();

It then folds the facilitator into the witness hash (keccak256(abi.encode(WITNESS_TYPEHASH, witness.to, witness.facilitator, witness.validAfter))) and calls _settle with the caller's amount.[9] So the facilitator chooses the final amount at settlement, but only within two bounds the payer signed: it cannot exceed the permitted maximum (also enforced independently by Permit2 itself[16]), and only the exact address the payer named as facilitator may call. The test suite exercises all of this: partial amounts succeed (test_settle_allowsPartialAmount, testFuzz_settle_partialAmountsSucceed), over-permit amounts revert (testFuzz_settle_amountNeverExceedsPermitted), and an attacker who is not the named facilitator reverts with UnauthorizedFacilitator.[11] settleWithPermit adds the same two guards plus the EIP-2612 step.[9]

The facilitator field is the key design difference from exact. Because an upto facilitator has discretion over the amount, the protocol restricts who may exercise that discretion to a single signed address — a restriction the exact proxy neither needs nor has.[8][9][2]

4.4 x402BatchSettlement — the payment-channel contract

The fourth file is real in the foundation tree and is a different kind of contract from the proxies: a custodial, stateful stateless unidirectional payment channel (the spec's phrasing means stateless off-chain — the contract keeps only minimal per-channel accounting and derives channel identity from an immutable config rather than allocating channel slots).[4][5] It inherits EIP712, OpenZeppelin's Multicall, and ReentrancyGuardTransient (the EIP-1153 transient-storage reentrancy guard), and its NatSpec warns it "must only be deployed on chains where that opcode is supported."[4][5] The economic model it implements is the capital-backed batch-settlement binding: deposit once, pay per request with off-chain signatures, reconcile on-chain in batches.[5]

Channel identity. A channel is defined entirely by an immutable ChannelConfig{payer, payerAuthorizer, receiver, receiverAuthorizer, token, withdrawDelay, salt}, and channelId = getChannelId(config) = _hashTypedDataV4(keccak256(abi.encode(CHANNEL_CONFIG_TYPEHASH, config))). Because the EIP-712 hash binds the config to this contract's chainId and address, "identical configs on different chains or different deployments produce different ids, preventing cross-chain channel-state collision."[4] There is no createChannel call: a channel comes into existence implicitly on its first deposit.[5]

Deposit. deposit(config, amount, collector, collectorData) validates the config (non-zero payer/receiver/receiverAuthorizer/token, withdrawDelay within MIN_WITHDRAW_DELAY = 15 minutes … MAX_WITHDRAW_DELAY = 30 days), credits ch.balance += amount, then calls a pluggable IDepositCollector.collect(...) to pull the tokens. It brackets the pull with a balance check — balAfter != balBefore + amount reverts DepositCollectionFailed — which defends against fee-on-transfer shortfalls and silent failed pulls.[4][23] The first deposit emits ChannelCreated; the implementer notes warn the same channelId may emit ChannelCreated more than once if a channel is drained and re-funded, so indexers must pair it with ChannelClosed.[23]

Claim and settle — the two-step that makes batching cheap. The receiver side does not pull tokens per request. Instead the payer signs cumulative vouchers (Voucher{channel, maxClaimableAmount}), and the receiver submits claim(VoucherClaim[]) or the relay-friendly claimWithSignature(VoucherClaim[], authorizerSignature). _processVoucherClaim is where the accounting lives: it ignores any vc.totalClaimed <= ch.totalClaimed (so "replaying an old voucher after it was applied is a no-op"), reverts ClaimExceedsCeiling if it exceeds the signed maxClaimableAmount, reverts ClaimExceedsBalance if it exceeds escrow, verifies the payer signature, then advances ch.totalClaimed and the per-receiver aggregate receivers[receiver][token].totalClaimed.[4] Crucially, claiming moves no tokens — it only updates accounting. Value moves in a separate settle(receiver, token) call, permissionless, that transfers totalClaimed - totalSettled for that (receiver, token) pair in a single ERC-20 transfer and sets totalSettled = totalClaimed.[4] This is the structural source of the gas savings the spec advertises: "A single claim transaction can cover many channels at once and only updates onchain accounting; claimed funds are later transferred to the receiver via a separate settle operation that sweeps many claims into one token transfer."[5]

Cumulative monotonicity replaces per-payment nonces. Because each voucher carries a cumulative ceiling that only ever increases, "old vouchers with lower ceilings are naturally superseded" and "the cumulative model makes nonces unnecessary."[5] Replay protection for vouchers is therefore structural, not a nonce bitmap: the contract simply refuses to decrease totalClaimed.[4]

Dual-authorizer signing. _processVoucherClaim checks the payer's voucher signature one of two ways. If payerAuthorizer != address(0), it does a plain ECDSA recover that must equal payerAuthorizer (a delegated EOA signing key, no RPC needed). If payerAuthorizer == address(0), it validates against payer via SignatureChecker.isValidSignatureNow, which supports EIP-1271 smart-contract wallets at the cost of an on-chain call.[4][5] The receiverAuthorizer plays the symmetric role on the claim/refund side and must be non-zero.[23]

Two exits: cooperative refund and timed withdrawal. Unclaimed escrow can leave the channel two ways. A cooperative refund (refund by the receiver side, or relay-friendly refundWithSignature carrying an EIP-712 Refund(channelId, nonce, amount) from the receiverAuthorizer) returns up to balance - totalClaimed to the payer immediately. A timed withdrawal is the payer's unilateral escape hatch: initiateWithdraw(config, amount) opens a window, and after withdrawDelay elapses finalizeWithdraw(config) pays out, capping the amount to whatever unclaimed escrow remains. The spec frames the 15-minute-to-30-day bound as preventing a server "from indefinitely trapping client funds while giving the server a fair window to claim outstanding vouchers."[4][5]

The refund nonce has a sharp edge. Both refund paths share _executeRefund, which increments refundNonce[channelId] first, before the cap is applied — "including when amount > 0 but available unclaimed escrow is zero (no transfer, no Refunded event)." A direct refund therefore advances the nonce and invalidates any pre-signed refundWithSignature digest bound to the previous nonce. The implementer notes flag this explicitly: "do not assume 'no-op' means 'nonce unchanged,'" and integrators must read the live refundNonce before signing.[4][23] (amount == 0 is the one path that reverts ZeroRefund without bumping the nonce.)[4]

The liveness race the contract does not solve on-chain. finalizeWithdraw and claim are independent entry points that both read live balance and totalClaimed; there is no on-chain reservation for vouchers signed but not yet claimed. If a payer's finalizeWithdraw lands before a receiver's claim, escrow can drop so the later claim reverts ClaimExceedsBalance — the receiver's earned-but-unclaimed value is forfeited.[4][23] This is a deliberate design choice pushed to integrator policy: claim early, use resilient relays, and choose a withdrawDelay well above the floor for high-value channels. The Foundry suite encodes the intended behavior — test_finalizeWithdraw_capsIfClaimedDuringDelay and an attack-path test test_initiateWithdraw_attackBypass_blocked — and the fork tests run a full Permit2 deposit→claim→settle lifecycle and assert a tampered witness reverts.[23][15]

4.5 The deposit collectors

x402BatchSettlement does not hard-code how tokens are pulled into escrow; it delegates to a pluggable IDepositCollector whose single collect(payer, token, amount, channelId, collectorData) method "MUST transfer tokens to msg.sender (the calling x402BatchSettlement)."[24] The abstract DepositCollector base pins each collector to one settlement deployment and gates collect with onlyx402BatchSettlement so "only x402BatchSettlement can call collect, mitigating frontrunning and theft of user funds" — without that guard, an attacker could invoke a collector directly and pull a victim's pre-signed authorization to an unintended destination.[24] Two reference collectors ship:

  • ERC3009DepositCollector uses ERC-3009 receiveWithAuthorization for gasless pulls on tokens like USDC. Because ERC-3009 requires msg.sender == to, tokens land on the collector and are forwarded to the settlement contract; the authorization nonce is bound to the channel as keccak256(abi.encode(channelId, salt)).[18]
  • Permit2DepositCollector reuses the same Permit2 witness machinery as the proxies (§2): it calls permitWitnessTransferFrom with a DepositWitness{bytes32 channelId} so the deposit is bound to its channel, moves tokens directly from payer to the settlement contract, and offers the same optional, non-reverting EIP-2612 permit step (with the value == amount precheck) seen in the base proxy.[18]

The post-deposit balance check in x402BatchSettlement.deposit (§4.4) means the settlement contract trusts receipt of tokens, not the collector's word — a collector that under-delivers makes the whole deposit revert.[4][23]

5. Security properties and threat model

Reading the contracts and their docs together yields a compact threat model. The Permit2 proxies and the batch-settlement contract have different shapes — the proxies are custody-free pass-throughs, the channel contract custodies escrow — so their properties are listed separately.

Permit2 proxies (exact, upto).[7][8][9][10]

  • Destination integrity. The witness binds to into the payer's signature, so a malicious or compromised facilitator cannot redirect funds; the README states the witness pattern "enforces payTo address," and the spec calls this out as the proxy's central purpose.[1][10]
  • Caller integrity (upto only). The facilitator field plus the msg.sender != witness.facilitator check stop a third party from settling someone else's upto authorization with an amount of their choosing.[9][2]
  • No custody. Tokens move directly from owner to witness.to through Permit2; the proxy never holds a balance. The README asserts "Contracts never hold tokens," and test_settle_proxyNeverHoldsTokens checks the proxy balance is zero after settlement.[10][11]
  • Immutability and reentrancy. "No upgrade mechanism, no owner, no admin functions"; every external settle function is nonReentrant, and test_settle_blocksReentrancy (driven by a malicious reentrant mock Permit2) confirms the guard fires.[10][11]
  • Replay / single-use. Provided by Permit2's unordered nonce, not by the proxy. Each authorization can be settled at most once.[17][13]
  • Amount safety, twice over. The upto proxy checks amount <= permit.permitted.amount, and Permit2's permitWitnessTransferFrom independently reverts if the requested amount exceeds the signed permission — defense in depth.[9][16][14]
  • Time bounds. Lower bound validAfter is enforced in _settle (PaymentTooEarly); upper bound is Permit2's deadline.[7][11]

Batch-settlement channel (x402BatchSettlement).[4][5][23]

  • Custody with bounded escrow. Unlike the proxies, the contract holds escrowed deposits, but each channel's funds are isolated by channelId and the per-receiver settlement aggregate only ever pays out claimed amounts. test_crossChannel_isolation checks one channel cannot draw on another's balance.[4][15]
  • Voucher replay protection without nonces. The cumulative totalClaimed is monotonic; a stale lower voucher is a silent no-op. Distinct EIP-712 type hashes for Voucher, Refund, and ClaimBatch mean a signature for one operation cannot be replayed as another.[4][5]
  • Signed-refund replay protection. A per-channel refundNonce, advanced inside _executeRefund before the amount cap, binds each refundWithSignature to a single use — at the cost of the cross-path invalidation edge described in §4.4.[4][23]
  • Transient reentrancy guard. ReentrancyGuardTransient (EIP-1153) guards every state-mutating entry point; the trade-off is that the contract is only safe to deploy where transient storage exists.[4][5]
  • Deposit integrity. The balance-delta check after collect rejects fee-on-transfer/rebasing shortfalls, and the onlyx402BatchSettlement collector guard blocks direct collector invocation.[4][24][23]
  • Liveness, not safety, is the residual risk. The withdrawal-vs-claim race (§4.4) cannot cause theft — a payer can never withdraw past balance - totalClaimed — but it can cause a cooperative-but-late receiver to forfeit unclaimed value. The withdraw-delay floor and integrator claim-early guidance are the mitigations, not an on-chain lock.[5][23]

Cross-chain determinism (all contracts). The proxies target the same address on every EVM chain via Arachnid's CREATE2 deployer, which requires byte-identical initCode; foundry.toml sets cbor_metadata = false and bytecode_hash = "none" so the compiler does not append an environment-dependent IPFS metadata hash that would break address determinism.[7][10][25] The batch-settlement stack follows the same scheme, with the two deposit collectors taking the settlement address in their constructors (so their initCode, and the mined vanity salt, depend on the settlement contract's address).[6]

Residual trust assumptions: integrators inherit Permit2's and the proxies' correctness; upto payers trust the server to charge fairly; and batch-settlement payers accept that a server can claim up to the signed maxClaimableAmount and bear the liveness risk on unclaimed vouchers (§6).

6. Discussion

A prediction the codebase fulfilled. The earlier revision of this report observed that batch-settlement shipped no EVM contract and added a hedge: "A future capital-backed binding (escrow or payment-channel) could introduce an EVM contract, but none ships today." That is exactly what landed. The foundation tree's scheme_batch_settlement_evm.md is explicitly "a capital-backed network binding using stateless unidirectional payment channels," implemented by x402BatchSettlement — escrow plus payment-channel, the two mechanisms the hedge named.[5] The lesson is about freshness, not correctness: the absence was true at dd927a2, the qualifier was the right one, and a fast-moving vendor protocol closed the gap in roughly seven weeks.

Why a channel contract rather than another proxy. The three exact/upto design lives entirely on the synchronous request path: one signature, one on-chain transfer, no custody. Batch-settlement optimizes the opposite regime — many tiny requests against one counterparty — where a per-request on-chain transfer is uneconomical. The channel contract amortizes gas across requests (off-chain vouchers, batched claims, one sweeping settle) at the cost of taking custody and introducing the withdrawal/claim liveness surface. That is a genuinely different security model from the custody-free proxies, which is why the protocol kept it a separate contract rather than a fourth proxy child.[4][5]

The upto trust asymmetry, echoed in batch. upto deliberately trades a trust guarantee for flexibility: the contract guarantees the server cannot exceed the signed maximum or pay a different recipient, but within the maximum the server's charge is discretionary, and clients "bear the risk of the full amount being charged."[17] Batch-settlement inherits the same shape at channel scale — the spec states "Clients bear risk up to the signed maxClaimableAmount; the receiver authorizer determines actual totalClaimed onchain within that bound. Over-claiming is a trust violation, not a protocol violation." _(spec's own stated risk framing, not an exploited bug.)_[5]

Dependency inheritance and audit status. The exact-EVM spec states plainly that integrators "inherit [Permit2's and the proxy's] security properties and any future vulnerabilities," and a code comment marks the proxy Witness as the post-audit shape ("post-audit: extra removed from Witness").[1] So an audit occurred and changed the proxy design, but the audit report itself was not available for this review, and no audit document was located for the newer batch-settlement contract — a contract that, unlike the proxies, takes custody. The audit outcome for the proxies is therefore vendor-stated, and the batch contract's audit status is simply unknown from the sources read. _(vendor-stated / unknown)_[1]

Build-determinism and address churn. Cross-chain address sameness is fragile, and the surface has moved. The earlier revision recorded the canonical Upto proxy at 0x4020a4f3b7b90CCA423b9FabCC0CE57c6c240002 (from the dd927a2 README); the foundation README now lists the canonical Upto proxy at 0x402015c795ecb48A360bDC6e35a2EaEb313a0002, a different address — direct evidence that even a shipped contract's deterministic address can be re-mined and superseded.[10][6] The current canonical addresses are: Exact 0x402085c248EeA27D92E8b30b2C58ed07f9E20001 (unchanged), Upto 0x402015c795ecb48A360bDC6e35a2EaEb313a0002 (changed since dd927a2), and the batch-settlement stack 0x4020074e9dF2ce1deE5A9C1b5c3f541D02a10003 (settlement), 0x4020806089470a89826cB9fB1f4059150b550004 (ERC3009 collector), 0x4020425FAf3B746C082C2f942b4E5159887B0005 (Permit2 collector), reported as deployed on Base, Arbitrum, World Chain, and Polygon mainnets.[6] We did not read the live bytecode at these addresses (§7).

Counter-evidence: settlement preemption and replay. An independent preprint, Five Attacks on x402, argues that the broader x402 settlement model has structural weaknesses that bear directly on these contracts.[22] Its Attack I-B (unauthorized settlement preemption) observes that "the settlement path does not bind the facilitator identity to authorization": for EIP-3009 and the exact Permit2 path, any observer of the signed authorization can submit the transfer, racing the legitimate facilitator and consuming the nonce so the honest settlement later fails.[22] This does not let the attacker steal funds — the witness still pins the destination — but it enables griefing and breaks the facilitator's expectation of exclusive settlement. The upto proxy's msg.sender == witness.facilitator check is exactly the binding the paper finds missing, so upto is hardened against I-B while exact is not. Notably, the batch-settlement channel sidesteps this class of attack differently: vouchers carry no Permit2 nonce to burn, claims are restricted to the receiver side (claim requires msg.sender ∈ {receiver, receiverAuthorizer}; claimWithSignature requires the receiverAuthorizer signature), and the cumulative model makes a replayed claim a no-op — so the preemption vector that hits the open exact caller has no analogue on the claim path. The paper's Attack II (replay/idempotency) remains an HTTP-layer concern outside all of these contracts. These are researcher-stated attack models, not confirmed exploits of the on-chain code, but they are real dissenting analysis and qualify the security story above. _(independent preprint)_

Independent corroboration. The Permit2 mechanism the proxies and the Permit2 deposit collector depend on — witness-bound signature transfer, unordered nonces, revert-on-over-amount — is documented identically by Uniswap's own developer docs and interface source, independent of the x402 project, which raises confidence in the parts of this analysis that rest on Permit2 behavior rather than x402's own prose.[13][14]

7. Limitations

This analysis rests on a repository read at two pinned commits: the three Permit2 proxies at coinbase/x402@dd927a2 (2026-04-21, now the development fork) and the batch-settlement machinery at x402-foundation/x402@dc656bb (2026-06-09). Specific limits:

  • No audit report. The proxies are described as audited and a post-audit change is referenced, but the audit document was not located or read; for the newer, custodial x402BatchSettlement contract no audit was found at all. Audit conclusions are taken on the project's word, and the batch contract's audit status is unknown from the sources read.[1]
  • No live-bytecode verification. Canonical addresses and the deterministic-deployment story come from the repo and README; we did not read deployed bytecode on Base, Arbitrum, World Chain, or Polygon via RPC/explorer, so cross-chain sameness and the "Deployed" status are verified as intent and configuration plus the project's deployment table, not as an observed on-chain fact.[10][25][6]
  • Tests read, not executed. The Foundry unit, fork, and gas tests for the batch contract are cited for the behavior they encode (test_finalizeWithdraw_capsIfClaimedDuringDelay, test_initiateWithdraw_attackBypass_blocked, the fork lifecycle), but were read as source, not run in this review.[15]
  • Mostly first-party sourcing. Aside from Uniswap's Permit2 documentation (independent) and the Five Attacks preprint (independent, dissenting), the scheme and contract claims are first-party. x402 is a vendor-led, fast-moving protocol; the Upto proxy's canonical address already changed between the two pins, so witness shapes, scheme names, and addresses may shift again after dc656bb.[6]
  • Attack models are researcher-stated. The preemption and replay weaknesses in §6 come from a preprint's threat analysis (s17), not from a reproduced on-chain exploit of these specific contracts; they should be read as design critique to weigh, not as confirmed vulnerabilities.[22]
