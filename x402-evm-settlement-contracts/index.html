x402 EVM Settlement Contracts and Payment Schemes: Permit2 Proxies and Batch Settlement

A code-level analysis of the x402 Permit2 proxy contracts and the exact, upto, and batch-settlement schemes they serve.

Published 2026-06-01 Tags x402, permit2, evm, payments, smart-contracts, agentic-payments Status ready

Download HTML

Abstract

x402 is an HTTP-native payment protocol in which a resource server answers a request with HTTP 402, a client returns a cryptographically signed payment authorization, and a facilitator broadcasts the resulting on-chain settlement while paying the gas.[1][2] On EVM chains, settlement for ERC-20 tokens that lack native transferWithAuthorization is handled by a small family of "Permit2 proxy" contracts. This report analyzes the four artifacts named in the request against the pinned repository state (coinbase/x402 at commit dd927a2, 2026-04-21): x402BasePermit2Proxy.sol, x402ExactPermit2Proxy.sol, x402UptoPermit2Proxy.sol, and the requested x402BatchSettlement.sol. A first finding corrects the premise: there is no x402BatchSettlement.sol contract. contracts/evm/src contains only the three proxies, the ISignatureTransfer interface, and a mock token; "batch-settlement" exists solely as a scheme specification whose reference binding settles off-chain through Cloudflare, not through an EVM contract.[3][4][5][6][7] The three real contracts share a single design: the proxy — not the facilitator — is the authorized Permit2 spender, and Uniswap Permit2's "witness" pattern cryptographically binds the payment destination into the payer's signature so a facilitator can broadcast but cannot redirect funds.[3][1][8] The exact proxy always transfers the full permitted amount; the upto proxy lets an authorized facilitator transfer any amount up to the signed maximum and adds a facilitator field to the witness for caller authorization.[4][5] The contracts hold no custody, are immutable, are reentrancy-guarded, and are designed to deploy to the same address on every EVM chain via CREATE2.[9]

x402 EVM Settlement Contracts and Payment Schemes: Permit2 Proxies and Batch Settlement

1. Introduction

x402 revives the long-dormant HTTP 402 Payment Required status code as the basis for machine-payable web resources, a use case sharpened by autonomous agents that must pay per request. The protocol's division of labor is consistent across its scheme documents: the client signs an authorization, the resource server decides what is owed, and the facilitator verifies the authorization and broadcasts the settlement transaction, paying gas so the flow is gasless for the payer.[1][2] The facilitator is explicitly a broadcaster, not a trusted custodian: "the Facilitator cannot modify the amount or destination. They serve only as the transaction broadcaster."[1]

That guarantee is trivial for tokens such as USDC that implement EIP-3009 transferWithAuthorization, because the signed authorization itself names the recipient and amount. The harder case is an arbitrary ERC-20 with no such hook. x402's answer is to route those payments through Uniswap's Permit2 and a thin x402-authored proxy that occupies the "spender" slot.[1] The four files named in this request are exactly that machinery (plus one file that, as it turns out, does not exist). This report reads the contract source directly at a pinned commit and cross-checks the surrounding scheme specs and the Foundry test suite, corroborating the Permit2 mechanism against Uniswap's own documentation.[3][4][5][6][7][8][9][10]

Scope note: the exact scheme on EVM also defines EIP-3009 and ERC-7710 (smart-account delegation) transfer methods. Those paths do not touch the four files under study and are discussed only as context for why the Permit2 proxy path exists.[1]

2. Background: Permit2 and the witness pattern

Permit2 is Uniswap's standalone approval/transfer contract deployed at a single canonical address. Its SignatureTransfer module performs one-time, signature-authorized token movements without a standing ERC-20 allowance to the spender: the token owner approves Permit2 once, then signs per-transfer messages that Permit2 verifies and executes.[9][10] Two features matter for x402.

Unordered nonces. Permit2 uses non-monotonic, bitmap-based nonces: a nonce encodes a word position and a bit, so signatures can be spent or invalidated in any order rather than in sequence.[11][9] x402's upto scheme leans on exactly this for its single-use guarantee — "On EVM, Permit2's nonce mechanism enforces this" — meaning the proxy does not need its own replay bookkeeping.[12]

The witness. The function x402 uses is permitWitnessTransferFrom, which extends a signature transfer with arbitrary caller-supplied data — the witness — plus a witnessTypeString that declares its EIP-712 type. The signer commits to that extra data, and the call reverts if the requested transfer amount exceeds the signed maximum.[11][10] Uniswap describes the witness as "arbitrary signed data used to reconstruct signature data and optionally validate additional context," and notes the type string "must follow EIP712 ordering of nested structs and must include the TokenPermissions type definition."[9][10]

x402 exploits the witness to solve its core trust problem. The payer signs a Permit2 message whose spender is the x402 proxy, not the facilitator, and whose witness contains the destination address. Because the destination is inside the signed witness, the facilitator who broadcasts the transaction cannot change where the money goes: "The spender in the signature is the x402ExactPermit2Proxy, not the Facilitator. This Proxy enforces that funds are only sent to the witness.to address."[1] The proxy's job is therefore narrow: be a fixed, well-known spender, reconstruct the witness hash exactly as the payer signed it, and hand everything to Permit2.

3. The payment schemes: exact, upto, batch-settlement

The three schemes differ in when and how much value moves.

exact transfers a specific amount the resource server knows in advance — paying to view an article, buying credits, an LLM paying for a tool call.[13] On EVM it can be realized three ways, ranked by the spec: EIP-3009 (recommended, simplest, for tokens like USDC), Permit2 + proxy (the universal fallback for any ERC-20), and ERC-7710 (smart-account delegation). If no method is specified, implementations prefer EIP-3009 then Permit2.[1] Only the Permit2 path uses x402ExactPermit2Proxy.

upto authorizes a maximum and settles the actual amount, determined at settlement time from resource consumption — pay-per-token LLM output, metered bandwidth, dynamic compute.[12] It is Permit2-only by construction: EIP-3009 "is not supported for the upto scheme because it requires exact amounts at signature time."[2] Two properties of upto are worth isolating:

  • Phase-dependent amount. The same PaymentRequirements.amount field means the maximum at verification time and the actual amount to settle at settlement time; the settled amount must be ≤ the authorized maximum and may be 0 (an unused authorization simply expires with no on-chain transaction).[12][2]
  • Facilitator binding. The server advertises its address; the client must place it in witness.facilitator, "which binds the authorization to a specific facilitator, preventing unauthorized settlement by other parties."[2]

batch-settlement is categorically different: "the commitment is accepted, access is granted immediately, and financial settlement occurs later through a process defined by the network binding."[14] Unlike exact/upto, settlement "stores [the commitment] rather than executing a transfer," returning a commitment identifier instead of a transaction hash; value moves later via the binding's redemption process.[14] The spec defines two trust models — capital-backed (escrow, payment channel, delegated wallet authorization) and credit-backed (a network intermediary underwrites against a billing identity).[14] The only shipped binding, cloudflare:402, is credit-backed: it authenticates commitments with HTTP Message Signatures (RFC 9421), grants access immediately, and has Cloudflare act as Merchant of Record, billing the signature agent's identity and settling off-chain on a periodic cycle.[15]

This is why the scheme→contract mapping is asymmetric. exact and upto each map to an on-chain proxy; batch-settlement maps to off-chain (or network-defined) infrastructure and, at the pinned commit, ships no EVM contract at all.

4. Contract code analysis

4.1 x402BasePermit2Proxy — the shared base

x402BasePermit2Proxy is an abstract contract inheriting OpenZeppelin's ReentrancyGuard. It stores the Permit2 address as an immutable set once in the constructor, reverting with InvalidPermit2Address on the zero address. The NatSpec explains the immutability is deliberate — it "eliminat[es] any post-deployment initialization race," and using the same canonical Permit2 argument on every chain "keeps the initCode identical, preserving CREATE2 address determinism."[3]

The base provides two internal helpers that the children compose:

  • _settle(...) performs the common validation and the actual Permit2 call. It reverts if settlementAmount == 0 (InvalidAmount), owner == address(0) (InvalidOwner), to == address(0) (InvalidDestination), or block.timestamp < validAfter (PaymentTooEarly). It then builds SignatureTransferDetails{to, requestedAmount: settlementAmount} and calls PERMIT2.permitWitnessTransferFrom(permit, transferDetails, owner, witnessHash, witnessTypeString, signature). Crucially, the child computes its own witnessHash and witnessTypeString — the base is agnostic to the witness shape.[3] The upper time bound is not re-checked here; it is delegated to Permit2's deadline, as the test suite notes ("validBefore was removed - upper time bound is enforced by Permit2's deadline").[7]
  • _executePermit(...) supports the fully gasless EIP-2612 flow. It first requires the EIP-2612 value to equal the Permit2 permitted amount, reverting Permit2612AmountMismatch otherwise — preventing a mismatch between the approval the payer grants Permit2 and the amount Permit2 is told it may move.[3] It then calls IERC20Permit(token).permit(owner, address(PERMIT2), ...) inside a try/catch that catches Error(string), Panic(uint256), and raw bytes, emitting EIP2612PermitFailedWith{Reason,Panic,Data} rather than reverting. The design rationale is explicit: "The actual permit call does not revert on failure because the approval might already exist or the token might not support EIP-2612."[3] The Foundry tests confirm both halves — settlement still succeeds when the permit reverts (test_settleWithPermit_succeedsWhenPermitFails), and the matching failure event is emitted for each revert flavor.[7]

The base also defines the EIP2612Permit struct (value, deadline, r, s, v) and the Settled / SettledWithPermit events.[3]

4.2 x402ExactPermit2Proxy — fixed-amount transfers

The exact proxy is a thin concrete child. Its witness is Witness{address to; uint256 validAfter} and its type string is "Witness witness)TokenPermissions(address token,uint256 amount)Witness(address to,uint256 validAfter)".[4] Its settle(permit, owner, witness, signature) computes witnessHash = keccak256(abi.encode(WITNESS_TYPEHASH, witness.to, witness.validAfter)) and calls _settle with the settlement amount hard-wired to permit.permitted.amount — i.e., it always transfers the entire permitted amount, "similar to EIP-3009's transferWithAuthorization behavior."[4] The test test_settle_transfersExactPermittedAmount and the bare Witness{to, validAfter} constructor in the test harness confirm both the exact-amount behavior and the absence of any facilitator field.[8] settleWithPermit(...) is identical except it first calls _executePermit to submit the EIP-2612 approval. Both functions are nonReentrant.[4]

Notably, the exact proxy imposes no caller restriction: any address can broadcast a valid settle. This is safe against fund theft — destination and amount are fixed by the signature, so an arbitrary caller cannot redirect or inflate the payment. It is not, however, safe against settlement preemption: because anyone holding the signed authorization can submit it, an attacker can front-run the legitimate facilitator and consume the Permit2 nonce, which independent security research frames as a structural flaw ("the settlement path does not bind the facilitator identity to authorization").[16] The upto proxy's facilitator field is precisely the mitigation for this class of attack (§4.3, §5); the exact proxy has no equivalent and is therefore preemptable. _(This is an independent researchers' framing of a design gap, discussed further in §6.)_

4.3 x402UptoPermit2Proxy — flexible-amount transfers

The upto proxy is structurally similar but adds variability and access control. Its witness is Witness{address to; address facilitator; uint256 validAfter}, with type string "...Witness(address to,address facilitator,uint256 validAfter)".[5] Its settle takes an extra caller-supplied amount and enforces two new guards before settling:

if (amount > permit.permitted.amount) revert AmountExceedsPermitted();
if (msg.sender != witness.facilitator) revert UnauthorizedFacilitator();

It then folds the facilitator into the witness hash (keccak256(abi.encode(WITNESS_TYPEHASH, witness.to, witness.facilitator, witness.validAfter))) and calls _settle with the caller's amount.[5] So the facilitator chooses the final amount at settlement, but only within two bounds the payer signed: it cannot exceed the permitted maximum (also enforced independently by Permit2 itself[11]), and only the exact address the payer named as facilitator may call. The test suite exercises all of this: partial amounts succeed (test_settle_allowsPartialAmount, testFuzz_settle_partialAmountsSucceed), over-permit amounts revert (testFuzz_settle_amountNeverExceedsPermitted), and an attacker who is not the named facilitator reverts with UnauthorizedFacilitator.[7] settleWithPermit adds the same two guards plus the EIP-2612 step.[5]

The facilitator field is the key design difference from exact. Because an upto facilitator has discretion over the amount, the protocol restricts who may exercise that discretion to a single signed address — a restriction the exact proxy neither needs nor has.[4][5][2]

4.4 The "missing" x402BatchSettlement.sol

The fourth requested file, x402BatchSettlement.sol, does not exist in contracts/evm/src at the pinned commit. The directory contains exactly: x402BasePermit2Proxy.sol, x402ExactPermit2Proxy.sol, x402UptoPermit2Proxy.sol, interfaces/ISignatureTransfer.sol, and mocks/MockGenericERC20.sol.[3][4][5] "Batch settlement" is real, but it lives under specs/schemes/batch-settlement/ as two Markdown specifications — the abstract scheme and the cloudflare:402 binding — neither of which references an EVM contract.[14][15] This is internally consistent: the scheme's whole premise is that value moves later and off the synchronous request path, so the credit-backed Cloudflare binding needs no on-chain settlement contract; it uses RFC 9421 HTTP Message Signatures and off-chain billing instead.[14][15] A future capital-backed binding (escrow or payment-channel) could introduce an EVM contract, but none ships today.

5. Security properties and threat model

Reading the contracts and the README's security section together yields a compact threat model.[3][4][5][6]

  • Destination integrity. The witness binds to into the payer's signature, so a malicious or compromised facilitator cannot redirect funds; the README states the witness pattern "enforces payTo address," and the spec calls this out as the proxy's central purpose.[1][6]
  • Caller integrity (upto only). The facilitator field plus the msg.sender != witness.facilitator check stop a third party from settling someone else's upto authorization with an amount of their choosing.[5][2]
  • No custody. Tokens move directly from owner to witness.to through Permit2; the proxy never holds a balance. The README asserts "Contracts never hold tokens," and test_settle_proxyNeverHoldsTokens checks the proxy balance is zero after settlement.[6][7]
  • Immutability and reentrancy. "No upgrade mechanism, no owner, no admin functions"; every external settle function is nonReentrant, and test_settle_blocksReentrancy (driven by a malicious reentrant mock Permit2) confirms the guard fires.[6][7]
  • Replay / single-use. Provided by Permit2's unordered nonce, not by the proxy. Each authorization can be settled at most once.[12][9]
  • Amount safety, twice over. The upto proxy checks amount <= permit.permitted.amount, and Permit2's permitWitnessTransferFrom independently reverts if the requested amount exceeds the signed permission — defense in depth.[5][11][10]
  • Time bounds. Lower bound validAfter is enforced in _settle (PaymentTooEarly); upper bound is Permit2's deadline.[3][7]
  • EIP-2612 robustness. The non-reverting try/catch means a redundant, already-granted, or unsupported permit cannot brick an otherwise valid settlement, while the value == permittedAmount precheck prevents an under- or over-scoped approval.[3][7]
  • Cross-chain determinism. The proxies target the same address on every EVM chain via Arachnid's CREATE2 deployer, which requires byte-identical initCode; foundry.toml sets cbor_metadata = false and bytecode_hash = "none" so the compiler does not append an environment-dependent IPFS metadata hash that would break address determinism.[3][6][17]

Residual trust assumptions: integrators inherit Permit2's and the proxy's correctness, and upto payers trust the server to charge fairly (§6).

6. Discussion

Why two proxies instead of one. The witness shapes differ ({to, validAfter} vs {to, facilitator, validAfter}), which changes the EIP-712 type hash and therefore the signature domain. Sharing the validation and Permit2 plumbing in an abstract base while letting each child own its witness is a clean separation: the base never assumes a witness layout, so a new scheme could be added as another child without disturbing the settlement core.[3][4][5]

The upto trust asymmetry. upto deliberately trades a trust guarantee for flexibility. The contract guarantees the server cannot exceed the signed maximum or pay a different recipient, but within the maximum the server's charge is discretionary. The spec is candid: clients "bear the risk of the full amount being charged," and "Malicious servers could charge up to amount regardless of actual usage." _(This is the spec's own stated risk framing, not an exploited bug.)_[12] Setting a tight maximum is the client's only on-chain protection.

Dependency inheritance. The exact-EVM spec states plainly that "integrators inherit [Permit2's and the proxy's] security properties and any future vulnerabilities," and a code comment marks the current Witness as the post-audit shape ("post-audit: extra removed from Witness").[1] So an audit occurred and changed the design, but the audit report itself was not available for this review; the audit outcome is therefore vendor-stated even though the code behavior is verified from source. _(vendor-stated)_[1]

Build-determinism caveat. Cross-chain address sameness is fragile. The README documents that the Exact proxy was deployed before the metadata fix and therefore ships a pre-built exact-proxy-initcode.hex to reproduce its original address, while Upto is compiled from source with metadata disabled.[6] It further flags a legacy Base Sepolia Upto deployment at a different address with different (CBOR-metadata) bytecode, superseded by the canonical 0x4020a4f3…0002.[6] The canonical addresses are 0x402085c248EeA27D92E8b30b2C58ed07f9E20001 (Exact) and 0x4020a4f3b7b90CCA423b9FabCC0CE57c6c240002 (Upto). _(Sources spell the Upto address with different checksum capitalization but the same underlying address.)_[2][6]

Counter-evidence: settlement preemption and replay. An independent preprint, Five Attacks on x402, argues that the broader x402 settlement model has structural weaknesses that bear directly on these contracts.[16] Its Attack I-B (unauthorized settlement preemption) observes that "the settlement path does not bind the facilitator identity to authorization": for EIP-3009 and the exact Permit2 path, any observer of the signed authorization can submit the transfer, racing the legitimate facilitator and consuming the nonce so the honest settlement later fails.[16] This does not let the attacker steal funds — the witness still pins the destination — but it enables griefing and breaks the facilitator's expectation of exclusive settlement. The upto proxy's msg.sender == witness.facilitator check is exactly the binding the paper finds missing, so upto is hardened against I-B while exact is not; this report therefore treats the exact proxy's open caller as a deliberate-but-debated trade-off rather than an unqualified safety property. The paper's Attack II (replay/idempotency) is an HTTP-layer concern outside these contracts: Permit2's nonce enforces "one settlement," but "unless the server atomically claims (pay_id, resource_id) before granting service, replay becomes a direct payment-service failure" at the web boundary.[16] These are researcher-stated attack models, not confirmed exploits of the on-chain code, but they are real dissenting analysis and qualify the security story above. _(independent preprint)_

Independent corroboration. The Permit2 mechanism the proxies depend on — witness-bound signature transfer, unordered nonces, revert-on-over-amount — is documented identically by Uniswap's own developer docs and interface source, independent of the x402 project, which raises confidence in the parts of this analysis that rest on Permit2 behavior rather than x402's own prose.[9][10]

7. Limitations

This analysis rests primarily on a single repository read at one pinned commit (coinbase/x402@dd927a2). Specific limits:

  • No audit report. The proxy is described as audited and a post-audit change is referenced, but the audit document was not located or read; audit conclusions are taken on the project's word.[1]
  • No live-bytecode verification. Canonical addresses and the deterministic-deployment story come from the repo and config; we did not read deployed bytecode on Base or any chain via RPC/explorer, so cross-chain sameness is verified as intent and configuration, not as an observed on-chain fact.[6][17]
  • Mostly first-party sourcing. Aside from Uniswap's Permit2 documentation (independent), the scheme and contract claims are first-party. x402 is a vendor-led, fast-moving protocol; witness shapes, scheme names, and addresses may shift after this commit. The already-superseded legacy Upto deployment is evidence the surface has churned once.[6]
  • Point-in-time absence. "No x402BatchSettlement.sol" is true at dd927a2; a future capital-backed batch-settlement binding could add an EVM contract.[14]
  • Attack models are researcher-stated. The preemption and replay weaknesses in §6 come from a preprint's threat analysis (s17), not from a reproduced on-chain exploit of these specific contracts; they should be read as design critique to weigh, not as confirmed vulnerabilities.[16]
