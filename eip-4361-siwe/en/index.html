A Deep Dive into EIP-4361 (Sign-In with Ethereum)

A primary-source reconstruction of the spec's norms, standardization history, ecosystem, and security risks

Abstract

EIP-4361 (Sign-In with Ethereum, SIWE) is a Final-status ERC that defines a standard message format by which Ethereum accounts authenticate to off-chain services. This report reconstructs the specification's normative content (ABNF grammar, MUST/SHOULD requirements), its standardization history (the Ethereum Foundation/ENS RFP and the selection of Spruce), the reference implementation and ecosystem adoption, and the known security and privacy risks, working primarily from primary sources. Key findings: (1) a SIWE message is human-readable structured plaintext with domain, address, uri, version, chain-id, nonce (8+ alphanumeric), and issued-at required; EIP-191 verification is a MUST for EOAs and ERC-1271 a SHOULD for contract wallets. (2) The spec's security model concentrates on wallet-side domain matching (MUST), mandatory display of key fields (MUST), and binding sessions to the address (MUST) — a direct response to the phishing and replay problems of pre-standard ad-hoc signature login. (3) The ecosystem has matured through the reference libraries, framework integrations (RainbowKit/NextAuth), an OIDC bridge, and adoption by a regulated financial service (Monerium), yet the reference TypeScript library itself states it has not undergone a formal security audit. (4) The ERC-1271 cross-account signature replay (a real 2023 incident), the linkability of wallet-address login to on-chain history, and blind signing remain live risks — the latter driving the 2026 Clear Signing (ERC-7730) effort. SIWE became the model for CAIP-122 (chain-agnostic generalization), SIWS (Solana), and x402's SIWX, making it the prototype of the "wallet-signature authentication" pattern well beyond a single chain.

A Deep Dive into EIP-4361 (Sign-In with Ethereum)

Introduction

Web login has converged on a handful of centralized identity providers. Spruce's SIWE documentation summarizes: "Today's login experiences rely on accounts controlled by centralized identity providers, for-profit behemoths like Google, Facebook, and Apple"[1]. The Ethereum ecosystem had already distributed a different kind of account at scale — on-chain accounts whose keys users hold — and dApps were using those accounts' signing ability for improvised logins before any standard existed. EIP-4361 standardizes that practice into a single verifiable message format, describing "how Ethereum accounts authenticate with off-chain services by signing a standard message format parameterized by scope, session details, and security mechanisms (e.g., a nonce)"[2][3].

This report analyzes EIP-4361 in three layers: first, the normative structure of the specification — what is MUST versus SHOULD, and why; second, how the standard came to be — who commissioned it and who wrote it; third, the reality beyond the text — the state of the reference implementation, the actual scope of adoption, and the risks the spec does not solve. A companion report (caip-122) covers the chain-agnostic generalization, so this one stays focused on the Ethereum context.

Background and Standardization History

SIWE is unusual in being a commissioned standard rather than purely community-grown. In July 2021 the Ethereum Foundation and ENS issued a public RFP for a "Sign-In with Ethereum" specification, and Spruce (SpruceID), a decentralized identity software company, was selected[4][5]. Announcing the start of work in September 2021, Spruce committed to a best-practices survey, user research, a specification draft, and a reference implementation, pledging that "development will happen in the open"[5]. EIP-4361 was created on October 11, 2021, authored by Wayne Chang and Gregory Rocco (Spruce), Brantly Millegan and Nick Johnson (ENS), and Oliver Terbu; it subsequently reached Final status as a Standards Track ERC[2].

That commissioning shaped the standard's character. The goal was not to invent a new authentication technology but to converge an existing practice into an interoperable format — one wallets can parse and display, and servers can verify consistently[1][3]. The reference implementation (the spruceid/siwe TypeScript library) notes its Ethereum Foundation and ENS sponsorship and remains maintained as of 2026 (1.1k stars; SIWE PARSER 3.0.0 released January 2025)[3].

Message Format and Protocol Analysis

Message structure

A SIWE message is structured plaintext defined in ABNF. The canonical first line is ${scheme}:// ${domain} wants you to sign in with your Ethereum account:, followed by the address, a blank line, an optional statement, and key-value lines for URI:, Version:, Chain ID:, Nonce:, Issued At:, and the optional fields[2]. Required fields are domain (RFC 3986 authority), address, uri, version, chain-id (EIP-155), nonce, and issued-at (RFC 3339); statement, expiration-time, not-before, request-id, and resources are optional[2]. The normative details are precise: the address MUST use EIP-55 checksum encoding, version MUST be 1, the nonce is at least eight alphanumeric characters (nonce = 8*( ALPHA / DIGIT )), and the statement MUST NOT contain a newline[2].

The human-readable plaintext design is deliberate. Because the format is structured, wallets can parse the message and show the user what they are signing — and the spec indeed requires (MUST) that wallets display scheme, domain, address, statement, and resources by default before signing[2].

Signing and verification

Verification splits by account type. For EOAs, "the verification method specified in ERC-191 MUST be used" — personal_sign-style ECDSA with ecrecover[2]. For contract accounts, "the verification method specified in ERC-1271 SHOULD be used, and if it is not, the implementer MUST clearly define the verification method," and the verifying contract MUST be resolved from the message's chain-id[2]. With the growth of smart accounts this path was complemented by EIP-6492 (signature validation for not-yet-deployed counterfactual wallets); Base (Coinbase) documentation advises that "for purely offchain signature verification such as 'Sign-In With Ethereum,' ensure you are using an ERC-6492-compliant signature verification library"[6][7].

The relying party's verification procedure is ordered: (1) check ABNF conformance; (2) check parsed fields against expected values (expiration-time, nonce, request-uri, etc.); (3) verify the signature; (4) establish the session — where "Sessions MUST be bound to the address and not to further resolved resources that can change" (such as ENS names)[2]. Interpretation of the resources list is explicitly out of scope[2].

The flow in framework integrations

The canonical production integration is "server issues nonce → client builds and signs the message → server parses, verifies, and issues a session." RainbowKit ships a first-class SIWE adapter combined with NextAuth, where on successful authentication the session token's sub (subject) is the user's Ethereum address[8]. The pattern shows SIWE grafting naturally onto existing web session infrastructure (cookies, JWTs): it does not replace the session layer but replaces the password at the session's starting point[8][2].

Security Requirements and Known Risks

Defenses the spec mandates

The center of gravity in the spec's security section is wallet-side responsibility. "Wallet implementers MUST prevent phishing attacks by verifying the origin of the request against the scheme and domain fields" — blocking attacks in which a phishing site relays a legitimate service's SIWE message for signing, by detecting the mismatch between the requesting origin and the message's domain[2]. A nonce "SHOULD be selected per session initiation with enough entropy to prevent replay attacks," with privacy-preserving variants (derived from a recent block hash or timestamp) also mentioned[2]. HTTPS is a SHOULD for web communication, and if an ERC-1271 implementation or its dependent data changes signature computation, servers SHOULD invalidate sessions appropriately[2].

Risks beyond the spec

ERC-1271 cross-account replay. In a real vulnerability disclosed in 2023, when one owner controls multiple smart contract accounts (SCAs) and an application omits the account address from the signed data, "the same signature would be valid across both accounts" — affecting wallets including LightAccount, OKX SmartAccount, Kernel, Safe (EIP4337Fallback), and Argent, and applications including Permit2, Cowswap, and OpenSea[9]. SIWE itself embeds the address field in the message, so it is not vulnerable in exactly this form; but the incident carries the general lesson for the ERC-1271 path — bind full context into the signed payload and enforce it in the verifier — and a SIWE verifier that is lax about field checks recreates the same class of risk[9][2].

Blind signing and the display-mandate gap. The spec makes wallet field display a MUST, yet signing UX across the ecosystem still frequently amounts to approving unreadable data. That problem culminated in the Ethereum Foundation-led Clear Signing standard (ERC-7730) in 2026 — human-readable descriptions before signing — motivated by major incidents exploiting blind signing[10]. SIWE messages, designed to be human-readable from the start, are close to the model answer here; but we found no measured data on how consistently wallets honor the display mandate (see Limitations).

Privacy: the address is a persistent identifier. SIWE login hands the service a wallet address, and an address is pseudonymous, not anonymous: "if an observer can link the pseudonymous address to a real-world identity, perhaps through a KYC-compliant exchange ramp, the entire financial history of that user becomes public"[11]. Logging into many services with one persistent address creates structural linkability across services and on-chain activity[11].

An unaudited reference implementation. The reference TypeScript library's README states plainly: "Our TypeScript library for Sign-In with Ethereum has not yet undergone a formal security audit"[3]. A Final standard does not confer assurance on its most-used implementation — a fact services placing SIWE at their authentication front line should register.

Ecosystem and Adoption

Libraries and frameworks. Around Spruce's maintained TypeScript reference implementation[3], mainstream wallet-connection stacks have integrated SIWE as a first-class feature — RainbowKit with NextAuth among them[8]. An OIDC bridge also exists: spruceid/siwe-oidc wraps SIWE as an OpenID Connect identity provider, letting existing OIDC clients (traditional web apps, enterprise SSO) add Ethereum wallet login without code changes[12].

Commercial adoption. Adoption extends beyond dApps into regulated finance. Monerium, an EU e-money issuer, uses EIP-4361 messages to authorize profile, payment-history, and IBAN access and payment initiation, presenting SIWE as letting users "authenticate securely using your wallet, eliminating the need for traditional usernames and passwords"[13]. No public quantitative metrics of SIWE login volume exist, however, so adoption statements rest on qualitative signals (see Limitations).

The prototype for derivative standards. EIP-4361's largest impact may lie outside Ethereum. CAIP-122 describes itself as work "meant to generalize and abstract the Sign in With Ethereum specification, thereby making EIP-4361 a specific implementation of this specification"[14]; Phantom's Sign-In-With-Solana is "modeled after EIP-4361 ... but extends beyond its capabilities"[15]; and the x402 protocol's SIWX extension uses EIP-4361 verbatim as its EVM message format[16]. The SIWE message design — domain-bound, human-readable, structured plaintext with a nonce and temporal bounds — has become the de facto prototype for wallet authentication across chains.

Relationship to passkeys. WebAuthn passkeys and SIWE are often framed as competitors, but they operate at different layers: passkeys authenticate at the device/credential level, SIWE at the on-chain account level. In practice they compose: Coinbase Smart Wallet uses a WebAuthn passkey as the smart account's primary signer, and that account signs SIWE messages via the ERC-1271/6492 path[7]. In this composition the passkey handles key-management UX while SIWE provides the service-facing authentication format[7][6].

Discussion

SIWE's promise is self-sovereignty: no loss of service access through an IdP account suspension, and no login relationship becoming a platform operator's data asset[1]. The price of that promise is the absence of what IdPs provided. Account recovery (the analogue of a password reset), key rotation, and multi-device synchronization are all pushed down to the wallet layer, and as the wallet-authentication-factor taxonomy shows, security then concentrates in key management[17]. Community skepticism goes further: in public discussion at the standard's debut, critics noted that "credential loss is literally irrevocable, which is the last thing home users want in an authentication system," and that since a core value of corporate SSO is onboarding/offboarding policy control, "a globally distributed authentication fabric is actually an anti-feature for those people"[18]. This suggests SIWE's fit is bounded to consumer dApps and contexts where self-sovereignty is a genuine requirement — it is not a standard that replaces enterprise IAM. That academic work trends toward bridging SIWE-style wallet authentication with established protocols like OIDC[19][12] is itself evidence that a pragmatic middle ground between the pure self-sovereign model and existing web infrastructure is needed.

On balance, what EIP-4361 got right is restraint of scope. The standard specifies only the authentication message format and verification rules, leaving session management, authorization, and identity attributes out of scope. That restraint is why SIWE could be grafted onto NextAuth sessions, OIDC IdPs, CACAO capabilities, and the x402 payment flow alike[8][12][16]. Meanwhile, the expectation the spec places on wallet display duties still has a gap against the ecosystem's blind-signing reality[10] — and that gap remains the weakest link in SIWE's trust model.

Limitations

  • No quantitative adoption metrics: we could not find public statistics on SIWE login volume or the number of adopting services. Adoption statements are qualitative, based on library integrations and commercial cases.
  • Wallet compliance unmeasured: we did not measure how consistently major wallets honor the spec's mandatory field display. The Clear Signing effort is only an indirect signal.
  • Access-limited literature: the ACM DLT paper on bridging Web3 identifiers (10.1145/3719661) returned 403 and was cited at abstract level; we also found no peer-reviewed paper analyzing SIWE in isolation.
