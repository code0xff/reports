## 초록

구글은 오늘 올린 글에서 그동안 설명으로만 존재했던 정책에 날짜를 박았다.
Workspace와 Google Cloud 에이전트는 REST 토큰 대신 MCP 서버와 전용 Agent
Identity를 쓰게 되며, 기존 경로는 2027년 2월 1일부터 계약상 막힌다.[^s01]
대형 플랫폼 바깥에서는 한 결제 라이브러리가, x402와 MPP를 관리하는
표준화 기구들이 세 번의 브리프 주기 동안 해내지 못한 일을 해냈다 — 두
프로토콜을 같은 결제 경로에서 동작하게 만들어, Solana MPP 챌린지를 x402
퍼실리테이터를 통해 정산하도록 한 것이다.[^s02] OpenAI의 안정 버전 Agents
SDK 라인은 최근 이틀 다룬 알파 라인의 Codex 통합 혼란과는 무관하게 샌드박스
보안을 강화했고,[^s03] OpenAI와 Cisco는 Codex가 방어 코드를 직접 작성하는
오픈소스 도구 Shirudo를 내놨다.[^s04] 두 브리프 전에 나온 x402 지급주소
검증 질문은 여전히 답이 없다.[^s05][^s06]

## 서론

이 브리프는 AI 에이전트, 개발자 도구, 에이전트 결제를 다루는 정기 보고서다
— 에이전트 프레임워크, 에이전트와 가맹점을 잇는 결제 레일(x402, AP2, ACP,
UCP, MPP, L402, Trusted Agent Protocol과 그 후속 규격), 카드 네트워크와
PSP의 에이전트 커머스 제품, 에이전트 신원 및 권한 부여가 대상이다. 다루는
기간은 2026년 11월 23일부터 25일까지이며, 이전 열네 편의 브리프와
대조해 중복을 걷어냈다. Ars Technica는 아마존이 공격자가 조종하는 AI
에이전트가 사람의 개입 없이 제로데이를 발견하고 악용했다고 밝혔다는
기사를 냈는데, 이 브리프는 해당 기사를 가져오지도, 아마존의 1차 출처를
찾지도 못했다. 그래서 간접 인용 대신 이 주장을 아예 다루지 않았다 —
자세한 내용은 `working/gaps.md`에 있다.

## 오늘의 움직임

### 구글, Workspace 에이전트에 MCP를 의무화하며 날짜를 박다

구글은 몇 주째 에이전트 거버넌스를 조각조각 발표해왔다 — Agent Gateway,
Model Armor, 시맨틱 정책. 오늘 글은 그 조각들을 하나로 묶고, 그전에는
없던 것을 더했다: 시행일이다. 2027년 2월 1일부터 발효되는 Workspace의
"AI Tools Addendum"은 에이전트가 Gmail, Drive, Docs, Sheets, Calendar,
Chat, Tasks에 접근할 때 REST API가 아니라 이번에 정식 출시된 MCP 서버나
새 CLI를 거치도록 요구한다. 그 위에 사용량 기반 과금이 2027년 4월 1일부터
시작된다.[^s01] MCP 서버와 CLI 모두 권한 검사와 DLP 검사를 내장하고
있으며, MCP 서버는 에이전트로 등록되지 않은 OAuth 클라이언트의 요청
자체를 거부한다.[^s01]

신원 쪽은 별개의, 역시 새로운 조각이다. Google Cloud의 Agent Registry를
통해 발급되는 Agent Identity는 공유되거나 수명이 긴 자격증명을 에이전트별
전용 OAuth 클라이언트 ID로 대체하며, 하나를 폐기하면 "접근이 즉시
멈춘다."[^s01] 모든 LLM·MCP·A2A 요청을 이 레지스트리와 대조하고 기본값을
아웃바운드 차단으로 두는 새 Agent Gateway와 결합하면, 정책은 일회성 동의
화면이 아니라 요청 경로 자체에 놓인다 — 구글의 표현을 빌리면 "유효한
토큰만으로는 더 이상 충분하지 않다."[^s01] 다만 시간제한 승인, 에이전트
활동을 사용자가 보고 취소할 수 있는 대시보드, 파일 단위로 좁힌 Workspace
접근 제한 같은 항목은 아직 "출시 예정"일 뿐 실제로 작동하지 않는다. Model
Armor나 DLP 검사의 탐지율이나 오탐율은 구글이 숫자로 밝히지 않았기 때문에,
이것이 집행인지 가시성 확보인지는 아직 열린 질문이다.

### mppx 0.22.0, x402와 MPP를 한 경로에 올리다

이 브리프는 세 번째 주기째 x402 재단 거버넌스를 "무엇이 나왔는가"가 아니라
"누가 결정하는가"의 이야기로 다뤘다. 그 흐름을 11월 24일 라이브러리
릴리스 하나가 깼다. Viem·Wagmi 팀(wevm)의 결제 클라이언트·서버
라이브러리 `mppx`가 0.22.0에서 네이티브 `solana/charge` MPP 챌린지를
기존 Solana `exact` x402 요구사항과 같은 경로에 나란히 올렸다. 클라이언트가
부분 서명한 전송은 그 경로의 x402 퍼실리테이터를 통해 검증·정산되는데, 이
퍼실리테이터가 두 프로토콜 모두의 수수료 지불자 역할을 겸한다.[^s02] 이는
두 프로토콜의 표준화 기구가 합의해서 나온 게 아니라 라이브러리
유지보수자가 만든 상호운용성이다 — 이 브리프가 추적해온, 플랫폼이
움직이는 속도와 재단이 결정하는 속도 사이의 간극을 배포 쪽에서 메운
사례다. 같은 릴리스는 이더리움 에이전트 신원 표준인 ERC-8004 검증에
신뢰 가능한 수신처 설정을 추가해, 한 서비스를 겨냥해 서명된 요청이 다른
서비스에 재전송되는 것을 막는다.[^s02] 이 두 변경은 오늘 나온 릴리스
자체가 유일한 출처이며, 이 시점까지 다른 곳의 독립적인 보도는 없었다.

### OpenAI, 아무도 안 보던 샌드박스를 강화하다

지난 두 브리프는 OpenAI Agents SDK의 v1.0.0 알파 라인이 네이티브 Codex
지원을 붙이면서 3일 만에 자체 저장 형식을 두 번 깨뜨린 이야기를 다뤘다.
11월 24일, 별도로 운영되는 안정 버전 0.x 라인이 v0.26.0을 내놨는데, 이
변경은 그 소동과 무관하다: Docker 샌드박스는 권한이 과한 컨테이너와 추가
capability를 아예 거부하고, CPU 제한과 TAR 경로 검증은 실행 단위가 아니라
구성요소 단위로 범위를 좁혔으며, Codex 툴을 통한 로컬 이미지 접근에는
명시적인 애플리케이션 승인이 필요해졌다.[^s03] 릴리스 자체의 자동 검토는
이를 "지원되는 업그레이드 경로를 갖춘 마이너 버전, 출시 승인"이라고
평가하는데, 이는 벤더의 CI 결론일 뿐 독립적인 검증은 아니다.[^s03] 같은
SDK 안에서 서로 다른 속도로, 서로 다른 이유로 움직이는 두 릴리스 라인이
존재한다는 사실 자체가, OpenAI가 1.0 전환을 어떻게 관리하는지 보여주는
작은 단서다.

### Shirudo: 정책 대신 코드를 쓰는 에이전트

OpenAI와 Cisco는 11월 23일 Shirudo를 오픈소스로 공개했다. 운영자가 영구
패치를 준비하는 동안 서비스를 재시작하지 않고도 악용된 코드 경로를 막는,
서명된 임시 "shield"를 배포하는 eBPF 도구다.[^s04] 여기서 Codex의 역할은
좁다 — shield를 생성하고 테스트하는 것뿐이며, 로드하기 전에는 여전히
사람 운영자의 승인이 필요하다. 유일하게 제시된 사례는 Codex가 생성한
shield가 Java의 Base64 디코더에 입력 검사를 추가해 Elasticsearch를
겨냥한 Java4Shell 공격을 막은 것으로, OpenAI는 이를 "통제된 테스트"라고
부르며 그 이상의 성능이나 오탐 데이터는 공개하지 않았다.[^s04] shield는
암호학적으로 서명되고 TPM이 로드·제거 시점을 증명할 수 있지만, 서명과 키
관리 방식 자체는 발표 글에 명시돼 있지 않다. 이 소식은 이 브리프의 핵심
범위에서 살짝 벗어난다. 에이전트 신원이나 결제가 아니라 에이전트가 직접
작성한 도구이기 때문이다. 그래도 "에이전트가 일을 하고 사람이 승인권을
쥔다"는, 이틀 전 Anthropic의 Claude Ship이 코드 리뷰에서 그린 것과 같은
구도를 이번 주 가장 선명하게 보여주는 사례다.

## 왜 중요한가

위 소식들 중 상호운용성 사례 하나를 빼면 전부 각자가 끝까지 통제하는
인프라 안에서 나왔다: 구글의 Workspace·Cloud 스택, OpenAI의 SDK와
샌드박스, OpenAI와 Cisco의 커널 도구. 예외인 상호운용성 사례도 두 프로토콜
재단이 뭔가에 합의해서 나온 게 아니라, 라이브러리 유지보수자가 클라이언트
단에서 둘을 꿰맨 결과다. 이 분야에서 어느 한 회사의 통제 밖에 있는
유일한 조각은 11월 16일 Discovery WG에서 Identity WG로 넘어간 x402
지급주소 검증 문제다. 이 문제는 사흘째 댓글이 하나도 없고, 관련 적합성
질문을 다룰 예정이던 오늘의 TSC 회의도 이 브리프의 마지막 확인 시점까지
눈에 보이는 결론을 내지 못했다.[^s05][^s06] 네 번의 브리프 주기를 거치며
굳어진 패턴은 이렇다: 한 회사가 해결책을 쥐고 있으면 하루 만에 나오고,
여러 조직의 합의가 필요하면 아예 움직이지 않는다.

## 지켜볼 신호

- 11월 25일 x402 TSC 회의가 tsc#21의 적합성 테스트 질문을 실제로
  해결했는지, 그리고 다음 브리프 전까지 wg-identity#52가 어떤 응답이라도
  받는지.
- mppx의 x402·MPP 연결을 다른 결제 라이브러리들이 따라갈지, 아니면
  라이브러리 하나만의 특이사항으로 남을지.
- 2월 시행일이 가까워지면서 구글의 새 Agent Identity 모델을 실제로 쓰는
  고객이 얼마나 되고, 얼마나 많은 고객이 여전히 REST 토큰에 머무는지.
- Java4Shell 시연 하나를 넘어선 Shirudo shield의 독립적인 검증, 그리고
  서명 방식이 문서화되는지.

## 한계

Ars Technica가 보도한 아마존의 제로데이 주장은 검증하지 못했다 — 기사
자체가 이 브리프의 접근을 거부했고, 아마존 보안 블로그 목록은 클라이언트
사이드 렌더링 때문인지 글 내용을 전혀 돌려주지 않았다. 카드 네트워크와
PSP 뉴스룸은 이번 주기에 직접 확인하지 않았다. 위에서 언급한 x402 TSC
회의는 11월 25일로 예정돼 있었지만 이 브리프의 마지막 확인 시점(일본
표준시 08:09)까지 눈에 보이게 마무리되지 않았으며, 그 결과는 다음
브리프로 넘긴다. Shirudo의 서명·키 관리 세부사항은 연결된 저장소나
문서가 아니라 발표 글에서만 확인했다.
