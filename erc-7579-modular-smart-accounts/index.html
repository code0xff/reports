ERC-7579: Minimal Modular Smart Accounts

A technical deep-dive into the minimal modular smart-account standard — interfaces, module taxonomy, ecosystem, and security.

Published 2026-06-19 Tags — Status ready

Download HTML

Abstract

ERC-7579 is an Ethereum standard that defines the minimal interfaces a smart account and its modules must implement so that modules are portable across different account implementations[1]. It sits on top of ERC-4337 account abstraction and is compatible with the EIP-7702 path for EOAs[2][3]. This report is a technical deep-dive: it explains the motivation (avoiding module lock-in), the standard's interface set, the four-way module taxonomy (validator, executor, fallback, hook)[1], the packed execution-mode encoding[1], and how validator modules plug into the ERC-4337 validation flow[1][2]. It then surveys the ecosystem — a shared reference implementation plus production accounts from Safe (via the Safe7579 adapter), ZeroDev (Kernel), Biconomy (Nexus), and OpenZeppelin — and the module tooling around it (ModuleKit, the ERC-7484 registry, SmartSessions)[4][5][6][7][8][9][10][11]. We contrast ERC-7579's minimal-interface philosophy with the more prescriptive ERC-6900[12][13][14], place it within its sibling-ERC stack (ERC-7484/7710/7715/7739/7562)[15][16][17][18][19], and examine the central security trade-off: installed modules are highly privileged, so a malicious or buggy module can endanger the account[1], which is why an attestation registry (ERC-7484) and third-party audits matter[15][20][21][22]. Findings are a June 2026 snapshot of fast-moving, largely author/vendor-led standards.

ERC-7579: Minimal Modular Smart Accounts

1. Introduction — what ERC-7579 is and why it exists

ERC-4337 brought account abstraction to Ethereum without consensus-layer changes, letting a smart contract account validate its own transactions[1]. But ERC-4337 deliberately left the account's internals — how it stores signers, session keys, recovery logic, or spending policy — unstandardized. Each smart-account vendor therefore grew its own module/plugin format, so a module written for one account did not work on another. ERC-7579 exists to fix exactly that: "The goal of this standard is to define the smart account and module interfaces and behavior that is as minimal as possible while ensuring interoperability between accounts and modules," with the explicit aims of "interoperability for modules to be used across different smart accounts" and "preventing significant vendor lock-in for smart account users"[2].

The "minimal" framing is a deliberate design choice: standardize the interface, not the implementation[2]. OpenZeppelin's description captures the resulting capability — the standard "enables accounts to install, uninstall, and interact with modules that extend their capabilities in a composable manner with different account implementations"[3]. ERC-7579 is layered on ERC-4337's validation flow today, but the authors anticipate decoupling: the spec notes a planned "upgrade path … to move the ERC-4337 dependency into an extension (ie a separate ERC) and to make it optional for smart accounts to implement"[2]. In parallel, ERC-4337's EntryPoint v0.8 added native EIP-7702 support, letting ordinary EOAs adopt smart-account code[4] — so ERC-7579 accounts can be reached both via deployed contract accounts and upgraded EOAs.

2. Background — account abstraction and the modularity problem

Under ERC-4337, users send UserOperation objects to a separate mempool; bundlers package them into a handleOps call to a singleton EntryPoint, and "this document is an account abstraction proposal which completely avoids the need for consensus-layer protocol changes"[1]. The account's required hook into this flow is validateUserOp(PackedUserOperation calldata userOp, bytes32 userOpHash, uint256 missingAccountFunds) returns (uint256 validationData)[1]. Everything above that — which signer or policy decides validity — is implementation-defined, which is the seam ERC-7579 standardizes.

The practical motivation is portability. Before a shared interface, a session-key or social-recovery module built for one account could not be reused on another; OKX's overview frames the contrast with the more constraining alternative, noting "ERC-6900 is more prescriptive, providing a detailed outline of acceptable account conduct, restricting the ability to balance complexity and security"[5] (interpretive). ERC-7579's bet is that a thin, shared interface lets a single module ecosystem serve many account vendors at once.

3. The standard — interfaces and module taxonomy

Module taxonomy. ERC-7579 defines four core module types, each with an incremental type ID that accounts and modules use to identify them: "Validation (type id: 1), Execution (type id: 2), Fallback (type id: 3), Hooks (type id: 4)"[2]. Validators decide whether an operation is authorized; executors can trigger calls from the account; fallback handlers extend the account's callable surface; hooks run pre-/post-execution checks.

Account interface. A conforming account exposes a small, fixed surface: execute(bytes32 mode, bytes executionCalldata) and executeFromExecutor(...) for execution; installModule / uninstallModule / isModuleInstalled for lifecycle; and capability-detection via accountId(), supportsExecutionMode(bytes32 encodedMode), and supportsModule(uint256 moduleTypeId)[2]. The capability-detection functions let off-chain tooling and modules discover what a given account supports before interacting with it.

Module interface. Every module must implement onInstall(bytes data), onUninstall(bytes data), and isModuleType(uint256 moduleTypeId) so the account can manage the module lifecycle and verify a module's claimed type[2].

Execution modes. ERC-7579 packs execution behavior into a bytes32 mode code. The first byte is the CallType — "0x00 for a single call, 0x01 for a batch call, 0xfe for staticcall and 0xff for delegatecall" — and the second byte is the ExecType — "0x00 for executions that revert on failure, 0x01 for executions that do not revert on failure"[2]. This lets one execute entrypoint cover single and batch calls and choose between revert-on-failure and best-effort (try) semantics.

Validation flow. Validator modules are how ERC-7579 plugs back into ERC-4337: a validator "MUST implement the IERC7579Module and the IERC7579Validator interface and have module type id: 1," and its validateUserOp(...) "MUST validate that the signature is a valid signature of the userOpHash, and SHOULD return ERC-4337's SIG_VALIDATION_FAILED (and not revert) on signature mismatch"[2][1]. The account delegates the authorization decision to whichever validator module the UserOperation selects.

4. Ecosystem & implementations

ERC-7579 ships with a shared reference implementation — erc7579/erc7579-implementation, described as the "Reference Implementation to Minimal Modular Smart Account (ERC-7579)" and co-authored by contributors from Rhinestone, ZeroDev, and Biconomy[6] — which is separate from the prose spec and serves as the canonical starting point.

Multiple independent production accounts implement the standard across distinct vendors:

  • Safe gains ERC-7579 support through the Safe7579 adapter, "a smart contract developed by Rhinestone and Safe to make Safe Smart Accounts compliant with ERC-7579," exposing 14 audited Rhinestone modules such as a dead-man switch, flash-loan, and social recovery[7][8].
  • ZeroDev Kernel is "Compatible with ERC-4337, Modular (supports ERC-7579 plugins), Highly gas-efficient"[9], and Pimlico's comparison calls Kernel "the most widely used modular smart account"[10] (vendor/third-party-stated).
  • Biconomy Nexus is described as an "ERC-7579 Modular Smart Account for Enhanced Account Abstraction"[11].
  • OpenZeppelin ships an AccountERC7579 preset in its Community Contracts[3].

Around the accounts sits a module ecosystem and tooling: Rhinestone's ModuleKit, "a development kit for building and testing smart account modules"[12]; the module registry, "an attestation registry for securely using smart account modules" that "serves as the reference implementation for ERC-7484"[13]; and reusable modules like SmartSessions, "an advanced module for ERC-7579 compatible smart accounts, enabling granular control over session keys"[14]. This is the payoff of the minimal interface — one module (e.g., SmartSessions) targeting many account implementations.

5. ERC-7579 vs ERC-6900 (and the sibling-ERC stack)

ERC-7579 is not the only modular-account standard. ERC-6900 "standardizes smart contract accounts and account modules … that allow for composable logic," coordinating "the implementation work between module developers and account developers"[15]. The difference is philosophy and scope. ERC-7579 aims to be "as minimal as possible"[2], whereas ERC-6900 is more prescriptive: Eco's guide observes that "6900 is roughly 3x the spec length of 7579 because it constrains more of the implementation"[16], and OKX similarly notes ERC-6900 "is more prescriptive, providing a detailed outline of acceptable account conduct"[5]. The adoption split tracks this divide: "6900 is implemented in Alchemy Modular Account … 7579 is implemented in Safe, ZeroDev, Biconomy, Rhinestone, and the OpenZeppelin Contracts modular account preset"[16] (interpretive — a 2026 snapshot, not a verdict; both standards continued to evolve). The contrast is a genuine trade-off rather than a simple win: ERC-6900's prescriptiveness — constraining more of the implementation and coordinating module- and account-developer expectations[15][16] — is intended to build in more safety, whereas ERC-7579's minimalism leaves storage layout and much safety responsibility to implementers in exchange for flexibility[2].

ERC-7579 also anchors a stack of sibling ERCs. ERC-7484 is the module attestation registry that lets accounts query security attestations about modules[17]. ERC-7710 (smart-contract delegation) and ERC-7715 (wallet_requestExecutionPermissions) standardize delegating and requesting scoped execution permissions[18][19]. ERC-7739 prevents cross-account signature replay for accounts owned by one EOA[20], and ERC-7562 defines the off-chain validation scope rules bundlers enforce[21]. Biconomy notes that its Nexus "architecture complies with ERC-7579, ERC-4337, ERC-7739, ERC-7562 and ERC-7484 standards" — illustrating how these are deployed together in practice[22].

6. Security considerations & analysis

The defining security property of a modular account is that installed modules are highly privileged. Because executors can initiate calls from the account and hooks gate execution (and may run via delegatecall), a malicious or buggy module can endanger the whole account. The spec's own security considerations warn that module callbacks can produce "unexpected callbacks (e.g. reentrancy)" and that "Malicious Hooks may revert on preCheck or postCheck, adding untrusted hooks may lead to a denial of service of the account"[2]. In other words, installing a module is a trust decision comparable to upgrading the account.

The standard's answer is install-time vetting via attestations. ERC-7484 frames the problem and the mitigation directly: "One solution to this security issue is to create a Module Registry that stores security attestations on Modules and allows Smart Accounts to query these attestations before using a module"[17], and Rhinestone's registry is the reference implementation of that idea[13].

The second layer of defense is third-party auditing of the implementations themselves. Concrete, independent audit evidence exists across the ecosystem: Ackee Blockchain Security "perform[ed] a security review of the Rhinestone ERC-7579 adapter for Safe smart accounts … between June 3 and June 14, 2024"[23]; Biconomy's Nexus repository carries audit reports from Zenith, Cyfrin/CodeHawks, Pashov, and Cantina[24]; and ZeroDev's Kernel repository holds ChainLight and Kalos audits plus incremental v3.2/v3.3 reports[25], with ZeroDev claiming Kernel v3 as the "first audited account for ERC-7579"[26] (vendor-stated). The Safe7579 adapter likewise advertises "14 audited modules"[7]. The caveat is standard: audited is not the same as bug-free, and audit scope and recency vary per implementation.

7. Limitations

  • The standard largely describes itself. Many interface-level claims (module type IDs, the account/module interfaces, the execution-mode encoding, the security considerations) rest on the ERC-7579 spec as the single primary source[2]. That is appropriate — a spec is the primary source for its own interfaces — but it is single-primary, and independent formal analysis of the standard is thin.
  • Vendor/author-led framing. Most "minimal / unified / unopinionated" language comes from the standard's authors and implementers (Rhinestone, Biconomy, ZeroDev, OpenZeppelin). Adoption superlatives such as Kernel being "most widely used"[10] are vendor/third-party marketing, marked accordingly.
  • Fast-moving, snapshot-bound. ERC-7579 and its siblings (7484, 7739, 7710/7715) continue to change, and module type IDs have been extended over time; this is a June 2026 snapshot. The ERC-6900-vs-7579 "adoption" picture[16] is a moment-in-time read, not a final outcome.
  • Security is conditional. Attestation registries (ERC-7484) and audits reduce but do not eliminate module risk; the privileged-module threat is intrinsic to the modular design[2].
