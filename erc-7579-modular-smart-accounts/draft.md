# ERC-7579: Minimal Modular Smart Accounts

## Abstract

ERC-7579 is an Ethereum standard that defines the *minimal* interfaces a smart account and its modules must implement so that modules are portable across different account implementations[^s01]. It sits on top of ERC-4337 account abstraction and is compatible with the EIP-7702 path for EOAs[^s02][^s03]. This report is a technical deep-dive: it explains the motivation (avoiding module lock-in), the standard's interface set, the four-way module taxonomy (validator, executor, fallback, hook)[^s01], the packed execution-mode encoding[^s01], and how validator modules plug into the ERC-4337 validation flow[^s01][^s02]. It then surveys the ecosystem — a shared reference implementation plus production accounts from Safe (via the Safe7579 adapter), ZeroDev (Kernel), Biconomy (Nexus), and OpenZeppelin — and the module tooling around it (ModuleKit, the ERC-7484 registry, SmartSessions)[^s06][^s08][^s09][^s10][^s04][^s13][^s14][^s15]. We contrast ERC-7579's minimal-interface philosophy with the more prescriptive ERC-6900[^s05][^s16][^s17], place it within its sibling-ERC stack (ERC-7484/7710/7715/7739/7562)[^s18][^s19][^s20][^s21][^s22], and examine the central security trade-off: installed modules are highly privileged, so a malicious or buggy module can endanger the account[^s01], which is why an attestation registry (ERC-7484) and third-party audits matter[^s18][^s24][^s25][^s26]. Findings are a June 2026 snapshot of fast-moving, largely author/vendor-led standards.

## 1. Introduction — what ERC-7579 is and why it exists

ERC-4337 brought account abstraction to Ethereum without consensus-layer changes, letting a smart contract account validate its own transactions[^s02]. But ERC-4337 deliberately left the account's *internals* — how it stores signers, session keys, recovery logic, or spending policy — unstandardized. Each smart-account vendor therefore grew its own module/plugin format, so a module written for one account did not work on another. ERC-7579 exists to fix exactly that: "The goal of this standard is to define the smart account and module interfaces and behavior that is as minimal as possible while ensuring interoperability between accounts and modules," with the explicit aims of "interoperability for modules to be used across different smart accounts" and "preventing significant vendor lock-in for smart account users"[^s01].

The "minimal" framing is a deliberate design choice: standardize the *interface*, not the *implementation*[^s01]. OpenZeppelin's description captures the resulting capability — the standard "enables accounts to install, uninstall, and interact with modules that extend their capabilities in a composable manner with different account implementations"[^s04]. ERC-7579 is layered on ERC-4337's validation flow today, but the authors anticipate decoupling: the spec notes a planned "upgrade path … to move the ERC-4337 dependency into an extension (ie a separate ERC) and to make it optional for smart accounts to implement"[^s01]. In parallel, ERC-4337's EntryPoint v0.8 added native EIP-7702 support, letting ordinary EOAs adopt smart-account code[^s03] — so ERC-7579 accounts can be reached both via deployed contract accounts and upgraded EOAs.

## 2. Background — account abstraction and the modularity problem

Under ERC-4337, users send `UserOperation` objects to a separate mempool; bundlers package them into a `handleOps` call to a singleton EntryPoint, and "this document is an account abstraction proposal which completely avoids the need for consensus-layer protocol changes"[^s02]. The account's required hook into this flow is `validateUserOp(PackedUserOperation calldata userOp, bytes32 userOpHash, uint256 missingAccountFunds) returns (uint256 validationData)`[^s02]. Everything above that — *which* signer or policy decides validity — is implementation-defined, which is the seam ERC-7579 standardizes.

The practical motivation is portability. Before a shared interface, a session-key or social-recovery module built for one account could not be reused on another; OKX's overview frames the contrast with the more constraining alternative, noting "ERC-6900 is more prescriptive, providing a detailed outline of acceptable account conduct, restricting the ability to balance complexity and security"[^s05] _(interpretive)_. ERC-7579's bet is that a thin, shared interface lets a single module ecosystem serve many account vendors at once.

## 3. The standard — interfaces and module taxonomy

**Module taxonomy.** ERC-7579 defines four core module types, each with an incremental type ID that accounts and modules use to identify them: "Validation (type id: 1), Execution (type id: 2), Fallback (type id: 3), Hooks (type id: 4)"[^s01]. Validators decide whether an operation is authorized; executors can trigger calls from the account; fallback handlers extend the account's callable surface; hooks run pre-/post-execution checks.

**Account interface.** A conforming account exposes a small, fixed surface: `execute(bytes32 mode, bytes executionCalldata)` and `executeFromExecutor(...)` for execution; `installModule` / `uninstallModule` / `isModuleInstalled` for lifecycle; and capability-detection via `accountId()`, `supportsExecutionMode(bytes32 encodedMode)`, and `supportsModule(uint256 moduleTypeId)`[^s01]. The capability-detection functions let off-chain tooling and modules discover what a given account supports before interacting with it.

**Module interface.** Every module must implement `onInstall(bytes data)`, `onUninstall(bytes data)`, and `isModuleType(uint256 moduleTypeId)` so the account can manage the module lifecycle and verify a module's claimed type[^s01].

**Execution modes.** ERC-7579 packs execution behavior into a `bytes32` mode code. The first byte is the CallType — "0x00 for a single call, 0x01 for a batch call, 0xfe for staticcall and 0xff for delegatecall" — and the second byte is the ExecType — "0x00 for executions that revert on failure, 0x01 for executions that do not revert on failure"[^s01]. This lets one `execute` entrypoint cover single and batch calls and choose between revert-on-failure and best-effort (try) semantics.

**Validation flow.** Validator modules are how ERC-7579 plugs back into ERC-4337: a validator "MUST implement the IERC7579Module and the IERC7579Validator interface and have module type id: 1," and its `validateUserOp(...)` "MUST validate that the signature is a valid signature of the userOpHash, and SHOULD return ERC-4337's SIG_VALIDATION_FAILED (and not revert) on signature mismatch"[^s01][^s02]. The account delegates the authorization decision to whichever validator module the UserOperation selects.

## 4. Ecosystem & implementations

ERC-7579 ships with a shared **reference implementation** — `erc7579/erc7579-implementation`, described as the "Reference Implementation to Minimal Modular Smart Account (ERC-7579)" and co-authored by contributors from Rhinestone, ZeroDev, and Biconomy[^s06] — which is separate from the prose spec and serves as the canonical starting point.

Multiple independent production accounts implement the standard across distinct vendors:

- **Safe** gains ERC-7579 support through the **Safe7579 adapter**, "a smart contract developed by Rhinestone and Safe to make Safe Smart Accounts compliant with ERC-7579," exposing 14 audited Rhinestone modules such as a dead-man switch, flash-loan, and social recovery[^s08][^s07].
- **ZeroDev Kernel** is "Compatible with ERC-4337, Modular (supports ERC-7579 plugins), Highly gas-efficient"[^s09], and Pimlico's comparison calls Kernel "the most widely used modular smart account"[^s11] _(vendor/third-party-stated)_.
- **Biconomy Nexus** is described as an "ERC-7579 Modular Smart Account for Enhanced Account Abstraction"[^s10].
- **OpenZeppelin** ships an `AccountERC7579` preset in its Community Contracts[^s04].

Around the accounts sits a **module ecosystem and tooling**: Rhinestone's **ModuleKit**, "a development kit for building and testing smart account modules"[^s13]; the **module registry**, "an attestation registry for securely using smart account modules" that "serves as the reference implementation for ERC-7484"[^s14]; and reusable modules like **SmartSessions**, "an advanced module for ERC-7579 compatible smart accounts, enabling granular control over session keys"[^s15]. This is the payoff of the minimal interface — one module (e.g., SmartSessions) targeting many account implementations.

## 5. ERC-7579 vs ERC-6900 (and the sibling-ERC stack)

ERC-7579 is not the only modular-account standard. **ERC-6900** "standardizes smart contract accounts and account modules … that allow for composable logic," coordinating "the implementation work between module developers and account developers"[^s16]. The difference is philosophy and scope. ERC-7579 aims to be "as minimal as possible"[^s01], whereas ERC-6900 is more prescriptive: Eco's guide observes that "6900 is roughly 3x the spec length of 7579 because it constrains more of the implementation"[^s17], and OKX similarly notes ERC-6900 "is more prescriptive, providing a detailed outline of acceptable account conduct"[^s05]. The adoption split tracks this divide: "6900 is implemented in Alchemy Modular Account … 7579 is implemented in Safe, ZeroDev, Biconomy, Rhinestone, and the OpenZeppelin Contracts modular account preset"[^s17] _(interpretive — a 2026 snapshot, not a verdict; both standards continued to evolve)_. The contrast is a genuine trade-off rather than a simple win: ERC-6900's prescriptiveness — constraining more of the implementation and coordinating module- and account-developer expectations[^s16][^s17] — is intended to build in more safety, whereas ERC-7579's minimalism leaves storage layout and much safety responsibility to implementers in exchange for flexibility[^s01].

ERC-7579 also anchors a stack of sibling ERCs. **ERC-7484** is the module **attestation registry** that lets accounts query security attestations about modules[^s18]. **ERC-7710** (smart-contract delegation) and **ERC-7715** (`wallet_requestExecutionPermissions`) standardize delegating and requesting scoped execution permissions[^s19][^s20]. **ERC-7739** prevents cross-account signature replay for accounts owned by one EOA[^s21], and **ERC-7562** defines the off-chain validation scope rules bundlers enforce[^s22]. Biconomy notes that its Nexus "architecture complies with ERC-7579, ERC-4337, ERC-7739, ERC-7562 and ERC-7484 standards" — illustrating how these are deployed together in practice[^s23].

## 6. Security considerations & analysis

The defining security property of a modular account is that **installed modules are highly privileged**. Because executors can initiate calls from the account and hooks gate execution (and may run via `delegatecall`), a malicious or buggy module can endanger the whole account. The spec's own security considerations warn that module callbacks can produce "unexpected callbacks (e.g. reentrancy)" and that "Malicious Hooks may revert on preCheck or postCheck, adding untrusted hooks may lead to a denial of service of the account"[^s01]. In other words, installing a module is a trust decision comparable to upgrading the account.

The standard's answer is **install-time vetting via attestations**. ERC-7484 frames the problem and the mitigation directly: "One solution to this security issue is to create a Module Registry that stores security attestations on Modules and allows Smart Accounts to query these attestations before using a module"[^s18], and Rhinestone's registry is the reference implementation of that idea[^s14].

The second layer of defense is **third-party auditing of the implementations themselves**. Concrete, independent audit evidence exists across the ecosystem: Ackee Blockchain Security "perform[ed] a security review of the Rhinestone ERC-7579 adapter for Safe smart accounts … between June 3 and June 14, 2024"[^s24]; Biconomy's Nexus repository carries audit reports from Zenith, Cyfrin/CodeHawks, Pashov, and Cantina[^s25]; and ZeroDev's Kernel repository holds ChainLight and Kalos audits plus incremental v3.2/v3.3 reports[^s26], with ZeroDev claiming Kernel v3 as the "first audited account for ERC-7579"[^s12] _(vendor-stated)_. The Safe7579 adapter likewise advertises "14 audited modules"[^s08]. The caveat is standard: audited is not the same as bug-free, and audit scope and recency vary per implementation.

## 7. Limitations

- **The standard largely describes itself.** Many interface-level claims (module type IDs, the account/module interfaces, the execution-mode encoding, the security considerations) rest on the ERC-7579 spec as the single primary source[^s01]. That is appropriate — a spec is the primary source for its own interfaces — but it is single-primary, and independent formal analysis of the standard is thin.
- **Vendor/author-led framing.** Most "minimal / unified / unopinionated" language comes from the standard's authors and implementers (Rhinestone, Biconomy, ZeroDev, OpenZeppelin). Adoption superlatives such as Kernel being "most widely used"[^s11] are vendor/third-party marketing, marked accordingly.
- **Fast-moving, snapshot-bound.** ERC-7579 and its siblings (7484, 7739, 7710/7715) continue to change, and module type IDs have been extended over time; this is a June 2026 snapshot. The ERC-6900-vs-7579 "adoption" picture[^s17] is a moment-in-time read, not a final outcome.
- **Security is conditional.** Attestation registries (ERC-7484) and audits reduce but do not eliminate module risk; the privileged-module threat is intrinsic to the modular design[^s01].
