초록

2025년부터 2026년 중반까지 AI 에이전트의 신원·인증·탐색·평판을 다루는 표준과 서비스가 서로 독립적으로 다수 등장했다. 이 보고서는 이들을 네 계층으로 분류해 정리한다. 웹 인프라 계층은 RFC 9421 HTTP Message Signatures를 재사용해 요청 단위로 에이전트를 서명 식별하는 방향(Web Bot Auth, Visa Trusted Agent Protocol)으로 수렴했고, 엔터프라이즈 IAM 계층은 에이전트를 사람 계정과 구분되는 1급 신원 객체로 등록하는 방향(Microsoft Entra Agent ID, Okta for AI Agents)으로, MCP 인가 규격은 OAuth 2.1 리소스 서버 모델로 정리됐다. 탐색 계층에서는 A2A의 /.well-known/agent-card.json, MCP 공식 레지스트리의 연합형 하위 레지스트리 모델, ERC-8004의 온체인 신원 레지스트리, x402 Bazaar 같은 결제 기반 인덱스가 병존한다. 평판 계층은 스펙은 존재하지만 실사용 데이터가 가장 희박하다. ERC-8004 에이전트 10,000건을 측정한 연구는 서비스 레코드를 노출한 에이전트가 67건, 피드백을 받은 에이전트가 628건에 불과했다고 보고했다. 전체적으로 신원 계층은 구성요소 수준의 부분 수렴이 관찰되지만 신뢰 앵커가 계층마다 달라 직접 상호운용되지 않으며, 실무에서는 표준보다 플랫폼 마켓플레이스의 심사가 먼저 신뢰 게이트키퍼로 작동하고 있다.

서론 및 배경

에이전트가 사람을 대신해 웹을 호출하기 시작하면서, 기존 웹 신원 스택이 답할 수 없는 질문이 생겼다. 서버 측 TLS 인증서는 "내가 접속한 서버가 누구인가"를 증명하지만 "이 요청을 보낸 클라이언트가 누구를 대신하는 어떤 에이전트인가"는 증명하지 않는다. Cloudflare는 이 공백을 직접 언급한다. "기존 식별 방법은 IP 주소 범위(다른 서비스와 공유될 수 있고 시간에 따라 변할 수 있음)와 user-agent 헤더(위조가 쉬움)의 조합에 의존한다. 이는 한계와 결함을 가진다."[1] IETF 측 초안도 같은 문제를 출발점으로 삼아, 목표를 "자동화된 HTTP 클라이언트가 아웃바운드 요청에 암호학적으로 서명하게 하여, HTTP 서버가 그 신원을 확신을 갖고 검증할 수 있게 하는 것"으로 규정한다.[2]

이 문제가 시급해진 배경에는 자동화 트래픽 자체의 비중 변화가 있다. 직접 확인 가능한 수치로는 Cloudflare Radar의 2025년 연간 리뷰가 있다. 2025년 12월 2일 기준으로 "사람 트래픽이 HTML 요청의 47%를, AI가 아닌 봇이 44%를 생성했다"는 것이다.[3] 같은 문서는 AI 봇 트래픽이 HTML 요청의 평균 4.2%를 차지했다고 밝힌다.[3] 이후 2026년 중반에는 자동화 트래픽이 사람 트래픽을 넘어섰다는 보도가 나왔고, 인용된 수치는 자동화 57.4% 대 사람 42.6%였다. 다만 본 보고서는 두 보도[4][5]의 본문을 직접 열람하지 못했고(양쪽 모두 스크립트 접근에 403 응답), 두 보도가 모두 Cloudflare Radar라는 단일 측정 시스템을 재인용한 것이므로 이 교차점 수치는 확인되지 않은 것으로 다룬다 _(unverified — single source)_.

같은 시기 학술·표준 진영도 문제를 정식화하기 시작했다. 한 연구는 AI 신원을 "AI 에이전트가 무엇이라고 선언되었는지와 실제로 무엇을 하는지 사이의 연속적 관계이며, 그 두 가지가 특정 시점에 서로 대응한다는 신뢰도로 한정되는 것"으로 정의한다.[6] 이 정의는 신원과 평판의 순서 관계를 설명해 준다. 관찰된 행동을 축적하려면 그 행동을 귀속시킬 안정적 식별자가 먼저 있어야 하기 때문이다. 프로토콜 비교 연구도 같은 방향을 지적하는데, 여기서는 LLM 특유의 취약성 — "프롬프트 인젝션, 아첨/유도 취약성, 환각, 기만, 정렬 실패" — 이 "순수하게 평판에만 의존하거나 주장에만 의존하는 접근을 취약하게 만든다"고 본다.[7] 제도 측면에서는 NIST NCCoE가 2026년 2월 5일 소프트웨어·AI 에이전트 신원과 인가에 관한 개념 문서를 공개하고, "AI 에이전트 신원·접근 관리를 안내하는 데 현재 또는 새롭게 사용되는 표준은 무엇인가"를 공개 질문으로 제시했다.[8] 표준을 정하는 쪽이 아직 질문 단계에 있다는 점 자체가 이 분야의 성숙도를 보여준다.

본 보고서는 네 계층으로 나눠 논의한다. 첫째 신원과 인증(누구이며 무엇을 대신하는가), 둘째 탐색·레지스트리·노출(어떻게 발견되는가), 셋째 평판·검증(신뢰할 만한가), 넷째 이들 간 비교. 기준 시점은 2026년 7월 말이다.

신원과 인증

웹 인프라 계층의 접근은 요청 자체에 서명을 붙이는 것이다. Web Bot Auth는 RFC 9421 HTTP Message Signatures를 기반으로, 에이전트가 Ed25519 키로 아웃바운드 요청에 서명하고 서버가 이를 검증하도록 한다.[2] Cloudflare 문서에 따르면 봇은 자신의 키 디렉터리를 HTTPS 도메인의 /.well-known/http-message-signatures-directory 경로에 게시하며, 이 디렉터리는 Ed25519 공개키를 담은 JWKS를 제공한다.[9] 필수 헤더는 Signature-Input, Signature, 그리고 키 디렉터리를 가리키는 Signature-Agent다.[9] 이 방식은 무엇을 제공하지 않는지도 명시한다. 초안은 서명 키가 특정 개인에게 결부되어서는 안 된다고 규정하며, 익명성을 원하는 에이전트에게는 적합한 프로토콜이 아니라고 밝힌다.[2] 즉 이것은 사업자 수준의 귀속(attribution)이지 개인 수준의 인증이 아니다.

문서 상태에는 주의가 필요하다. 본 보고서가 읽은 아키텍처 초안은 버전 05로 2026년 3월 2일 공개되어 2026년 9월 3일 만료 예정이며 후속 문서로 대체된 것으로 표시된다.[2] 반면 IETF에는 webbotauth 워킹그룹이 승인된 charter와 함께 활동 중이며, charter는 "자동화된 클라이언트(통칭 '봇')는 웹에서 점점 더 많이 사용된다. 이러한 클라이언트는 특정 주체에 속한다는 것을 안전하게 인증하고자 할 수 있다"로 시작한다.[10] 개별 초안은 만료됐지만 표준화 트랙 자체는 제도화 단계에 들어간 상태다.

Visa Trusted Agent Protocol은 같은 원시 구성요소를 상거래 문맥으로 옮긴다. 에이전트는 RFC 9421에 따라 Signature-Input과 Signature 헤더로 신원을 제시하고, 가맹점은 Visa가 https://mcp.visa.com/.well-known/jwks에 호스팅하는 공개키로 검증한다.[11] 여기서 한 걸음 더 나아가는 부분은 위임 정보다. 요청 본문의 Agentic Consumer Recognition Object는 해시된 전화번호·이메일 등 난독화된 소비자 식별자를 담은 ID 토큰과 기기·위치 맥락 데이터를 전달하며, 메시지 서명과 동일한 nonce로 서명되어 진정성 사슬을 형성한다.[11] 가맹점은 평문 개인정보를 받지 않고도 기존 고객 관계 여부를 판단할 수 있다. 다만 본 보고서가 읽은 TAP 스펙 페이지에는 버전 번호나 공개일이 명시되어 있지 않아, "현행 TAP 스펙"이라는 표현은 고정된 대상을 가리키지 못한다.[11]

엔터프라이즈 IAM 계층은 전혀 다른 앵커를 쓴다. Microsoft Entra Agent ID는 "AI 에이전트를 위한 고유 식별과 인증 기능을 제공하는 Microsoft Entra ID 내의 신원 계정"으로 에이전트를 정의하고, "사람 사용자와 애플리케이션을 위해 설계된 신원 모델은 불충분하다"고 명시한다.[12] 문서는 에이전트 신원을 서비스 프린시펄과도 구분한다. 서비스 프린시펄이 장기 안정성과 알려진 소유권을 전제하는 반면, 에이전트는 몇 분만 존재하거나 하루에 수천 번 생성·파괴될 수 있다는 것이다.[12] Okta 역시 "에이전트를 1급 신원으로 취급한다"는 표현으로 같은 포지션을 취한다 _(vendor-stated)_.[13] 이 계층에서 위임은 토큰으로 표현된다. Entra 문서는 에이전트가 사용자에게 부여된 권한을 사용해 사용자를 대신해 행동하는 위임 접근과, 에이전트 신원 자체에 직접 부여된 권한을 쓰는 자율 접근을 구분한다.[12]

MCP는 이 계층의 프로토콜 측면을 담당한다. 2025-06-18 개정 인가 규격은 보호된 MCP 서버를 OAuth 2.1 리소스 서버로 규정하고, "MCP 서버는 인가 서버의 위치를 표시하기 위해 OAuth 2.0 Protected Resource Metadata(RFC 9728)를 구현해야 한다(MUST)"고 요구한다.[14] 클라이언트는 RFC 8707 Resource Indicators를 구현해 토큰의 대상 리소스를 명시해야 하며, 서버는 자신을 대상으로 발급되지 않은 토큰을 거부해야 한다.[14] 여기에 조직 경계를 넘는 위임을 붙이는 것이 Cross-App Access다. oauth.net은 이를 "공식적으로 Identity Assertion Authorization Grant로 알려진 OAuth의 확장으로, 엔터프라이즈 신원 공급자가 두 애플리케이션 간 연결을 관리할 수 있게 하는 것"으로 설명하며, RFC 8693 Token Exchange와 RFC 7523 JWT Profile 위에 구성된다.[15] 2026년 6월 1일 공개된 IETF 개별 초안은 AIMS(Agent Identity Management System)를 "에이전트 워크로드의 신원과 권한을 확립·유지·평가하는 데 필요한 기능 집합을 기술하는 개념 모델"로 정의하고, SPIFFE·WIMSE·OAuth 2.0·OpenID Shared Signals Framework를 조합한다.[16] 새 프로토콜을 발명하는 대신 기존 워크로드 신원 스택을 재배열하는 접근이다.

온체인 계층은 세 번째 앵커를 쓴다. ERC-8004의 신원 레지스트리는 URIStorage를 갖춘 ERC-721로 구현되어 각 에이전트에 {namespace}:{chainId}:{identityRegistry} 형식의 전역 식별자와 agentId를 부여하고, agentURI가 등록 파일을 가리킨다.[17] 등록 파일에는 type·name·description·image와 함께 web, A2A, MCP, OASF, ENS, DID, email 엔드포인트를 나열하는 services 배열이 포함된다.[17] 즉 DID는 이 스펙에서 여러 선택지 중 하나로 등장한다. 학술 문헌은 DID·Verifiable Credentials를 에이전트 신원의 기반으로 제안하며, 한 연구는 "각 에이전트에 자기주권적 디지털 신원을 부여하고, 원장에 고정된 고유한 W3C DID와 제3자가 발급한 W3C VC 집합을 결합"하는 설계를 제시한다.[18] 그러나 같은 연구는 "에이전트의 LLM이 해당 보안 절차를 단독으로 통제하게 되는 순간 한계가 드러난다"고 평가한다.[18] 실제 대규모 배포에서 DID가 기본 신원 형식으로 채택된 증거는 확인되지 않았고, Entra·Okta·MCP·Web Bot Auth 계열 문서는 모두 DID가 아닌 다른 식별자 체계를 전제한다.[12][14][9]

정리하면 위임을 표현하는 단일 표준은 없다. OAuth 토큰 audience 바인딩(MCP)[14], 서명 헤더에 결합된 소비자 인식 객체(Visa TAP)[11], IdP 중개 토큰 교환(ID-JAG)[15], 온체인 권한과 지갑 메타데이터(ERC-8004)[17], 워크로드 신원 조합(AIMS)[16]이 각각 다른 방식으로 같은 문제를 푼다.

탐색 · 레지스트리 · 노출

A2A는 탐색을 도메인 규약으로 해결한다. 스펙은 "표준 경로는 https://{agent-server-domain}/.well-known/agent-card.json이며, RFC 8615의 원칙을 따른다"고 규정한다.[19] Agent Card의 무결성은 JWS로 보장할 수 있다. 서명 전에 Agent Card 내용은 RFC 8785 JSON Canonicalization Scheme으로 정규화되어야 하며(MUST), signatures 필드 자체는 순환 의존을 피하기 위해 서명 대상에서 제외되어야 한다.[20] 다만 검증은 권고 수준이다. 스펙은 클라이언트가 Agent Card를 신뢰하기 전에 최소 하나의 서명을 검증해야 한다(SHOULD)고만 말한다.[20] 공개된 Agent Card 중 실제로 서명을 담고 있는 비율을 보여주는 자료는 확인하지 못했다.

레지스트리 방식에 대해 A2A 스펙은 의도적으로 비워 둔 부분이 있다. "중개 서비스(레지스트리)가 Agent Card 모음을 유지하고, 클라이언트가 다양한 기준으로 에이전트를 찾기 위해 이 레지스트리에 질의한다"고 서술하면서도, "현행 A2A 스펙은 큐레이션된 레지스트리를 위한 표준 API를 규정하지 않는다"고 명시한다.[19] 이 공백을 MCP 레지스트리가 다른 방식으로 채웠다. 2025년 9월 8일 프리뷰로 공개된 MCP 레지스트리는 공개 MCP 서버의 오픈 카탈로그이자 API이며, 연합형 모델을 채택한다. 공식 발표는 "각 MCP 클라이언트에 연결된 의견 있는 'MCP 마켓플레이스'가 상위 MCP 레지스트리에서 수집한 데이터를 자유롭게 보강·확장할 수 있다"고 설명한다.[21] 이름공간 소유권은 세 경로로 검증되는데, GitHub OAuth, GitHub Actions용 OIDC, 그리고 "도메인과 그 서브도메인의 소유권을 DNS 또는 HTTP 챌린지로 증명"하는 방식이다.[22] 다만 이 레지스트리는 여전히 프리뷰로, 데이터 지속성 보장이나 기타 보증을 제공하지 않는다고 스스로 밝히고 있다.[21]

/.well-known 방식과 도메인 기반 이름공간은 공통의 전제를 가진다. 에이전트가 검증 가능한 도메인을 소유하고 있어야 한다는 것이다.[19][22] 도메인을 갖지 않거나 밀리초 단위로 생성·이동하는 에이전트에는 이 전제가 성립하지 않으며, 이 지점에서 대안 이름공간 제안들이 등장한다. NANDA 인덱스 논문은 "전통적인 DNS 중심 탐색은 밀리초 단위로 협상·위임·이동하는 에이전트를 처리할 수 없다"고 주장하며 암호학적으로 검증 가능한 AgentFacts를 제안한다.[23] OWASP GenAI Security Project의 Agent Name Service는 DNS에서 착안한 구조에 PKI 인증서로 검증 가능한 에이전트 신원을 결합하고, A2A·MCP·ACP 등 다양한 통신 표준을 지원하는 모듈형 프로토콜 어댑터 계층을 둔다.[24][25] ERC-8004의 온체인 신원 레지스트리도 같은 문제에 대한 다른 답이다. 식별자가 도메인이 아니라 체인 상의 토큰이므로 도메인 소유권을 요구하지 않는다.[17]

결제를 탐색 신호로 쓰는 접근도 있다. x402 Bazaar는 "의미론적 설명, 결제 메타데이터, 온체인 활동에서 도출된 신뢰 신호를 갖춘 유료 API 엔드포인트의 검색 가능한 인덱스"로 스스로를 규정한다.[26] 등록이 별도로 필요하지 않고, CDP Facilitator가 해당 엔드포인트에 대해 처음 결제를 정산하는 시점에 자동으로 카탈로그에 올린다.[26] 순위에는 구매자 도달 범위, 거래량, 최근성, 메타데이터 품질, 호스팅 평판이 반영되고, Coinbase가 검증한 엔드포인트는 순위 가점과 지속적 상태 점검을 받는다. 30일 이상 비활성 리소스는 자동으로 목록에서 제외된다.[26] 학술 쪽에서도 결제 그래프를 평판으로 쓰는 제안이 나왔다. TraceRank 논문은 "에이전트가 서비스를 점점 더 많이 소비하게 되면 탐색이 중요해진다. 어떤 스왑 인터페이스를 에이전트가 신뢰해야 하는가? 어떤 데이터 공급자가 가장 신뢰할 만한가?"라는 문제를 제기하고, 결제 트랜잭션을 추천으로 간주해 평판을 전파한다.[27]

플랫폼 마켓플레이스는 탐색과 심사를 결합한다. AWS Marketplace는 AI 에이전트 유형으로 등록하려면 "에이전트가 추론 LLM을 사용하고 자율적 능력을 보인다는 것을 확인해야 하며, 이 요건은 AWS Marketplace에서 제공되는 에이전트가 높은 품질 기준을 충족하도록 보장하기 위한 것"이라고 규정한다.[28] Salesforce는 더 직접적이다. AgentExchange에 배포하려면 관리형 패키지, Salesforce Platform API 솔루션, Marketing Cloud Engagement API 솔루션이 보안 검토를 통과해야 한다(must).[29] Google Cloud의 경우 두 문서의 서술이 갈린다. 2026년 4월 23일자 블로그는 "모든 주요 에이전트는 기본 기능, 출력 정확성, 자율 실행, 엔터프라이즈 표준에 대한 엄격한 4단계 평가를 통과한 후에만 'Google Cloud Ready - Gemini Enterprise' 지정을 획득한다"고 서술하지만,[30] Agent Gallery 제품 문서는 마켓플레이스 에이전트를 "관리자 승인이 필요하며 가시성은 관리자 설정에 따르는" 항목으로만 설명하고 Google 측 검증에 대해서는 언급하지 않는다.[31] 마케팅 문서와 제품 문서 사이의 이 간극은 그대로 남겨 둔다.

탐색의 반대편, 즉 노출을 막거나 값을 매기는 통제도 같은 시기에 제품화됐다. Cloudflare는 2025년 7월 1일 "창작자에게 콘텐츠 비용을 지불하지 않는 한 AI 크롤러를 차단하도록 기본값을 변경"한다고 발표해, 옵트아웃에서 허가 기반 모델로 전환했다.[32] 2026년에는 범위가 확대되어, 2026년 9월 15일부터 Cloudflare 기본 설정은 광고를 게재하는 페이지에서 "혼용(mixed-use)" 크롤러를 차단한다.[33] 신원 검증과 접근 통제가 같은 계층에서 결합되는 구조다. 서명으로 자신을 식별한 에이전트에게만 특정 콘텐츠를 노출하는 정책이 가능해지는 것이 Web Bot Auth의 실질적 효용 중 하나다.[9]

평판 · 검증 · 신뢰 신호

ERC-8004는 평판을 온체인 점수로 만들지 않는다. 온체인에 저장되는 것은 피드백 값, valueDecimals, tag1, tag2, isRevoked 상태, 그리고 클라이언트–에이전트 쌍별 feedbackIndex 카운터이며, endpoint·feedbackURI·feedbackHash는 이벤트로 발행되지만 저장되지 않는다.[17] 함수는 giveFeedback(), revokeFeedback(), appendResponse()와 읽기 측 getSummary(), readAllFeedback()으로 구성된다.[17] 즉 스펙은 신호를 공개적이고 균일하게 만드는 데 집중하고, 복잡한 평판 집계와 리뷰어 신뢰도 평가는 오프체인에 남긴다. EIP의 보안 고려 절은 이 설계의 한계를 스스로 인정한다. "시빌 공격이 가능하며, 가짜 에이전트의 평판을 부풀릴 수 있다."[17] 또한 온체인 해시는 등록의 무결성을 보장하지만 광고된 에이전트 능력이 실제로 작동하거나 무해하다는 것을 암호학적으로 검증할 수는 없다고 명시한다.[17]

검증 계층은 여러 방식이 병존하고 어느 하나로 수렴하지 않았다. ERC-8004 자체가 평판 시스템, 스테이크로 담보된 검증, zkML 증명, TEE 어테스테이션을 선택지로 제시하며 신뢰 모델을 위험 규모에 따라 조정하도록 한다.[17] 검증 요청은 validationRequest(validatorAddress, agentId, requestURI, requestHash)로 이루어지고 검증자는 0–100 범위의 응답을 반환하지만, 검증자 인센티브와 슬래싱은 프로토콜별 사안으로 남는다.[17] 그 위에 별도 표준이 쌓이는 사례도 나왔다. Final 상태인 ERC-8126은 "ERC-8004를 통해 등록된 이더리움 상의 AI 에이전트를 검증하기 위한 표준 인터페이스"를 정의하고, 검증 제공자가 Private Data Verification으로 영지식 증명을 생성하도록 한다.[34] 온체인 어테스테이션 인프라도 담체로 거론된다. EAS는 자신을 "누구나 스키마를 등록하고 신원, 평판, RWA, AI 평가 또는 기타 주장에 관한 어테스테이션을 발행할 수 있게 하는 토큰 없는 공공재"로 설명하며 AI 평가와 에이전트 행위의 서명을 용례로 든다 _(vendor-stated)_.[35] ERC-8126은 검증 제공자가 ERC-8004 검증 레지스트리에 어테스테이션을 게시할 수 있도록 허용한다.[34] 다만 에이전트 문맥에서 발행된 어테스테이션의 실제 규모를 독립적으로 측정한 자료는 확보하지 못했다.

학술 문헌은 평판만으로는 부족하다는 데 일관된다. 프로토콜 비교 연구는 신뢰 모델을 여섯 가지로 분류한다. "Brief(자기 또는 제3자가 검증 가능한 주장), Claim(자기 선언한 능력과 신원, 예컨대 AgentCard), Proof(영지식 증명과 신뢰 실행 환경 어테스테이션을 포함한 암호학적 검증), Stake(슬래싱과 보험을 포함한 담보 예치), Reputation(군중 피드백과 그래프 기반 신뢰 신호), Constraint(샌드박싱과 능력 한정)."[7] 결론은 "어떤 단일 메커니즘도 충분하지 않다"는 것이다.[7] 다른 연구는 평판 시스템이 에이전트에 대해 실패하는 이유를 세 가지로 든다. "에이전트가 평가 절차에 대해 전략적으로 최적화할 수 있고, 입증된 역량이 이질적인 과업 문맥으로 신뢰성 있게 전이되지 않으며, 검증의 엄격성이 크게 다르다."[36] 결제 그래프를 쓰는 접근도 같은 문제의식에서 출발한다.[27] Forbes 보도 역시 "평판 시스템은 조작에 취약하기로 유명하다. 시빌 공격, 결탁 고리, 매수된 리뷰"라고 지적하며, 최근 연구가 평판만으로는 취약하고 증명과 스테이크 게이팅을 결합한 하이브리드가 필요하다고 주장한다는 점을 전한다.[37]

가장 구체적인 증거는 실측이다. ERC-8004 핵심 레지스트리는 2026년 1월 29일 이더리움 메인넷에 배포됐고, 그에 앞선 약 3개월의 테스트넷 기간에 10,000건 이상의 에이전트 등록과 20,000건 이상의 피드백 항목이 기록됐다고 보도됐다.[37] 이후 이더리움상의 ERC-8004 에이전트 10,000건을 대상으로 한 측정 연구는 훨씬 냉정한 그림을 제시한다. "서비스 레코드를 노출한 에이전트는 67건뿐이고, 평판 피드백을 받은 에이전트는 628건뿐이며, 메타데이터·서비스·피드백·크로스체인 등록을 모두 결합한 에이전트는 19건뿐이다."[38] 집중도도 높다. 상위 10개 소유자 지갑이 전체 에이전트의 51.40%를 보유하고, 최대 피드백 클라이언트 한 곳이 전체 피드백 레코드의 65.82%를 생성했다.[38] 등록은 값싸고 평판은 비싸다는 구조적 비대칭이 수치로 나타난 것이다. 검색 과정에서 발견된 다른 총계 수치들(첫 달 45,000건 이상, 3월 24,500건, 7월 말 약 98,000건 등)은 모두 암호화폐 콘텐츠 사이트 출처여서 본 보고서의 출처 기준을 충족하지 못했고, 따라서 현재 유통되는 누적 등록 수치는 서로 일치하지 않는 상태로 보아야 한다.

엔터프라이즈 쪽 준비도 신호도 유사한 격차를 보여준다. Cloud Security Alliance의 2026년 3월 연구 노트는 "보안 리더 중 현재 IAM 인프라가 AI 에이전트 신원을 처리할 수 있다고 높은 확신을 보고한 비율은 18%에 불과하다"고 전하며, 활성 에이전트의 실시간 레지스트리를 유지하는 조직이 21%뿐이라고 보고한다.[39] 이 수치들은 보안 리더 자기보고 설문이므로 표본 설계를 확인할 수 없다는 점을 함께 두고 읽어야 한다.

비교 분석

세 계층은 서로 다른 신뢰 앵커에 뿌리를 둔다. 웹 인프라 계층의 앵커는 사업자가 통제하는 키 디렉터리다. 검증자는 /.well-known/http-message-signatures-directory에서 공개키를 가져와 서명을 확인한다.[9] 엔터프라이즈 IAM 계층의 앵커는 테넌트의 인가 서버다. MCP 서버는 RFC 9728로 자신의 인가 서버를 공표하고, 자신을 대상으로 발급된 토큰만 받아들여야 한다.[14] 온체인 계층의 앵커는 컨트랙트 주소와 토큰 소유권이다. 식별자에 체인 ID와 레지스트리 주소가 포함된다.[17] 세 앵커는 서로를 검증할 수단을 갖고 있지 않다. 어떤 조직의 Entra 테넌트가 발급한 토큰은 가맹점의 TAP 검증기에 아무 의미가 없고, ERC-8004 agentId는 Cloudflare 엣지에서 검증되지 않는다. 이는 해석이지만, 신원 표준을 조사한 연구가 현재 인프라에 조직 경계를 넘어 자율 주체를 식별·검증하는 적절한 메커니즘이 없다고 결론지은 것과 같은 방향이다.[6]

동시에 부분적 수렴의 증거도 분명하다. RFC 9421 HTTP Message Signatures는 Web Bot Auth[2][9]와 Visa TAP[11]이 공유하고, well-known URI 규약은 A2A Agent Card[19], Web Bot Auth 키 디렉터리[9], OAuth Protected Resource Metadata[14]가 공유한다. JWS/JCS는 A2A Agent Card 서명[20]과 Visa TAP의 ID 토큰[11]에서 각각 쓰인다. OAuth 계열은 MCP 인가[14], Cross-App Access[15], AIMS[16]의 공통 기반이다. DNS 검증은 MCP 레지스트리 이름공간 소유권 증명에 쓰인다.[22] 새 프로토콜들이 새 암호 원시함수를 발명하기보다 기존 웹 표준을 재조합하고 있다는 뜻이다. 다만 공통 원시함수의 재사용은 상호운용성과 같은 것이 아니다. 같은 RFC 9421을 쓰더라도 어떤 키 디렉터리를 신뢰하는지가 다르면 검증은 통하지 않는다.

네 계층을 모두 규정하는 단일 프로토콜은 없다. ERC-8004는 신원·평판·검증을 다루지만 인증 방식과 전송은 다른 프로토콜에 위임한다. 등록 파일의 services 배열이 A2A·MCP 엔드포인트를 참조하는 구조가 그 증거다.[17] A2A는 탐색과 인증 스킴 선언을 다루지만 평판을 다루지 않고, 레지스트리 API는 명시적으로 규정하지 않는다.[19] MCP는 인가와 서버 탐색을 다루지만 평판 계층이 없다.[14][21] Web Bot Auth와 TAP는 요청 단위 신원만 다룬다.[2][11] Entra와 Okta는 조직 내부 신원·거버넌스를 다루지만 조직 경계를 넘는 탐색 규약은 아니다.[12][13] 레지스트리 접근을 조사한 연구도 같은 구도를 보고한다. "자율 AI 에이전트는 이제 클라우드, 엔터프라이즈, 분산 도메인에 걸쳐 작동하며, 신뢰할 수 있는 탐색, 능력 협상, 신원 보증을 가능하게 하는 레지스트리 인프라에 대한 수요를 만든다"고 문제를 제기하고, MCP 레지스트리의 중앙집중형 모델부터 Microsoft Entra의 엔터프라이즈 디렉터리, AGNTCY의 IPFS 기반 분산 시스템까지 다섯 가지 접근을 비교한다.[40]

계층 사이의 의존 관계도 비대칭이다. 평판은 신원 없이 성립하지 않는다. 관찰된 행동을 축적할 대상이 필요하기 때문이며, 이는 AI 신원을 선언과 관찰 사이의 연속적 관계로 정의한 연구의 함의이기도 하다.[6] 반대 방향은 성립한다. Web Bot Auth와 Entra는 평판 개념 없이도 유용하다. 다만 이 순서를 완전히 우회하는 설계도 있다. TraceRank는 결제 트랜잭션 자체를 추천 신호로 쓰므로 등록된 신원보다 지갑 주소를 식별자로 삼는다.[27] 즉 "신원 먼저"는 논리적 필연이 아니라 대부분의 설계가 채택한 순서다.

실무 채택 관점에서는 표준보다 플랫폼이 먼저 게이트키퍼가 되어 있다는 해석이 자료에 부합한다. 마켓플레이스는 이미 강제력 있는 심사를 운영한다. Salesforce는 보안 검토 통과를 필수로 요구하고[29], AWS는 추론 LLM 사용과 자율성 확인을 등록 조건으로 두며[28], Google Cloud는 4단계 평가 통과를 지정 조건으로 제시한다[30]. 반면 표준 쪽에서는 배포된 평판 데이터가 희박하고[38] 엔터프라이즈 IAM 준비도가 낮으며[39] 표준화 기구는 아직 "어떤 표준이 쓰이고 있는가"를 묻는 단계다[8]. 다만 이 해석에는 반론이 가능하다. 서명 계층은 자동화 트래픽 전반의 앞단에 놓이므로[3][9] 커버리지 기준으로는 마켓플레이스보다 넓은 게이트일 수 있다. 두 주장은 "게이트키퍼"를 심사 강도로 볼 것인가 트래픽 커버리지로 볼 것인가에 따라 갈린다.

한계와 열린 질문

첫째, 채택 규모를 나타내는 수치의 상당 부분이 1차 당사자 발표이거나 자기보고 설문이다. Cloudflare의 서명 기반 에이전트 인증 배포는 Cloudflare 자신의 블로그[1]와 개발자 문서[9]로만 확인되며, IETF 워킹그룹의 존재[10]는 표준화 트랙을 확인해 주지만 실제로 몇 개의 오리진이 Web Bot Auth를 강제하는지는 알려 주지 않는다. Okta의 "1급 신원" 서술도 벤더 자료다.[13] CSA의 설문 백분율[39]은 표본 설계를 확인할 수 없다. 검색 과정에서 접한 "에이전틱 트래픽 전년 대비 7,851% 성장" 같은 수치는 벤더 벤치마크 보고서 출처여서 본문에 채택하지 않았다.

둘째, 온체인 어테스테이션 인프라가 실제로 에이전트 평판 신호의 담체로 쓰이고 있다는 주장은 이번 조사에서 끝까지 1차 당사자 근거를 넘어서지 못했다. EAS 문서가 AI 평가와 에이전트 행위 어테스테이션을 용례로 들고[35] ERC-8126이 검증 레지스트리 게시를 허용하지만[34], 에이전트 문맥에서 발행된 어테스테이션의 규모를 독립적으로 측정한 자료는 찾지 못했다. 본문에서는 이 주장을 벤더 진술로 표시하고 수치를 제시하지 않았다.

셋째, 자동화 트래픽 비중에서 직접 확인된 것은 Cloudflare 자신의 2025년 12월 측정치뿐이다.[3] 2026년 중반의 교차점 보도는 매체 수가 둘이지만 측정 시스템은 하나이고, 두 페이지 모두 스크립트 접근을 차단해 본문 대조가 불가능했다.[4][5] 마찬가지로 A2A Agent Card 서명이 실제로 얼마나 쓰이는지에 대한 자료가 없어, 스펙이 정의한 것과 배포된 것 사이의 간격을 이 항목에서는 측정할 수 없었다.

넷째, 여기서 다룬 문서 다수가 확정 전이다. ERC-8004은 여전히 Draft 상태이고[17] Forbes도 스펙이 아직 움직이고 있다고 전한다[37]. 본문이 인용한 Web Bot Auth 아키텍처 초안은 만료·대체 표시가 붙어 있으며[2] 워킹그룹은 별도로 활동 중이다[10]. AIMS 초안은 2026년 12월 3일 만료 예정이고 IETF의 승인을 받은 것이 아니라고 스스로 명시한다.[16] Cross-App Access도 RFC가 아닌 활동 중 초안이다.[15] MCP 레지스트리는 프리뷰이며 데이터 지속성을 보장하지 않는다.[21] Visa TAP 스펙 페이지에는 버전과 날짜가 없다.[11] 인용한 MCP 인가 규격은 2025-06-18 개정판이며, 이후 개정이 존재할 수 있다.[14] 따라서 본문의 함수 시그니처·헤더 이름·경로는 모두 인용 시점의 상태다.

다섯째, 공개 탐색 자체가 공격 표면을 만든다. A2A 스펙은 Agent Card가 "내부 또는 제한된 에이전트의 URL, 민감한 스킬의 설명" 같은 민감 정보를 포함할 수 있다고 경고하고, 정적 비밀을 카드에 넣지 말고 대역 외 동적 자격증명을 쓰도록 강력히 권고한다.[19] ANS 논문은 에이전트 사칭, 레지스트리 오염, 서비스 거부를 위협 모델에 명시적으로 포함한다.[25] 무엇이 발견 가능해야 하고 무엇이 감춰져야 하는가는 이 분야에서 아직 해결되지 않은 설계 문제다.

여섯째, 범위상 제외한 영역이 있다. 결제 프로토콜(x402, AP2, L402)의 내부 동작은 탐색 표면을 제외하고 다루지 않았다. 지역별 규제(EU AI Act, 국내 법령) 역시 자료를 수집하지 않았으므로 어떤 주장도 하지 않는다. 한국어 검색 결과는 벤더 마케팅 페이지에 그쳐 출처 기준을 충족하지 못했고, 따라서 본 보고서는 영어권 자료에 의존한다. 마지막으로 본 보고서는 코드를 실행하거나 실제 에이전트 카드를 가져와 검증하지 않았다. 모든 기술적 서술은 스펙 텍스트 또는 인용된 측정 연구에 근거한다.
