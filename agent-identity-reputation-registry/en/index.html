AI Agent Identity, Reputation, and Discovery: The Protocol and Registry Landscape

Signed web identity, enterprise agent IAM, on-chain registries, and marketplace review — a survey of the agent trust stack as of mid-2026.

Published 2026-07-30 Tags ai-agents, agent-identity, reputation, agent-registry, web-bot-auth, rfc-9421, a2a, mcp-registry, erc-8004, trusted-agent-protocol, entra-agent-id, agent-marketplace Status ready

Abstract

Between 2025 and mid-2026 a large number of mutually independent standards and services appeared for AI-agent identity, authentication, discovery, and reputation. This report sorts them into four layers. The web-infrastructure layer converged on reusing RFC 9421 HTTP Message Signatures to identify agents cryptographically per request (Web Bot Auth, Visa Trusted Agent Protocol); the enterprise IAM layer converged on registering agents as first-class identity objects distinct from human accounts (Microsoft Entra Agent ID, Okta for AI Agents), with MCP authorization settling on the OAuth 2.1 resource-server model. At the discovery layer, A2A's /.well-known/agent-card.json, the MCP registry's federated sub-registry model, ERC-8004's on-chain identity registry, and payment-derived indexes such as x402 Bazaar coexist. The reputation layer has specifications but the thinnest deployed data: a measurement study of 10,000 ERC-8004 agents found only 67 exposing service records and only 628 having received any feedback. Overall, partial convergence is visible at the level of shared primitives, but the layers anchor trust in different places and therefore do not interoperate directly — and in practice platform marketplace review is functioning as the trust gatekeeper ahead of any standard.

Introduction and Background

Once agents began calling the web on a person's behalf, a question appeared that the existing web identity stack cannot answer. Server-side TLS certificates prove "who is the server I connected to," not "which agent sent this request, and on whose behalf." Cloudflare names the gap directly: "Existing identification methods rely on a combination of IP address range (which may be shared by other services, or change over time) and user-agent header (easily spoofable). These have limitations and deficiencies."[1] The IETF-side draft takes the same starting point, stating its goal as allowing "automated HTTP clients to cryptographically sign outbound requests, allowing HTTP servers to verify their identity with confidence."[2]

What made this urgent is a shift in the composition of traffic itself. The directly verifiable figure comes from Cloudflare Radar's 2025 year in review: as of 2 December 2025, "human traffic generated 47% of HTML requests, and non-AI bots generated 44%."[3] The same document puts AI bot traffic at an average of 4.2% of HTML requests.[3] Reporting in mid-2026 then held that automated traffic had overtaken human traffic, at 57.4% against 42.6%. This report could not read the body of either article directly — both return 403 to scripted access — and both restate the same Cloudflare Radar measurement, so that crossover figure is treated as unconfirmed[4][5] (unverified — single source).

Academic and standards work formalised the problem over the same period. One study defines AI identity as "the continuous relationship between what an AI agent is declared to be and what it is observed to do, bounded by the confidence that those two things correspond at any given moment."[6] That definition explains the ordering between identity and reputation: accumulating observed behaviour requires a stable identifier to attribute it to. A comparative protocol study points the same way, arguing that LLM-specific fragilities — "prompt injection, sycophancy/nudge-susceptibility, hallucination, deception, and misalignment" — "render purely reputational or claim-only approaches brittle."[7] Institutionally, NIST's NCCoE published a concept paper on software and AI agent identity and authorization on 5 February 2026, posing as an open question: "What current or emerging standards are being used to guide AI agent identity and access management?"[8] That the standards body is still at the question stage is itself a measure of the field's maturity.

This report proceeds in four layers: identity and authentication (who is this, and on whose behalf), discovery/registries/exposure (how is it found), reputation and verification (is it trustworthy), and a comparison across them. The cut-off is late July 2026.

Identity and Authentication

The web-infrastructure approach is to sign the request itself. Web Bot Auth builds on RFC 9421 HTTP Message Signatures, having agents sign outbound requests with Ed25519 keys for servers to verify.[2] Per Cloudflare's documentation, bots host a key directory at /.well-known/http-message-signatures-directory on an HTTPS domain, serving a JWKS of Ed25519 public keys.[9] The required headers are Signature-Input, Signature, and Signature-Agent, the last pointing at the key directory.[9] The scheme is explicit about what it does not provide: the draft states that the signing key must not be tied to a specific human individual, and that if an agent wishes not to identify itself this is not the right protocol.[2] This is operator-level attribution, not person-level authentication.

Document status needs care here. The architecture Internet-Draft read for this report is version 05, published 2 March 2026, expiring 3 September 2026, and marked as replaced by a successor.[2] Meanwhile the IETF has an active webbotauth working group with an approved charter that opens: "Automated clients (colloquially, 'bots') are increasingly used on the Web. These clients may want to securely authenticate themselves as belonging to a specific entity..."[10] The individual draft has lapsed; the standardisation track has become institutional.

Visa's Trusted Agent Protocol moves the same primitives into commerce. An agent presents identity through RFC 9421 Signature-Input and Signature headers, and the merchant verifies against public keys Visa hosts at https://mcp.visa.com/.well-known/jwks.[11] Where it goes further is delegation. An Agentic Consumer Recognition Object in the request body carries an ID token with obfuscated consumer identifiers (hashed phone or email) plus device and location context, signed with the same nonce as the message signature so the two form one authenticity chain.[11] The merchant can determine whether an existing customer relationship exists without receiving plaintext personal data. The TAP specification page read here carries no version number or publication date, so "the current TAP spec" does not name a fixed object.[11]

The enterprise IAM layer uses an entirely different anchor. Microsoft Entra Agent ID defines agents as "identity accounts within Microsoft Entra ID that provide unique identification and authentication capabilities for AI agents," stating that "identity models designed for human users and applications prove insufficient."[12] The documentation also separates agent identities from service principals: service principals assume long-term stability and known ownership, whereas an agent "might exist for minutes during a specific task, or might be created and destroyed thousands of times per day."[12] Okta takes the same position, describing its product as "treating your agents as first-class identities" (vendor-stated).[13] Delegation in this layer is expressed as tokens: Entra's documentation distinguishes delegated access, where the agent acts on behalf of a human using rights granted to the user, from autonomous access using rights granted directly to the agent identity.[12]

MCP supplies the protocol side of this layer. The 2025-06-18 authorization revision casts a protected MCP server as an OAuth 2.1 resource server and requires that "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728) to indicate the locations of authorization servers."[14] Clients must implement RFC 8707 Resource Indicators to name the target resource, and servers must reject tokens not issued for them as audience.[14] Cross-organizational delegation is layered on top by Cross-App Access, which oauth.net describes as "formally known as the 'Identity Assertion Authorization Grant', ... an extension of OAuth that enables an enterprise identity provider to manage the connection between two applications," built on RFC 8693 Token Exchange and RFC 7523.[15] An individual IETF draft published 1 June 2026 defines AIMS (Agent Identity Management System) as "a conceptual model describing the set of functions required to establish, maintain, and evaluate the identity and permissions of an agent workload," composing SPIFFE, WIMSE, OAuth 2.0 and the OpenID Shared Signals Framework.[16] It rearranges the existing workload-identity stack rather than inventing a protocol.

The on-chain layer uses a third anchor. ERC-8004's identity registry is implemented as ERC-721 with URIStorage, assigning each agent a global identifier of the form {namespace}:{chainId}:{identityRegistry} plus an agentId, with agentURI resolving to a registration file.[17] That file carries type, name, description and image plus a services array listing web, A2A, MCP, OASF, ENS, DID and email endpoints.[17] DID, in other words, appears here as one option among several. Academic work does propose DIDs and Verifiable Credentials as the base of agent identity, with one study endowing "each agent ... with a self-sovereign digital identity ... combining a unique and ledger-anchored W3C Decentralized Identifier (DID) of an agent with a set of third-party issued W3C Verifiable Credentials (VCs)."[18] The same study finds that limitations appear "once an agent's LLM is in sole charge to control the respective security procedures."[18] No evidence was found of DIDs being adopted as the base identity format in large-scale deployments; the Entra, MCP and Web Bot Auth families all presume other identifier schemes.[12][14][9]

There is, then, no single standard for expressing delegation. OAuth token audience binding (MCP)[14], a consumer-recognition object bound into signature headers (Visa TAP)[11], IdP-mediated token exchange (ID-JAG)[15], on-chain permissions and wallet metadata (ERC-8004)[17], and a composition of workload identities (AIMS)[16] each solve the same problem differently.

Discovery, Registries, and Exposure

A2A solves discovery by domain convention: "The standard path is https://{agent-server-domain}/.well-known/agent-card.json, following the principles of RFC 8615."[19] Card integrity can be secured with JWS. Before signing, the card content MUST be canonicalized using the JSON Canonicalization Scheme (RFC 8785), and the signatures field itself MUST be excluded from the signed content to avoid circular dependencies.[20] Verification, however, is advisory: the spec says only that clients SHOULD verify at least one signature before trusting an Agent Card.[20] No source was found quantifying what share of published Agent Cards actually carries a signature.

On registries, the A2A spec deliberately leaves a hole. It describes an intermediary registry that "maintains a collection of Agent Cards" which clients query, while stating that "the current A2A specification does not prescribe a standard API for curated registries."[19] The MCP registry filled that hole differently. Launched in preview on 8 September 2025 as an open catalog and API for public MCP servers, it adopts a federated model: the announcement explains that "opinionated 'MCP marketplaces' associated with each MCP client are free to augment and enhance data they ingest from the upstream MCP Registry."[21] Namespace ownership is proved by three routes — GitHub OAuth, GitHub Actions OIDC, and "Domain Verification - For proving ownership of a domain and its subdomains via DNS or HTTP challenge."[22] The registry remains a preview that explicitly offers no data-durability guarantees or other warranties.[21]

The /.well-known route and domain-based namespaces share a premise: the agent must own a verifiable domain.[19][22] That premise fails for agents with no domain, or ones spawned and moved in milliseconds — which is where alternative namespaces enter. The NANDA index paper argues that "traditional DNS-centered discovery cannot handle agents that negotiate, delegate, and migrate in milliseconds" and proposes cryptographically verifiable AgentFacts.[23] The OWASP GenAI Security Project's Agent Name Service combines DNS-inspired naming with PKI-certificate-backed agent identity and a "modular Protocol Adapter Layer supporting diverse communication standards (A2A, MCP, ACP etc.)."[24][25] ERC-8004's on-chain identity registry is another answer to the same problem: the identifier is a token on a chain, so no domain ownership is required.[17]

A further approach treats payment as the discovery signal. x402 Bazaar describes itself as "a searchable index of payable API endpoints with semantic descriptions, payment metadata, and trust signals derived from on-chain activity."[26] Services need no separate registration; the CDP Facilitator catalogs a route the first time it settles a payment for that endpoint.[26] Ranking reflects buyer reach, transaction volume, recency, metadata quality and hosting reputation, Coinbase-verified endpoints receive ranking boosts and continuous health-probing, and resources inactive for 30+ days are automatically delisted.[26] Academic work makes the same move: the TraceRank paper poses the problem as "which swap interface should an agent trust? Which data provider is the most reliable?" and propagates reputation by treating payment transactions as endorsements.[27]

Platform marketplaces fuse discovery with review. AWS Marketplace requires that, for the AI agent tool type, sellers "confirm that your agent uses reasoning LLMs and demonstrates autonomous capabilities. These requirements help ensure that agents offered on AWS Marketplace meet a high quality bar."[28] Salesforce is blunter: to distribute on AgentExchange, "managed packages, Salesforce Platform API solutions, or Marketing Cloud Engagement API solutions must pass our security review."[29] Google Cloud's two documents diverge. A blog post dated 23 April 2026 states that "every featured agent earns the 'Google Cloud Ready - Gemini Enterprise' designation only after passing a strict four-step evaluation for basic functionality, output accuracy, autonomous execution, and enterprise standards,"[30] while the Agent Gallery product documentation describes marketplace agents only as "agents requiring administrator approval; visibility depends on admin settings" and says nothing about Google-side validation.[31] That gap between marketing and product documentation is left as found.

The opposite of discovery — blocking exposure or pricing it — was productised over the same period. On 1 July 2025 Cloudflare announced it was "changing the default to block AI crawlers unless they pay creators for their content," moving from an opt-out to a permission-based model.[32] The scope widened in 2026: from 15 September 2026, Cloudflare's default settings block "mixed-use" crawlers from any pages that host ads.[33] Identity verification and access control thus fuse in the same layer — one of Web Bot Auth's practical payoffs is precisely that an origin can serve particular content only to agents that identified themselves by signature.[9]

Reputation, Verification, and Trust Signals

ERC-8004 does not turn reputation into an on-chain score. What is stored on chain is the feedback value, valueDecimals, tag1, tag2, isRevoked status and a per-client-agent feedbackIndex counter, while endpoint, feedbackURI and feedbackHash are emitted as events but not stored.[17] The functions are giveFeedback(), revokeFeedback(), appendResponse() plus read-side getSummary() and readAllFeedback().[17] The spec concentrates on making signals public and uniform, leaving complex aggregation and reviewer-credibility assessment off chain. Its security considerations concede the limits of that design: "Sybil attacks are possible, inflating the reputation of fake agents."[17] The same section states that on-chain hashes guarantee registration integrity but cannot cryptographically verify that advertised agent capabilities are functional or benign.[17]

The verification layer has multiple coexisting mechanisms and no convergence. ERC-8004 itself offers reputation systems, stake-secured validation, zkML proofs and TEE attestations as options, with the trust model tiered to the stakes.[17] Validation is requested via validationRequest(validatorAddress, agentId, requestURI, requestHash) and validators return a 0–100 response, but validator incentives and slashing remain protocol-specific.[17] Separate standards have begun stacking on top: ERC-8126, whose status is Final, "defines a standard interface for verifying AI agents on Ethereum that have been registered via ERC-8004," with verification providers using Private Data Verification to generate zero-knowledge proofs.[34] On-chain attestation infrastructure is also proposed as a carrier: EAS describes itself as "a tokenless public good that lets anyone register a schema and issue attestations about identity, reputation, RWAs, AI evaluations or any other claim," naming AI evals and agent actions among its use cases (vendor-stated).[35] ERC-8126 permits verification providers to post attestations to the ERC-8004 validation registry.[34] No independent measurement of attestation volume specifically in the agent context was obtained.

The academic literature is consistent that reputation alone is insufficient. The comparative protocol study sorts trust models into six: "Brief (self- or third-party verifiable claims), Claim (self-proclaimed capabilities and identity, e.g. AgentCard), Proof (cryptographic verification, including zero-knowledge proofs and trusted execution environment attestations), Stake (bonded collateral with slashing and insurance), Reputation (crowd feedback and graph-based trust signals), and Constraint (sandboxing and capability bounding)."[7] Its conclusion is that "no single mechanism suffices."[7] Another study gives three reasons reputation systems fail for agents: "agents can strategically optimize against evaluation procedures; demonstrated competence does not reliably transfer across heterogeneous task contexts; and verification rigor varies widely."[36] The payment-graph approach starts from the same premise.[27] Forbes coverage likewise notes that "reputation systems are famously gameable: Sybil attacks, collusion rings, bribed reviews," and reports that recent research argues reputation alone is brittle and that safer markets need hybrids of proof and stake gating.[37]

The most concrete evidence is measured. ERC-8004's core registries were deployed to Ethereum mainnet on 29 January 2026; over roughly three preceding months on testnet the ecosystem was reported to have registered 10,000+ agents and logged 20,000+ feedback entries.[37] A measurement study of 10,000 ERC-8004 agents on Ethereum then produced a far colder picture: "Only 67 agents expose service records, only 628 agents receive reputation feedback, and only 19 agents combine metadata, services, feedback, and cross-chain registration."[38] Concentration is high as well: the top 10 owner wallets hold 51.40% of agents, and the largest feedback client contributes 65.82% of all feedback records.[38] The structural asymmetry — registration is cheap, reputation is expensive — shows up as numbers. Other cumulative totals encountered during searching (45,000+ in the first month, ~24,500 in March, roughly 98,000 by late July 2026) all originated from crypto-content sites that did not meet this report's sourcing bar, so circulating registration totals should be read as mutually inconsistent.

Enterprise readiness signals show a comparable gap. A March 2026 Cloud Security Alliance research note reports that "only 18% of security leaders report high confidence that their current IAM infrastructure can handle AI agent identities," and that only 21% maintain real-time registries of active agents.[39] These figures are self-reported survey responses whose sampling frame is not verifiable from the published note.

Comparative Analysis

The three layers root trust in different places. The web-infrastructure anchor is an operator-controlled key directory: verifiers fetch public keys from /.well-known/http-message-signatures-directory and check the signature.[9] The enterprise IAM anchor is the tenant's authorization server: an MCP server advertises its authorization server via RFC 9728 and must accept only tokens issued for itself as audience.[14] The on-chain anchor is a contract address and token ownership, with chain ID and registry address embedded in the identifier.[17] None of the three has a means of verifying the others. A token issued by one organisation's Entra tenant means nothing to a merchant's TAP verifier, and an ERC-8004 agentId is not verified at the Cloudflare edge. This is an interpretation, but it runs in the same direction as the standards survey that concludes current infrastructure lacks adequate mechanisms for identifying and verifying autonomous entities across organisational boundaries.[6]

Partial convergence is equally clear. RFC 9421 HTTP Message Signatures are shared by Web Bot Auth[2][9] and Visa TAP[11]; the well-known URI convention is shared by A2A Agent Cards[19], the Web Bot Auth key directory[9] and OAuth Protected Resource Metadata[14]; JWS/JCS appear in A2A card signing[20] and in TAP's ID token[11]; the OAuth family underlies MCP authorization[14], Cross-App Access[15] and AIMS[16]; and DNS verification is used to prove MCP registry namespace ownership[22]. New protocols are recombining existing web standards rather than inventing new cryptographic primitives. Shared primitives are not the same as interoperability, though: two systems can both use RFC 9421 and still fail to verify each other if they trust different key directories.

No single protocol specifies all four layers. ERC-8004 covers identity, reputation and validation but delegates authentication and transport elsewhere — its registration file's services array points at A2A and MCP endpoints.[17] A2A covers discovery and security-scheme declaration but not reputation, and explicitly declines to specify a registry API.[19] MCP covers authorization and server discovery but has no reputation layer.[14][21] Web Bot Auth and TAP cover per-request identity only.[2][11] Entra and Okta cover in-organisation identity and governance but are not cross-boundary discovery conventions.[12][13] The registry survey reports the same shape, framing the problem as autonomous agents that "now operate across cloud, enterprise, and decentralized domains, creating demand for registry infrastructures that enable trustworthy discovery, capability negotiation, and identity assurance," and comparing five approaches from the MCP registry's centralized model through Microsoft Entra's enterprise directory to AGNTCY's IPFS-based distributed system.[40]

Dependence between layers is asymmetric. Reputation does not stand without identity, because accumulated behaviour needs something to attach to — which is the implication of defining AI identity as a continuous relationship between declaration and observation.[6] The reverse holds: Web Bot Auth and Entra are useful with no notion of reputation at all. One design does route around the ordering, however: TraceRank uses payment transactions themselves as endorsement signals, making the wallet address rather than a registered identity the identifier.[27] "Identity first" is therefore the ordering most designs chose, not a logical necessity.

On adoption, the evidence fits the reading that platforms are gatekeeping ahead of standards. Marketplaces already run enforceable review: Salesforce makes passing security review mandatory[29], AWS conditions listing on confirming reasoning-LLM use and autonomy[28], and Google Cloud states a four-step evaluation as the condition for its designation[30]. On the standards side, deployed reputation data is sparse[38], enterprise IAM readiness is low[39], and the standards body is still asking which standards are in use[8]. There is a counter-argument: the signature layer sits in front of automated traffic generally[3][9], so by coverage it may be the broader gate. The two readings differ on whether "gatekeeper" means strength of review or breadth of traffic.

Limitations and Open Questions

First, much of the adoption-scale evidence is first-party or self-reported. Cloudflare's deployment of signature-based agent authentication is confirmed only by Cloudflare's own blog[1] and developer documentation[9]; the existence of the IETF working group[10] confirms the standardisation track but says nothing about how many origins actually enforce Web Bot Auth. Okta's "first-class identities" framing is vendor material.[13] The CSA survey percentages[39] have no verifiable sampling frame. Figures encountered in search such as "agentic traffic grew 7,851% year over year" trace to a vendor benchmark report and were deliberately not used.

Second, the claim that on-chain attestation infrastructure actually carries agent reputation signals never got past first-party evidence in this investigation. EAS documentation lists AI evaluations and agent actions as use cases[35] and ERC-8126 permits posting to the validation registry[34], but no independent measurement of attestation volume in the agent context was found. The claim is marked as vendor-stated in the body and no figure is given for it.

Third, the only directly verified traffic-share figure is Cloudflare's own December 2025 measurement.[3] The mid-2026 crossover reporting has two outlets but one measurement system, and both pages block scripted access, so their wording could not be checked against the page.[4][5] Likewise, with no data on real-world use of A2A Agent Card signing, the distance between what the spec defines and what is deployed could not be measured for that item.

Fourth, many of the documents here are pre-final. ERC-8004 remains at Draft status[17] and Forbes notes the spec is still moving[37]. The Web Bot Auth architecture draft cited is marked expired and replaced[2] while the working group operates separately[10]. The AIMS draft expires 3 December 2026 and states it is not IETF-endorsed.[16] Cross-App Access is an active draft, not an RFC.[15] The MCP registry is a preview with no data-durability guarantee.[21] The Visa TAP specification page carries no version or date.[11] The MCP authorization revision cited is 2025-06-18 and later revisions may exist.[14] Every function signature, header name and path in this report is therefore as of the time of citation.

Fifth, public discovery is itself an attack surface. The A2A specification warns that Agent Cards may include sensitive information such as "URLs for internal or restricted agents" and "descriptions of sensitive skills," and strongly recommends out-of-band dynamic credentials rather than static secrets embedded in the card.[19] The ANS work puts agent impersonation, registry poisoning and denial of service explicitly in its threat model.[25] What should be discoverable and what should stay hidden remains an unresolved design question in this field.

Sixth, some areas were out of scope. The internals of payment protocols (x402, AP2, L402) are not covered beyond their discovery surfaces. Jurisdiction-specific regulation (the EU AI Act, Korean law) was not researched and no claims are made about it. Korean-language search returned only vendor marketing pages that did not meet the sourcing bar, so this report rests on English-language sources. Finally, nothing here was verified by running code or fetching live agent cards; every technical statement rests on specification text or a cited measurement study.
