# CAIP-122 (Sign in With X): 체인 불가지론적 지갑 인증 표준 분석

## 초록

CAIP-122(Sign in With X, SIWx)는 블록체인 계정이 오프체인 서비스에 인증·인가하는 방법을 체인 불가지론적으로 규정한 CASA(Chain Agnostic Standards Alliance) 표준이다. 본 리포트는 CAIP-122 원문과 그 기반 표준(CAIP-2, CAIP-10, CAIP-74/CACAO), 네임스페이스 프로파일(eip155, solana 등), 그리고 실제 구현(Reown AppKit SIWX, x402 SIWX 확장, Ceramic did-session)을 1차 사료로 재구성했다. 핵심 확인 사항은 다음과 같다. (1) CAIP-122는 EIP-4361(Sign-In with Ethereum)을 "자신의 특정 구현으로 만드는" 명시적 일반화로, 추상 데이터 모델과 체인별 서명 프로파일을 분리한다 — 각 네임스페이스는 서명 알고리즘, type 문자열, 서명 입력 생성 절차를 MUST로 제공해야 한다. (2) 서명된 SIWx 메시지는 CAIP-74의 CACAO(IPLD 기반 캐퍼빌리티 오브젝트)로 직렬화되어 "인증 영수증"을 넘어 "합성 가능하고 재생 가능한 인가 영수증"이 되며, did:pkh와 결합해 Ceramic did-session 같은 프로덕션 세션 시스템을 구동한다. (3) 그러나 일반화에는 대가가 있다: EIP-4361에서 필수(8자 이상)였던 nonce가 CAIP-122에서는 선택 필드로 내려갔고, 보안 섹션도 도메인 매칭 MUST 중심으로 간결해져 세부 방어는 프로파일과 구현자에게 위임됐다. (4) 표준 자체는 2022년 이후 Review 상태에 머물러 있고 네임스페이스 프로파일은 6개 체인에 그치지만, 구현(Reown, x402, Ceramic)은 표준 확정을 기다리지 않고 확산 중이다 — 사실상의 표준화가 문서상의 표준화를 앞지르는 전형적 사례다.

## 서론

지갑 서명 로그인은 이더리움에서 EIP-4361로 표준화됐지만, 웹은 이더리움만으로 이루어져 있지 않다. Solana, Tezos, Stacks 등 각 생태계가 저마다의 사인인 관행을 만들면, 다중 체인을 지원하려는 서비스와 지갑은 체인 수만큼의 인증 코드를 유지해야 한다. CAIP-122는 이 파편화에 대한 응답으로, "블록체인 계정이 스코프·세션 세부·보안 장치로 매개변수화된 체인 불가지론적 메시지를 서명해 오프체인 서비스에 인증·인가하는 방법"을 규정한다[^s01]. 스스로 밝히는 목표는 명확하다: "이 작업은 Sign in With Ethereum 스펙을 일반화·추상화해, EIP-4361을 이 스펙의 특정 구현으로 만들기 위한 것이다"[^s01].

본 리포트는 CAIP-122를 네 겹으로 분석한다: (a) 표준이 서 있는 CASA/CAIP 체계, (b) 추상 데이터 모델과 네임스페이스 프로파일 구조, (c) CACAO·did:pkh로 이어지는 상위 스택과 실제 구현들, (d) 일반화 과정에서 얻은 것과 잃은 것. EIP-4361 자체의 상세 분석은 자매 리포트(`eip-4361-siwe`)에서 다룬다.

## 배경: CAIP 체계와 ChainAgnostic 표준 스택

CAIP를 발행하는 CASA는 "프로토콜·소프트웨어·회사 간 상호운용성과 소통을 뒷받침하는 표준을 만드는 블록체인 개발자들의 자기 조직적 연합"이며, 제안은 공개 워킹그룹에서 "토론·초안·발행"된다[^s07]. CAIP-122가 딛고 선 기반은 세 개의 선행 CAIP다. CAIP-2는 블록체인 자체의 식별자를 `namespace:reference` 형식(예: `eip155:1`)으로 정의한 Final 표준으로, "이더리움 체인 ID로는 비트코인이나 코스모스 체인을 지칭할 수 없다"는 문제를 푼다[^s05]. CAIP-10은 여기에 계정 주소를 결합한 계정 식별자이며, CAIP-122의 account_address 필드는 CAIP-10의 주소 세그먼트로, chain_id 필드는 CAIP-2 식별자로 정의된다[^s01]. 마지막으로 CAIP-104가 네임스페이스별 프로파일 문서 체계를 규정해, 각 체인 계열이 공통 CAIP를 자기 방식으로 구체화할 자리를 만든다[^s01][^s06].

이 구조가 CAIP-122의 설계 언어다: 공통 부분(무엇을 서명하는가)은 추상 데이터 모델로 올리고, 체인 고유 부분(어떻게 서명·검증하는가)은 네임스페이스 프로파일로 내린다.

## CAIP-122 데이터 모델 분석

### 추상 데이터 모델

CAIP-122 메시지의 필수 필드는 domain(RFC 4501 dnsauthority), account_address(CAIP-10 세그먼트), chain_id(CAIP-2), uri(RFC 3986), version, type(네임스페이스가 정의한 서명 타입), signature다[^s01]. statement(개행 금지), nonce, issued-at, expiration-time, not-before, request-id, resources는 선택 필드다[^s01]. 서명 입력의 사람 가독성은 규범적 관심사다 — 스펙은 EIP-4361과 같은 골격의 평문 템플릿(`${domain} wants you to sign in with your **blockchain** account:` …)을 제시하며 "서명이 사용자의 충분한 정보에 근거한 동의를 나타내도록 문자열은 사람이 읽을 수 있어야 한다"고 명시한다[^s01].

주목할 규범 차이가 하나 있다. EIP-4361에서 nonce는 필수이며 최소 8자 영숫자로 문법까지 규정되지만[^s11], CAIP-122에서 nonce는 "서명 리플레이 공격을 막기 위한 무작위 토큰"이라는 설명과 함께 **선택** 필드다[^s01]. 일반화 과정에서 리플레이 방어의 규범 강도가 한 단계 내려간 것이다. 이 함의는 §평가에서 다룬다.

### 네임스페이스 프로파일 요구

CAIP-122는 각 CAIP-104 네임스페이스가 구현 프로파일로 세 가지를 MUST로 제공하도록 요구한다: (1) 서명 알고리즘(복수 가능), (2) 각 알고리즘을 지정하는 type 문자열, (3) 추상 데이터 모델에서 서명 입력을 만드는 절차 — 서명 방법과 검증 방법을 포함해서[^s01]. 실제 프로파일 두 개가 이 구조를 보여준다.

**eip155 프로파일**은 ECDSA 서명에 type `eip191`(개인 서명)과 `eip1271`(컨트랙트 서명)을 지정하고, 서명 입력은 EIP-4361과 동일한 평문 형식을 쓰며, "EIP-191·EIP-1271에 명시된 검증 기법과 EIP-4361에 명시된 추가 단계"를 그대로 채택한다. 프로파일 스스로 "EIP-4361이 CAIP-122의 영감이었고, 이 문서는 EIP-4361이 CAIP-122에 어떻게 부합하는지 보여준다"고 밝힌다[^s02].

**solana 프로파일**은 Ed25519 서명에 type `solana:ed25519`를 제안하고, 추상 모델을 "모호하지 않은 형식의 문자열 표현으로 변환한 뒤 바이트 배열로 변환해 서명"하도록 규정한다. 검증에는 base58 인코딩된 Ed25519 공개키인 Solana 주소를 쓴다[^s03]. 한편 지갑 생태계에는 Phantom이 주도한 Sign-In-With-Solana(SIWS)가 병렬로 존재하는데, SIWS 저장소는 "EIP-4361을 모델로 하되 그 능력을 확장"했다고 밝히면서도 CAIP-122는 언급하지 않는다[^s12]. 즉 solana 네임스페이스에서는 CASA 프로파일과 지갑 주도 표준이 나란히 있고, 실무 구현(예: x402 SIWX)은 SIWS 형식을 CAIP-122 우산 아래의 구현으로 취급한다[^s10].

2026년 7월 기준 caip122 프로파일이 존재하는 네임스페이스는 arweave, eip155, solana, stacks, tezos, xrpl 여섯 개다[^s06]. 체인 불가지론이라는 이름에 비해 커버리지는 아직 좁고, 프로파일 문서들 자체도 Draft 상태다[^s02][^s06].

### CACAO: 서명에서 캐퍼빌리티로

CAIP-122의 상위 스택은 CAIP-74가 정의하는 CACAO(Chain-Agnostic CApability Object)다. CACAO는 "CAIP-122로 생성된 체인 불가지론적 오브젝트 캐퍼빌리티(OCAP)를 IPLD 오브젝트로 표현"하며, 헤더(페이로드 형식: `caip122` 또는 `eip4361`)·페이로드(도메인, did:pkh 형식의 발급자, 대상, 타임스탬프, 논스, 리소스)·서명(type 포함)의 3부 구조로 CBOR 직렬화된다[^s04]. 스펙의 표현을 빌리면 이는 "인증의 이벤트 영수증일 뿐 아니라, 합성 가능하고 재생 가능한 인가 영수증"이다 — 서명 한 번이 일회성 로그인 증거가 아니라, 체이닝·위임 가능한 이식성 있는 권한 오브젝트가 된다[^s04]. CACAO 헤더가 `eip4361`을 그대로 수용한다는 점은 두 표준의 실질적 호환성을 보여주는 세부다[^s04].

이 스택의 프로덕션 소비자가 Ceramic의 did-session이다. 블록체인 계정을 `did:pkh:<chain_id>:<address>` 형식의 DID로 취급하고, 사용자가 지갑으로 한 번 사인인(SIWE/SIWx)하면 CACAO 인가를 통해 브라우저의 임시 세션 키가 사용자의 DID를 대행한다 — "did:pkh를 Sign-In with Ethereum과 CACAO 인가와 함께 지원"하며 기본 세션은 1주일, 쓰기 접근 리소스는 인가 시점에 명시적으로 스코프된다[^s08]. 지갑 서명 1회 → 스코프·만료가 있는 위임 세션이라는 이 패턴은, CAIP-122가 단순 로그인 표준이 아니라 인가 체계의 입구로 설계됐음을 보여준다.

## 구현과 생태계

**Reown AppKit SIWX.** WalletConnect의 후신 Reown은 AppKit의 사인인 기능을 SIWE 전용 설정에서 CAIP-122 기반 SIWX로 이행시켰다 — "Sign In With X 기능은 CAIP-122 표준에 따라 설계됐다"고 명시하며, AppKit 1.5.0 이후 기존 siweConfig 사용자를 SIWX로 마이그레이션하고 Ethereum·Solana·Bitcoin을 지원한다[^s09]. 지갑 연결 SDK 최대 계열의 기본 사인인 계층이 CAIP-122 준거를 선언했다는 점은 채택 신호 중 가장 무겁다.

**x402 SIWX 확장.** HTTP 402 결제 프로토콜 x402의 공식 확장 SIWX는 "x402 보호 리소스에 대한 CAIP-122 지갑 인증"을 구현해, 결제 이력이 있는 지갑의 재접근과 인증 전용 라우트를 제공한다. EVM은 EIP-4361 형식, Solana는 SIWS 형식으로 서명하고 서버가 체인별 알고리즘으로 검증한다[^s10]. 결제 프로토콜이 세션 계층을 CAIP-122로 채웠다는 점에서, 표준의 적용 범위가 "로그인 화면"을 넘어 기계 간 프로토콜로 확장되고 있음을 보여준다.

**Ceramic did-session.** 위 §CACAO에서 본 대로, 분산 데이터 네트워크 Ceramic은 CAIP-122 계열 사인인과 CACAO를 세션 인프라의 기본으로 수년째 사용해 왔다[^s08].

세 구현의 공통점은 모두 표준이 Review 상태인 채로 채택했다는 것이다. CAIP-122는 2022년 6월 생성·같은 해 7월 갱신 이후 상태가 바뀌지 않았다[^s01].

## 평가와 논의

**추상화의 득.** CAIP-122의 분리 설계 — 공통 데이터 모델 + 체인별 프로파일 — 는 새 체인 추가를 프로파일 문서 하나의 문제로 축소한다. 실제로 eip155 프로파일은 기존 EIP-4361을 사실상 재선언하는 것으로 충분했고[^s02], solana 프로파일은 서명 알고리즘과 바이트 변환 규칙만 새로 정의했다[^s03]. 구현 쪽에서도 Reown이 세 체인을 한 인터페이스로 묶고[^s09], x402가 체인 네임스페이스 프리픽스로 검증기를 라우팅하는[^s10] 등, 추상화가 실질 코드 재사용으로 이어진 증거가 있다.

**추상화의 실.** 대가는 규범 강도의 하향 평준화다. nonce가 선택 필드가 된 것이 대표적이다[^s01][^s11]. CAIP-122의 보안 섹션은 "지갑 구현자는 서명 요청 처리 시 domain 항을 대조해 피싱 공격을 방지해야 한다(MUST)"를 중심으로 간결하며[^s01], EIP-4361이 명시하던 지갑의 필드 표시 의무, 세션의 주소 바인딩, 채널 보안(HTTPS), ERC-1271 상태 변화 시 세션 무효화 같은 세부 규범이 추상 계층에는 없다[^s11][^s01]. 결과적으로 보안 속성의 실제 수준은 프로파일 작성자와 구현자의 선택에 좌우된다. 실무 구현들이 스펙보다 엄격하게 동작하는 경향은 있으나(예: x402 SIWX는 매 챌린지마다 fresh nonce를 생성한다[^s10]), 이는 표준이 보장하는 바가 아니라 구현의 선의다.

**구현자들의 공개 비판.** 표준 저장소 자체에 구현자 피드백이 이슈로 남아 있다. WalletConnect 설계자 Pedro Gomes는 2024년 "SIWx로 여러 체인에 인증하려면 여러 메시지를 서명해야 한다"며, 멀티체인이 기본값이 된 Web3에서 "사용자가 체인 A·B·C에 인증하려면 세 번이 아니라 한 번 서명해야 한다"고 단일 체인 설계의 한계를 지적했다 — 와일드카드·ReCap 등 대안이 논의됐으나 미해결 상태다[^s13]. 같은 시기 또 다른 구현자 피드백은 resources 필드의 필수/선택이 CAIP-122와 EIP-4361 간에 불일치한다고 보고했는데[^s14], 2026년 7월 현재 main 브랜치 필드 표에서 resources는 선택으로 표기되어 있어 보고 이후 본문이 수정된 것으로 보인다. Review 상태 표준의 규범이 버전 표기 없이 움직인다는 것 자체가, 아래에서 논할 "확정 없는 확산"의 실무 비용을 보여준다[^s14][^s01].

**문서상 표준화 vs 사실상 표준화.** CAIP-122는 4년째 Review 상태이고 프로파일은 6개 네임스페이스에 그치지만[^s01][^s06], 그 위의 구현 생태계는 이미 움직였다. 이 간극은 두 가지로 읽을 수 있다. 표준의 방향이 옳아서 확정을 기다릴 필요가 없었다는 긍정적 독해와, 규범이 확정되지 않은 채 구현이 굳어지면 향후 스펙 개정(예: nonce 필수화)이 사실상 불가능해진다는 부정적 독해다. 어느 쪽이든, CAIP-122를 채택하는 서비스는 "표준 준수"가 EIP-4361 수준의 보안 규범을 자동으로 포함하지 않음을 인지하고, eip155 프로파일처럼 EIP-4361의 추가 단계를 명시적으로 채택하는 것이 안전하다[^s02].

**정체성 스택에서의 위치.** CACAO·did:pkh와의 결합은 CAIP-122를 W3C DID 세계와 잇는 다리로 만든다[^s04][^s08]. 지갑 서명이 DID 세션의 루트 권한이 되는 이 구성은, 자매 리포트에서 본 SIWE-OIDC 브리지와 함께, 지갑 인증이 기존 신원 인프라(OIDC, DID)에 흡수되는 두 갈래 경로를 이룬다. 체인 불가지론적 추상화를 맡는 것이 CAIP-122의 역할이라면, 그 보안 하한을 지키는 것은 여전히 각 프로파일과 구현의 몫이다.

## 한계 (Limitations)

- **채택 정량 지표 부재**: Reown AppKit·Ceramic did-session의 사용 규모(앱 수, 세션 수)를 정량 확인하지 못했다. 채택 서술은 공식 문서의 준거 선언에 근거한 정성 판단이다.
- **CAIP-10 원문 미직접 대조**: CAIP-10은 CAIP-122 원문의 필드 정의와 CAIP-2 원문을 통해 간접 확인했다.
- **프로파일 전수 검토 아님**: 6개 프로파일 중 eip155·solana만 정독했다. arweave·stacks·tezos·xrpl 프로파일의 규범 품질은 미확인이다.
- **학술 문헌 부재**: CAIP-122를 단독 분석한 피어리뷰 논문을 확인하지 못했다(신규·니치 표준). 분석은 1차 사료 정독에 기반한다.
- **구현의 nonce 처리 전수 미확인**: "구현이 스펙보다 엄격한 경향"은 x402 SIWX 사례 등 제한된 표본에 근거하며, Reown·Ceramic의 nonce 정책은 코드 수준으로 확인하지 않았다.
- **스냅샷 시효**: 표준 상태·프로파일 목록은 2026-07-06 기준이다.
