CAIP-122 (Sign in With X) — The Chain-Agnostic Wallet Authentication Standard

A primary-source analysis of the abstract data model, namespace profiles, the CACAO stack, and the implementation ecosystem

Abstract

CAIP-122 (Sign in With X, SIWx) is a CASA (Chain Agnostic Standards Alliance) standard that specifies, in a chain-agnostic way, how blockchain accounts authenticate and authorize with off-chain services. This report reconstructs CAIP-122 from primary sources: the specification itself, its foundational standards (CAIP-2, CAIP-10, CAIP-74/CACAO), the namespace profiles (eip155, solana, and peers), and the production implementations (Reown AppKit SIWX, the x402 SIWX extension, Ceramic did-session). Key findings: (1) CAIP-122 is an explicit generalization of EIP-4361 (Sign-In with Ethereum) — "making EIP-4361 a specific implementation of this specification" — separating an abstract data model from per-chain signing profiles, each of which MUST provide a signing algorithm, a type string, and a signing-input procedure. (2) A signed SIWx message can be serialized as a CAIP-74 CACAO (an IPLD-based capability object), turning an "event receipt of an authentication" into "a composable and replay-able authorization receipt," and combining with did:pkh to power production session systems such as Ceramic's did-session. (3) Generalization has a price: the nonce, mandatory (8+ alphanumeric) in EIP-4361, becomes an optional field in CAIP-122, and the security section thins to a domain-matching MUST, delegating detailed defenses to profiles and implementers. (4) The standard has sat in Review status since 2022 and namespace profiles cover only six chains, yet implementations (Reown, x402, Ceramic) are spreading without waiting for finalization — a textbook case of de facto standardization outrunning de jure.

CAIP-122 (Sign in With X): The Chain-Agnostic Wallet Authentication Standard

Introduction

Wallet-signature login was standardized on Ethereum as EIP-4361, but the web is not made of Ethereum alone. If Solana, Tezos, Stacks, and every other ecosystem grows its own sign-in convention, multi-chain services and wallets must maintain one authentication stack per chain. CAIP-122 answers that fragmentation, describing "how blockchain accounts should authenticate and authorize with off-chain services by signing a chain-agnostic message parameterized by scope, session details, and security mechanisms"[1]. Its stated goal is unambiguous: "This work is meant to generalize and abstract the Sign in With Ethereum specification, thereby making EIP-4361 a specific implementation of this specification"[1].

This report analyzes CAIP-122 in four layers: (a) the CASA/CAIP system the standard stands on; (b) the abstract data model and the namespace-profile structure; (c) the upper stack leading to CACAO and did:pkh, and the real implementations; (d) what the generalization gained and what it gave up. EIP-4361 itself is analyzed in detail in the companion report (eip-4361-siwe).

Background: the CAIP System and the ChainAgnostic Standards Stack

CASA, which publishes CAIPs, is "a self-organized alliance of blockchain developers creating standards that support interoperability and facilitate communication between protocols, software, and companies," with proposals "debated, drafted, and published" in open working groups[2]. CAIP-122 rests on three prior CAIPs. CAIP-2 — a Final standard — defines blockchain identifiers in namespace:reference form (e.g., eip155:1), solving the problem that "with an Ethereum chain ID you cannot reference e.g. a Bitcoin or Cosmos chain"[3]. CAIP-10 extends this into account identifiers; CAIP-122's account_address field is defined as the CAIP-10 address segment and its chain_id field as a CAIP-2 identifier[1]. Finally, CAIP-104 establishes the per-namespace profile system that gives each chain family a place to concretize common CAIPs in its own terms[1][4].

That structure is CAIP-122's design language: the common part (what is signed) rises into an abstract data model; the chain-specific part (how it is signed and verified) descends into namespace profiles.

Analysis of the CAIP-122 Data Model

The abstract data model

The mandatory fields of a CAIP-122 message are domain (RFC 4501 dnsauthority), account_address (a CAIP-10 segment), chain_id (CAIP-2), uri (RFC 3986), version, type (a namespace-defined signature type), and signature[1]. Optional fields are statement (no newlines), nonce, issued-at, expiration-time, not-before, request-id, and resources[1]. Human readability of the signing input is a normative concern: the spec provides a plaintext template with the same skeleton as EIP-4361 (${domain} wants you to sign in with your blockchain account: …) and states that "the string should be human-readable, so that the signing represents the fully-informed consent of a user"[1].

One normative difference stands out. In EIP-4361 the nonce is required, with its grammar pinned to at least eight alphanumeric characters[5]; in CAIP-122 the nonce — described as a "randomized token to prevent signature replay attacks" — is optional[1]. The normative strength of replay defense dropped one level in the generalization. The implications are taken up in the Assessment section.

Namespace profile requirements

CAIP-122 requires each CAIP-104 namespace to provide three things (MUST) in an implementation profile: (1) a signing algorithm or a finite set of them; (2) a type string designating each algorithm; (3) a procedure for creating a signing input from the abstract data model — covering both how to sign and how to verify[1]. Two live profiles illustrate the structure.

The eip155 profile designates ECDSA with types eip191 (personal signatures) and eip1271 (contract signatures), uses the EIP-4361 plaintext format as the signing input, and adopts "signature verification techniques from EIP-191 and EIP-1271 as specified as well as any additional steps specified in EIP-4361." The profile itself states that "EIP-4361 ... was the inspiration for CAIP-122" and that the document "highlights how EIP-4361 conforms with CAIP-122"[6].

The solana profile proposes Ed25519 with type solana:ed25519, requiring that "the abstract data model must be converted into a string representation in an unambiguous format, and then the string converted to a byte array to be signed over," with verification against the Solana address — a base58-encoded Ed25519 public key[7]. In the wallet ecosystem, Phantom-led Sign-In-With-Solana (SIWS) exists in parallel: the SIWS repository describes itself as "modeled after EIP-4361 ... but extends beyond its capabilities" while never referencing CAIP-122[8]. In the solana namespace, then, the CASA profile and the wallet-led standard sit side by side, and practical implementations (e.g., x402's SIWX) treat the SIWS format as the implementation under the CAIP-122 umbrella[9].

As of July 2026, caip122 profiles exist for exactly six namespaces: arweave, eip155, solana, stacks, tezos, and xrpl[4]. For a standard named chain-agnostic, coverage remains narrow, and the profile documents themselves are Draft-status[6][4].

CACAO: from signature to capability

CAIP-122's upper stack is CACAO (Chain-Agnostic CApability Object), defined by CAIP-74. A CACAO "represent[s] a chain-agnostic Object Capability (OCAP), created using CAIP-122, as an IPLD object," with a three-part structure — header (payload format: caip122 or eip4361), payload (domain, issuer as did:pkh, audience, timestamps, nonce, resources), and signature (with type) — deterministically serialized with CBOR[10]. In the spec's words, this creates "not just an event receipt of an authentication, but also a composable and replay-able authorization receipt": one signature becomes not a one-shot login proof but a portable, chainable authority object supporting delegation[10]. That the CACAO header accepts eip4361 directly is a telling detail of the two standards' practical compatibility[10].

The production consumer of this stack is Ceramic's did-session. It treats a blockchain account as a DID of the form did:pkh:<chain_id>:<address>; after one wallet sign-in (SIWE/SIWx), a temporary browser session key acts for the user's DID under CACAO authorization — the library "supports did:pkh for blockchain accounts with Sign-In with Ethereum and CACAO for authorization," with sessions defaulting to one week and write-access resources explicitly scoped at authorization time[11]. One wallet signature → a scoped, expiring delegated session: the pattern shows CAIP-122 was designed as the entrance to an authorization system, not merely a login standard.

Implementations and Ecosystem

Reown AppKit SIWX. Reown, WalletConnect's successor, migrated AppKit's sign-in layer from a SIWE-specific configuration to CAIP-122-based SIWX — stating that "the Sign In With X feature is designed in accordance with the CAIP-122 standard," migrating siweConfig users from AppKit 1.5.0 onward, and supporting Ethereum, Solana, and Bitcoin[12]. The default sign-in layer of the largest wallet-connection SDK family declaring CAIP-122 conformance is the weightiest adoption signal available.

The x402 SIWX extension. SIWX, an official extension of the HTTP 402 payment protocol x402, "implements CAIP-122 for chain-agnostic wallet authentication" for x402-protected resources — repeat access for wallets with payment history and auth-only routes. EVM signs the EIP-4361 format and Solana the SIWS format, with servers verifying via chain-appropriate algorithms[9]. A payment protocol filling its session layer with CAIP-122 shows the standard's reach extending beyond login screens into machine-to-machine protocols.

Ceramic did-session. As covered above, the decentralized data network Ceramic has used CAIP-122-family sign-in and CACAO as its default session infrastructure for years[11].

What the three implementations share: all adopted the standard while it remains in Review. CAIP-122's status has not changed since its creation in June 2022 and update in July 2022[1].

Assessment and Discussion

What the abstraction gained. CAIP-122's separation — common data model plus per-chain profiles — reduces adding a new chain to the problem of writing one profile document. In practice the eip155 profile amounted to re-declaring the existing EIP-4361[6], and the solana profile only had to define the signing algorithm and byte-conversion rule[7]. On the implementation side there is evidence the abstraction yields real code reuse: Reown binds three chains under one interface[12], and x402 routes verifiers by chain-namespace prefix[9].

What it gave up. The cost is a downward leveling of normative strength. The nonce becoming optional is the emblematic case[1][5]. CAIP-122's security section is terse, centered on "Wallet implementers MUST prevent phishing attacks by matching on the domain term when processing a signing request"[1]; the detailed norms EIP-4361 spelled out — the wallet's mandatory field display, binding sessions to the address, channel security (HTTPS), session invalidation on ERC-1271 state changes — are absent at the abstract layer[5][1]. The actual security level therefore depends on choices by profile authors and implementers. Implementations tend to behave more strictly than the spec (x402's SIWX, for instance, generates a fresh nonce for every challenge[9]), but that is implementers' good practice, not a guarantee of the standard.

Implementers' public criticism. Implementer feedback sits as open issues in the standard's own repository. In 2024 Pedro Gomes, the architect of WalletConnect, pointed at the single-chain design: "if you would like to authenticate yourself with SIWx for multiple chains then you need to sign multiple messages," arguing that in a multi-chain-by-default Web3, "if a user wants to authenticate for chain A, B and C then it should sign a single message rather than 3 messages" — wildcard and ReCap alternatives were discussed but remain unresolved[13]. Contemporaneous implementer feedback reported a required/optional mismatch on the resources field between CAIP-122 and EIP-4361[14]; as of July 2026 the main-branch field table marks resources optional, suggesting the text was amended after the report. That a Review-status standard's norms move without version markers is itself a practical cost of the "diffusion without finalization" discussed next[14][1].

De jure vs. de facto standardization. CAIP-122 has been in Review for four years and its profiles cover six namespaces[1][4], yet the implementation ecosystem above it has already moved. The gap reads two ways: positively — the direction was right enough that no one needed to wait for finalization; negatively — once implementations harden around an unfinalized norm, future spec revisions (say, making the nonce mandatory) become practically impossible. Either way, services adopting CAIP-122 should recognize that "standard conformance" does not automatically include EIP-4361-level security norms, and the safe course is to adopt EIP-4361's additional steps explicitly, as the eip155 profile does[6].

Position in the identity stack. The combination with CACAO and did:pkh makes CAIP-122 a bridge to the W3C DID world[10][11]. Wallet signatures becoming the root authority of DID sessions — together with the SIWE-OIDC bridge covered in the companion report — forms the two paths by which wallet authentication is being absorbed into existing identity infrastructure (OIDC and DID). If CAIP-122's role is the chain-agnostic abstraction, holding the security floor remains the job of each profile and implementation.

Limitations

  • No quantitative adoption metrics: we could not quantify usage of Reown AppKit or Ceramic did-session (app counts, session counts). Adoption statements rest on official conformance declarations.
  • CAIP-10 not directly examined: CAIP-10 was confirmed indirectly through CAIP-122's field definitions and the CAIP-2 text.
  • Not an exhaustive profile review: of the six profiles, only eip155 and solana were read closely; the normative quality of the arweave, stacks, tezos, and xrpl profiles is unverified.
  • No academic literature: we found no peer-reviewed paper analyzing CAIP-122 (a new, niche standard). The analysis rests on close reading of primary sources.
  • Implementations' nonce handling not exhaustively verified: the "implementations stricter than spec" tendency rests on a limited sample (x402 SIWX); Reown's and Ceramic's nonce policies were not verified at code level.
  • Snapshot staleness: standard status and the profile list are as of 2026-07-06.
