- **iOS 18.0–18.3 '데이터 손실' 표현** (c15): Apple 포럼은 "hybrid에서 다른 PRF 값 반환"을 확인. '영구 데이터 손실'로 이어지는지는 앱 설계에 따라 다름 — 해석적 서술로 처리.

## 개정 2 (2026-08-07) 추가

### 검증된 것과 검증되지 않은 것의 경계
`working/verify/`의 42개 검사는 **암호 파이프라인의 수학**을 검증한다. 검증 대상은
도메인 분리 해싱, HMAC-SHA-256, HKDF, AES-GCM 봉투 암호화, 회전, KCV, 타입 정규화이며,
기준값은 W3C 공식 테스트 벡터(s30)와 RFC 5869 부록 A(s35)다.

검증되지 **않은** 것을 명확히 해 둔다.
- 실제 `navigator.credentials.create()` / `.get()` 호출 경로.
- CTAP 전송 계층: 공유 비밀 협상(ECDH), `saltEnc` 암호화, `saltAuth` 인증,
  PIN/UV 프로토콜 1 대 2의 차이. 스펙의 이 부분 테스트 벡터(s30 §16.17.1.2)는
  대조하지 않았다 — 클라이언트 구현자용이며 RP 개발자의 관심 범위를 넘는다.
- 플랫폼별 UV 처리와 `CredRandomWithUV`/`WithoutUV` 실제 분기.
- 동기화 패브릭이 PRF 기반 비밀을 실제로 어떻게 보관·전파하는지.

즉 본 개정의 실행 검증은 "스펙을 따르는 인증기라면 이 값이 나온다"를 보이며,
"특정 플랫폼이 스펙을 따른다"는 별개 문제로 §지원 현황의 벤더·커뮤니티 보고에
의존한다. iOS 18.0–18.3 CDA 버그(s15)는 후자가 깨질 수 있음을 보여주는 사례이고,
그것이 KCV 권고의 근거다.

### 여전히 유동적인 것
- **CTAP 버전 표기**: `hmac-secret-mc`의 규범 근거를 2.2 PS로 기재했으나
  벤더 표기는 2.3까지 섞여 있다(s29, s31, s34). 2.2 Review Draft에는 없었다.
- **create 시점 평가의 실제 가용성**: 규범은 확정됐지만 플랫폼·인증기 조합별
  실현 여부는 여전히 벤더·커뮤니티 보고에 의존한다(s01, s13).
- **지원 매트릭스**: 안정판 Safari 전파, Firefox 149 Android 출하가 미확인
  상태로 남아 있다(s14, s33).
- **가이드 권고의 지위**: HKDF 목적 구속, 봉투 암호화, KCV, 원자적 회전은
  1차 사료의 규범이 아니라 벤더 가이드(s04)·구현 사례(s10)·본 리포트의 추론을
  실행 검증으로 뒷받침한 **권고**다. 스펙이 요구하는 사항과 구별해 읽어야 한다.
