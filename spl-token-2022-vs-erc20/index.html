초록

Solana와 Ethereum은 "토큰 표준"이라는 같은 목표를 서로 다른 아키텍처로 달성한다. Ethereum의 ERC-20에서는 토큰 하나하나가 독립적으로 배포된 스마트 컨트랙트이며, 각 컨트랙트가 자신의 잔고 장부를 직접 보관한다[1]. 반면 Solana에서는 단 하나의 공유 온체인 프로그램(SPL Token Program)이 모든 토큰의 로직을 담당하고, 개별 토큰의 상태(총발행량·잔고)는 별도의 Mint 계정과 Token 계정에 저장된다[2][3]. 2022년 도입된 SPL Token-2022는 원본 프로그램의 상위집합(superset)으로서 전송 수수료, 기밀 전송, 전송 훅(transfer hook), 이자 지급, 전송 불가 토큰, 온체인 메타데이터 등 "Token Extensions"를 프로토콜 수준에서 제공한다[4][5]. 본 보고서는 세 표준의 데이터 모델·기능·보안 표면을 대조하고, 공유 프로그램 방식과 컨트랙트별 배포 방식이 각각 어떤 트레이드오프를 갖는지 분석한다. 핵심 대조는 다음과 같다. Solana는 기능을 프로그램 업그레이드로 확장하고, Ethereum은 기능을 새 컨트랙트 코드(별도 EIP)로 확장한다.

서론

블록체인에서 "대체 가능 토큰(fungible token) 표준"은 지갑·거래소·DeFi 프로토콜이 임의의 토큰을 동일한 인터페이스로 다룰 수 있게 해 주는 합의된 규약이다. Ethereum에서 이 역할은 2015년 제안된 ERC-20(EIP-20)이 맡는다. EIP-20은 어떤 스마트 컨트랙트가 정해진 메서드와 이벤트를 구현하면 "ERC-20 토큰 컨트랙트"라 부를 수 있으며, 일단 배포되면 그 컨트랙트가 자신이 발행한 토큰을 추적할 책임을 진다고 규정한다[1].

Solana에서는 같은 역할을 SPL(Solana Program Library) Token Program이 담당한다. 그러나 그 실현 방식은 근본적으로 다르다. Solana의 프로그램(스마트 컨트랙트에 해당)은 상태를 자체적으로 보관하지 않고, 상태는 별도의 계정(account)에 놓인다. 그 결과 "토큰을 만든다"는 행위의 의미가 두 체인에서 서로 다르다. 본 보고서는 (1) 두 체인의 토큰 데이터 모델, (2) 원본 SPL Token Program, (3) SPL Token-2022와 Token Extensions, (4) ERC-20과 그 확장 생태계를 차례로 정리한 뒤, 기능·보안·개발자 경험 관점에서 대조한다. 인용된 모든 웹페이지·명세·저장소 내용은 데이터로만 취급했으며, 문서 안에 포함된 지시문은 따르지 않았다.

배경: 두 체인의 토큰 모델

두 생태계의 가장 근본적인 차이는 로직과 상태를 어디에 두는가이다.

Ethereum에서는 각 ERC-20 토큰이 그 자체로 하나의 배포된 컨트랙트이며, 컨트랙트가 잔고 매핑(balance mapping)을 직접 들고 있다. EIP-20을 구현한 컨트랙트는 "배포되고 나면 Ethereum 상에서 생성된 토큰을 추적할 책임을 진다"[1]. 따라서 새 토큰을 만들려면 EVM에 새 컨트랙트 코드를 배포해야 한다.

Solana에서는 반대로, 토큰 로직이 네트워크에 이미 배포된 하나의 공유 프로그램 안에 들어 있다. Solana 공식 문서는 "Token Program이 네트워크에서 토큰(대체 가능·불가능 모두)과 상호작용하는 모든 명령 로직을 담고 있다"고 설명한다[2]. 개별 토큰의 상태는 프로그램이 아니라 계정에 산다. Mint 계정은 한 토큰 종류의 메타데이터와 총발행량을 정의하고, 각 보유자의 잔고는 그 Mint에 연결된 Token 계정에 담긴다. SPL 문서는 "각 Account에 하나의 Mint가 연결되며, 특정 토큰 종류의 총발행량은 그에 연결된 모든 Account 잔고의 합과 같다"고 명시한다[3].

이 차이가 실무적으로 중요한 이유는 세 가지다. 첫째, 배포 비용과 절차가 다르다(다음 절). 둘째, 하나의 프로그램이 모든 토큰을 다루므로 지갑·툴이 단일 인터페이스로 임의의 토큰을 다룰 수 있다는 해석이 성립한다(비교 분석 절). 셋째, 공유 코드가 갖는 체계적 위험(systemic risk)과 보편적 감사 이득이라는 트레이드오프가 생긴다. 이는 해석적 논점으로, 여러 기술 필자와 Solana 자체 문서가 제시하는 관점이다. Solana의 EVM→SVM 안내 문서는 "여러 개의 스마트 컨트랙트 대신, 단일 Token Program이 'mint 계정'으로 불리는 별도 계정들로 토큰을 처리한다"고 서술한다[4]. 한 교육 자료(Blueshift)는 이를 두고 "SPL Token은 광범위하게 감사를 받았고, 그 감사가 이 프로그램을 쓰는 모든 토큰을 보호한다 … 잘 검증된 하나의 프로그램이 수조 달러의 가치를 보호한다"고 표현한다[5]. 뒤집어 말하면 그 공유 프로그램의 버그는 모든 토큰에 영향을 줄 수 있는 반면, ERC-20의 버그는 개별 컨트랙트 구현에 국한된다는 뜻이다 _(해석 — 설계 트레이드오프)_[6].

SPL 토큰 프로그램

원본 SPL Token Program은 Solana 메인넷에서 주소 TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA에 배포되어 있다[7][8]. 흔히 앞 글자를 따 "Tokenkeg"로 부른다.

이 프로그램은 대체 가능·불가능 토큰의 기본 연산을 모두 제공한다. 발행(mint), 전송(transfer), 소각(burn)에 더해, Mint에 설정된 freeze_authority가 FreezeAccount 명령으로 특정 계정을 "사용 불가" 상태로 만들 수 있고 ThawAccount로 다시 해제할 수 있다[9]. 또한 approve를 통한 위임(delegation)과, Mint 권한이나 계정 소유자 자리에 쓸 수 있는 M-of-N 멀티시그도 지원한다[10].

토큰을 새로 만드는 절차는 Ethereum과 뚜렷이 대비된다. Solana에서는 새 프로그램 바이트코드를 배포할 필요가 없다. 대신 System Program의 CreateAccount 명령으로 rent-exempt 계정을 만들고 그 소유권을 기존 Token Program에 넘긴 뒤 Mint로 초기화한다. 공식 문서는 "System Program의 CreateAccount 명령이 새 rent-exempt 계정을 만들고 그 새 계정의 프로그램 소유자로 Token Program을 지정한다"고 설명한다[11]. 즉 토큰 생성은 코드 배포가 아니라 계정 초기화다.

보유자별 잔고는 대개 연관 토큰 계정(Associated Token Account, ATA)에 담긴다. ATA는 지갑 주소·토큰 프로그램 주소·Mint 주소로부터 결정론적으로 도출되는 프로그램 파생 계정이다[12][13]. Token 계정은 온체인 계정이므로 rent를 위한 SOL 예치가 필요하다[12]. 이는 Ethereum에서 잔고가 컨트랙트 내부 매핑의 한 항목일 뿐 별도 계정 생성 비용이 없는 것과 대비된다.

원본 프로그램의 인터페이스는 오랫동안 안정적으로 유지되어 Solana 생태계 전반의 사실상 표준이 되었으며, 뒤에 나온 Token-2022는 바로 이 인터페이스와의 호환성을 설계 목표로 삼았다(다음 절).

SPL 토큰 2022와 확장 기능

SPL Token-2022(브랜드명 "Token Extensions")는 원본 Token Program과 별개의 온체인 프로그램으로, 다른 주소 TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb에 배포되어 있다[14][15]. SPL 문서는 Token-2022를 "Token Program이 제공하는 기능의 상위집합(superset)"이라 정의하며, 나아가 "Token-2022는 Token과 정확히 같은 명령 레이아웃을 바이트 단위로(byte for byte) 지원한다"고 명시한다[16]. 즉 원본 기능 집합에 대해서는 명령 단위로 하위 호환된다.

Token-2022가 추가하는 것은 Mint 또는 Token 계정에 붙이는 "확장(extension)"들이다. 공식 문서가 열거하는 확장에는 전송 수수료(TransferFeeConfig), 기밀 전송(ConfidentialTransferMint), 전송 훅(TransferHook), 이자 지급(InterestBearingConfig), 전송 불가(NonTransferable, 소울바운드), 기본 계정 상태(DefaultAccountState), 영구 위임자(PermanentDelegate), CPI 가드(CpiGuard), 메타데이터 포인터(MetadataPointer) 등이 있다[17].

몇 가지 확장은 특히 ERC-20 세계와의 대조에서 중요하다.

  • 전송 수수료. "Token Extension 프로그램의 TransferFeeConfig mint 확장은 해당 mint의 모든 전송에 수수료를 적용하며, 원천징수된 수수료는 수신 토큰 계정에 기록된다"[18]. 즉 수수료가 프로토콜(프로그램) 수준의 1급 기능이다.
  • 전송 훅. 전송 훅은 mint 발행자가 "모든 토큰 전송마다 커스텀 명령 로직을 실행"하도록 강제할 수 있게 한다. 공식 가이드는 그 용례로 "NFT 로열티 강제", "토큰을 받을 수 있는 지갑의 블랙/화이트리스트"를 들며, 실행은 "Token Extensions 프로그램이 Transfer Hook 프로그램에 CPI(Cross Program Invocation)를 걸어" 이뤄진다고 설명한다[19].
  • 기밀 전송. 기밀 전송에서는 "전송 금액과 토큰 잔고만 비공개이며, 토큰 계정 주소는 공개로 남는다"[20]. 즉 숨겨지는 것은 금액과 잔고이지 송·수신자 신원이 아니다. 기저 암호 기법은 Solana의 ZK ElGamal 증명 계열이며, 공식 문서가 "동형암호(homomorphic encryption)"라는 표현을 문자 그대로 쓰지는 않으므로 기법 명칭을 과장하지 않도록 주의한다.

호환·마이그레이션 측면에서 중요한 점은, 원본 SPL 토큰이 Token-2022로 자동 전환되지 않는다는 것이다. 두 프로그램은 나란히(side by side) 쓰이며, 한 토큰이 어느 프로그램에 속하는지는 mint 생성 시점에 고정된다. Solana의 개발자 가이드는 "토큰 확장은 새로운 토큰 표준이지만, 누구든 한 표준에서 다른 표준으로 마이그레이션해야 한다는 요구사항은 아니다"라고 못박는다[21][14].

ERC-20와 이더리움 확장 모델

ERC-20(EIP-20)은 대체 가능 토큰의 최소 인터페이스를 정의한다. 핵심은 totalSupply, balanceOf, transfer, transferFrom, approve, allowance의 여섯 함수와 두 이벤트다. 명세는 토큰이 이동할 때(0값 전송 포함) Transfer 이벤트가 반드시 발생해야 하고, approve 호출이 성공하면 Approval 이벤트가 반드시 발생해야 한다고 규정한다[22].

위임 지출은 approve/transferFrom 허용량(allowance) 패턴으로 이뤄진다. 이 패턴에는 잘 알려진 위험이 따른다. EIP-20 명세 자체가 허용량을 갱신할 때 발생하는 경쟁 조건(race condition)을 경고하며, 클라이언트가 "같은 spender에 대해 허용량을 다른 값으로 바꾸기 전에 먼저 0으로 설정"하는 UI를 만들 것을 권고한다[23]. OpenZeppelin 문서도 같은 위험을 "이 방식으로 허용량을 바꾸면 트랜잭션 순서에 따라 누군가 옛 허용량과 새 허용량을 모두 쓸 수 있는 위험이 있다"고 경고하며, 완화책으로 "먼저 spender의 허용량을 0으로 줄인 뒤 원하는 값을 설정"할 것을 든다[24]. 무제한 허용량(unlimited approval)을 노린 피싱 위험을 줄이기 위한 대안으로는 EIP-2612의 permit이 있는데, 이는 온체인 트랜잭션 없이 서명만으로 허용량을 부여하는 함수 permit(owner, spender, value, deadline, v, r, s)를 정의한다[25].

Ethereum에서 "고급 토큰 동작"은 프로토콜 업그레이드가 아니라 추가 표준(별도 EIP)을 상속·배포하는 방식으로 붙는다. 대표적으로:

  • EIP-2612(permit) — 서명 기반 가스리스 승인[25].
  • ERC-1363(Payable Token) — "transfer/transferFrom 후 수신자 코드를, approve 후 spender 코드를 실행"하는 콜백 지원[26].
  • ERC-777 — "ERC-20과 하위 호환을 유지하면서 토큰 컨트랙트와 상호작용하는 새로운 방식"으로, operator와 send/receive 훅을 정의[27].
  • ERC-4626(Tokenized Vaults) — "단일 기반 EIP-20 토큰의 지분을 표현하는 토큰화 금고의 표준 API … EIP-20 토큰에 대한 확장"[28].

핵심은 이 모든 확장이 컨트랙트 코드 수준에서 일어난다는 점이다. 새 기능을 원하면 해당 EIP를 구현한 코드를 상속하거나 새 컨트랙트를 배포한다. 이는 Solana가 하나의 업그레이드된 프로그램(Token-2022)에 확장을 몰아넣은 것과 대조된다.

비교 분석

전송 수수료. 네이티브 프로토콜 수준 전송 수수료는 Token-2022의 전송 수수료 확장으로 제공된다[18]. ERC-20 표준에는 그런 개념이 없다. Ethereum의 "fee-on-transfer" 토큰은 수수료를 커스텀 컨트랙트 코드로 구현하는데, 이는 "받은 금액 = 보낸 금액"을 가정하는 통합을 깨뜨리는 것으로 잘 알려져 있다. Uniswap 문서는 아예 "fee-on-transfer 토큰은 우리 라우터 컨트랙트와 동작하지 않으며, 앞으로도 이를 지원하는 라우터를 만들지 않을 것"이라고 명시한다[29]. 한 보안 해설도 AMM들이 "보낸 토큰 양 = 받은 양"을 가정하기 때문에 fee-on-transfer 토큰에서 이 가정이 깨져 초과 슬리피지와 트랜잭션 실패가 생긴다고 설명한다[30]. 다만 Token-2022의 프로토콜 수준 수수료 역시 훅·확장을 인식하지 못하는 통합에는 유사한 통합 부담을 남길 수 있다는 점에서, 수수료 문제 자체가 사라지는 것은 아니라 표준의 일부로 명시화되었다는 차이로 보는 것이 정확하다.

동결·블랙리스트. 두 Solana 토큰 프로그램은 freeze_authority를 통한 계정 동결을 기본 제공한다[9]. ERC-20 표준에는 동결·블랙리스트 메커니즘이 없다. USDC·USDT 같은 실제 토큰의 동결 기능은 표준이 아니라 커스텀 컨트랙트 로직으로 구현된다. Spark의 조사 자료는 "USDT와 USDC 모두 블랙리스트 기능을 자신들의 ERC-20 토큰 컨트랙트에 직접 구현하며, 발행자가 관리하는 특권 주소가 임의의 지갑을 온체인 매핑에 추가할 수 있다"고 정리한다[31]. Circle FiatToken 설계 문서도 "블랙리스트에 오른 주소는 transfer나 transferFrom을 호출할 수 없고 토큰을 받을 수도 없다"고 기술한다[32]. 요컨대 Solana에서는 동결이 프로그램 표준 기능인 반면, Ethereum에서는 발행자가 표준 밖에서 덧붙인 선택적 커스텀 기능이다.

툴링·조합성. Solana에서는 지갑·툴이 하나의 프로그램 인터페이스를 통해 임의의 SPL/Token-2022 토큰과 상호작용할 수 있다. Blueshift는 SPL Token을 "템플릿이 아니라 … 주소 Tokenkeg…에서 실제로 돌아가는 프로그램"이라 표현하며, 이 단일성을 강조한다[8]. Ethereum에서는 각 토큰이 별도 배포된 컨트랙트이지만 같은 ABI를 따르므로 툴이 공통 인터페이스로 다룰 수 있다 — 통일성의 원천이 "하나의 프로그램"이 아니라 "공유된 ABI 규약"이라는 점이 다르다 _(해석)_[4]. 두 방식 모두 상호운용을 달성하지만, Solana는 실행 코드 자체를 공유하고 Ethereum은 인터페이스 규약을 공유한다.

보안 표면. 앞서 본 체계적 위험/보편적 감사 트레이드오프가 여기서 구체화된다. Solana 모델에서는 단일 프로그램이 광범위하게 감사되어 그 이득이 모든 토큰에 파급되지만[5], 그 프로그램의 결함은 원리상 모든 토큰에 파급될 수 있다. Ethereum 모델에서는 결함이 개별 컨트랙트에 국한되는 대신, 매 배포가 새로운(그리고 종종 감사되지 않은) 코드를 도입한다. 또한 Token-2022의 강력한 확장(영구 위임자, 전송 훅 등)은 새로운 신뢰 가정과 공격 표면을 만든다는 점에서, "표준에 내장된 기능"이 반드시 "더 안전"을 의미하지는 않는다.

이 대목은 Token-2022가 자동으로 유리하다는 인상에 대한 반례가 필요하다. 확장은 통합하는 쪽에 실질적 부담을 지운다. 보안 감사사 Neodyme는 확장을 두고 "이런 종류의 확장에서 자금을 잃는 것은 명백한 귀결이며, 특히 사용자 토큰을 보관하는 금고로 단일 토큰 계정만 쓰는 프로토콜에서 그렇다"고 경고한다[33]. 즉 프로토콜은 통합 전에 대상 mint가 어떤 확장을 달고 있는지(전송 수수료·영구 위임자·전송 훅 등) 반드시 검사해야 하며, 그러지 않으면 "받은 금액 = 보낸 금액" 가정이나 잔고 불변 가정이 조용히 깨질 수 있다. 이는 앞서 본 ERC-20의 fee-on-transfer 통합 문제[29]와 구조적으로 같은 위험이 Solana에서도 확장 형태로 재현됨을 뜻한다 — 즉 기능을 프로토콜 수준으로 옮긴다고 해서 통합 위험이 사라지는 것이 아니라, 위험의 위치가 바뀔 뿐이다.

논의

두 설계는 상반된 곳에 복잡성을 둔다. Solana는 복잡성을 공유 프로그램에 집중시킨다. 그 대가로 토큰 생성이 값싼 계정 초기화가 되고 툴링이 단순해지지만, 확장 기능을 추가하려면 새 프로그램(Token-2022)과 프로그램 간 마이그레이션 부재라는 현실을 감수해야 한다[21]. Ethereum은 복잡성을 각 컨트랙트에 분산시킨다. 그 대가로 무한한 커스터마이즈 자유를 얻지만, 확장이 파편화되고(EIP-2612/1363/777/4626 …) 매 컨트랙트가 잠재적 버그 원천이 된다.

Token-2022의 실제 채택은 실험 단계를 넘어섰다. 가장 잘 문서화된 사례는 PayPal의 PYUSD로, Solana Foundation은 "PYUSD on Solana는 token extensions를 활용한 가장 이른 스테이블코인 중 하나"라고 밝혔고[34], PayPal 개발자 블로그도 "Solana 상의 PYUSD는 Solana의 token extensions로 구축되었다"고 확인한다[35]. 다만 전체 발행량·발행자 중 Token-2022가 차지하는 비중은 본 보고서에서 정량화하지 않았으므로, PYUSD는 "광범위한 시장 점유"의 증거가 아니라 구체적 프로덕션 사례로 읽어야 한다.

전체적으로 보면, "어느 쪽이 우월한가"보다는 "어디에 복잡성과 신뢰를 두기로 선택했는가"가 두 모델을 가르는 축이다. Solana Token-2022는 과거 ERC-20 생태계가 여러 EIP로 나눠 해결하던 기능(수수료, 훅, 메타데이터, 권한 통제)을 프로토콜 수준으로 끌어올린 시도로 볼 수 있다.

한계

  • 정량적 채택 데이터 부재. Token-2022 대 원본 SPL Token의 발행 비중, ERC-20 대비 사용량 등 시장 점유 수치는 다루지 않았다. PYUSD 등은 사례 증거일 뿐이다.
  • 암호 기법의 깊이. 기밀 전송의 ZK ElGamal 증명 구조를 프로토콜 수준에서 상세히 검증하지는 않았고, 공개 문서의 서술("금액·잔고 비공개, 주소 공개")에 근거했다[20].
  • 부재 주장(absence claims)의 성격. "ERC-20 표준에는 수수료/동결이 없다"는 명제는 EIP-20 정본 텍스트에 근거한 것이며, 모든 확장 EIP를 소진적으로 검사해 증명한 것은 아니다.
  • 해석적 논점. 체계적 위험 대 보편적 감사, 툴링 통일성의 원천은 측정된 결과가 아니라 설계 트레이드오프에 대한 분석적 관점이다.
  • 일부 2차 출처. USDT의 destroyBlackFunds 같은 세부는 조사 자료(Spark)에 의존했으며 컨트랙트 원문까지 대조하지는 않았다.
  • 빠른 변화. Token Extensions 세트와 EIP 생태계는 계속 확장 중이므로, 특정 확장 목록은 시점 의존적이다.
