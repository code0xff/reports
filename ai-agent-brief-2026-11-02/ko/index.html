초록

x402가 퍼실리테이터의 라이프사이클 훅 중 예외를 던지는 훅을 제대로 격리하지 못하던 문제를 고친 지 이틀 뒤, 같은 코드 영역에서 또 다른 결함 두 건이 발견됐다. 하나는 Python SIWX 확장의 재사용 방지 검사가 사실상 한 번도 실행된 적이 없게 만드는, 오타 수준의 버그다[1]. 다른 하나는 훅이 중단(abort)될 때 남기는 진단 메시지를 Go 퍼실리테이터의 새 코드 경로에서만 빠뜨리는 버그다[2]. 둘 다 아직 수정되지 않았다. 같은 기간 중 훅과는 무관한 크로스 클라이언트 격차 하나는 해결됐다: Go 클라이언트의 ERC-20 승인(allowance) 검사가 불필요한 승인에 서명하거나 실패할 수밖에 없는 읽기를 시도할 수 있었는데, TypeScript와 Python 클라이언트는 이미 이 문제를 피해 가고 있었다[3].

서론

이번 호는 2026년 10월 30일부터 11월 2일까지를 다룬다. 결제 레일 전반에 대한 배경은 사이트의 에이전트 커머스 프로토콜 비교 리포트에 있다. 이번 호의 발견들이 뒤따르는 훅 격리 수정, 즉 2026년 10월 30일 머지된 x402 PR #3151[1]은 11월 1일 호에서 다뤘다.

무엇이 움직였나

x402 Go 클라이언트, 다른 두 SDK는 이미 맞게 처리하던 승인 검사를 뒤늦게 따라잡다

2026년 10월 30일 머지된 PR #3916은 Go SDK의 exact와 upto 결제 스킴이 전송 전 ERC-20 승인이 필요한지 판단하는 방식을 고친다. 두 스킴 모두 서명자가 ClientEvmSignerWithReadContract를 직접 지원한다고 가정했을 뿐, SDK 자체의 배치 정산 경로나 EIP-2612 스킴이 이미 쓰던 방식으로 이를 해석하지 않았다. 그 결과 두 가지 문제가 생겼다. RPC 클라이언트 없이 생성된 서명자는 실패할 수밖에 없는 승인 조회를 시도했고, 설정된 RPCURL이나 RPCByChainID 폴백은 전혀 참조되지 않아 기존 승인량이 이미 충분한데도 클라이언트가 불필요한 승인에 서명할 수 있었다[2]. 수정은 두 스킴 모두를 배치 정산이 쓰는 동일한 resolveReadSigner 헬퍼로 연결한다. 이 건은 버그 리포트에서 나온 게 아니다. 전혀 다른 PR(#3551)에 대한 리뷰 피드백에서 나왔는데, 어느 한 리뷰어가 세 코드 경로를 나란히 비교해 봤을 때나 드러나는 성격의 격차다.

Python SIWX 확장의 재사용 방지 검사, 애초에 작동한 적이 없다

2026년 10월 31일 등록되어 아직 열려 있는 이슈 #4079는 유독 선명한 실패 양상을 추적한다. Sign-In-With-X 확장의 create_siwx_request_hook은 스토리지 백엔드가 has_used_nonce와 또 하나의 기능을 모두 구현해야만 통과시켜야 하는데, 이 두 번째 기능을 has_record_nonce라는, 코드베이스 어디에도 존재하지 않는 이름으로 찾는다. 실제로 프로토콜 규약과 TypeScript SDK가 확인하는 기능명은 record_nonce다. 문서화된 두 기능을 정확히 구현한 스토리지는 훅 생성 단계에서 ValueError로 거부당한다. record_nonce만 구현한 스토리지는 이 (고장난) 검사를 통과하지만, record_nonce 자체가 같은 플래그에 종속되어 있어 결국 한 번도 호출되지 않는다. 재사용된 SIWX 서명은 "이 논스가 이미 쓰였는가"라는 검사를 영원히 통과한다. 애초에 그 논스가 쓰였다는 기록 자체가 남지 않기 때문이다[3]. 버그 리포트는 정확한 파일과 줄 번호(hooks.py:L105)를 정상 작동하는 TypeScript 쌍과 대조해 제시하고, 재현에 쓴 PyPI 버전(2.26.0)과 main의 커밋(e208bd39)까지 명시한다.

Go 퍼실리테이터의 신버전 오류 경로, 훅의 진단 메시지를 빠뜨리다

같은 날 등록된 이슈 #4081은 더 좁지만 관련된 결함을 찾아냈다. V2 퍼실리테이터 훅이 {Abort: true, Reason, Message}로 검증이나 정산을 중단시키면, Reason은 리소스 서버까지 도달하지만 훅 작성자가 남긴 자유 텍스트 진단인 Message는 Verify와 Settle V2 경로 양쪽에서 빈 문자열로 처리되어 사라진다. 같은 함수의 V1 분기는 메시지를 유지하고, 서버 쪽 V2 훅 처리도 메시지를 유지한다. 퍼실리테이터 쪽 V2 빌더만 이를 빠뜨린다. 보고서에 따르면 수정은 두 호출 지점에 한 줄만 추가하면 되는 수준이지만, 아직 아무도 머지하지 않았다[4].

왜 중요한가

x402는 2026년 10월 30일, 두 호 전에 이 지면에서 다룬 예외 훅 격리 버그를 제대로 고쳤다. 그런데 그로부터 하루 반 만에 같은 영역에서 다른 문제 두 건이 연이어 발견됐다. 하나는 Go 퍼실리테이터의 오류 생성 코드에서, 다른 하나는 무관한 확장의 논스 저장소 검사에서 나왔다. 둘 다 머지 전 코드 리뷰로 쉽게 잡히는 종류의 결함이 아니다. 어떤 함수가 받아야 하는 값과 실제로 확인하는 값을 언어별로 줄 단위까지 대조해봐야 드러난다. Go 클라이언트는 이번 기간에 자체 패리티 수정을 두 건 더 해야 했다. 위의 승인 검사 건과, TypeScript·Python은 이미 제거한 퍼실리테이터 URL의 끝 슬래시를 떼어내는 한 줄짜리 수정이다[5]. 원인은 셋 다 다르지만 패턴은 하나다. x402는 세 언어로 동시에 배포되는데, 그 셋을 행동 면에서 똑같이 맞추는 일이 개별 버그를 고치는 것보다 더 어려운 일로 드러나고 있다.

지켜볼 신호

  • #4079나 #4081이 다음 호까지 머지된 수정을 받는지, 아니면 이달 초 mppx의 두 PR처럼 3~4주를 그냥 묵혀 있는지.
  • 메인테이너의 반응. 두 리포트 모두 지금은 제3자 기여자 본인의 코드 판독에만 의존하고 있다.
  • SIWX의 논스 검사를 깬 것과 같은 종류의 기능명 불일치가 x402의 다른 확장(Bazaar, 배치 정산 트레저리 로직)에도 있는지에 대한 점검 여부.

한계

카드 네트워크와 PSP의 에이전트 커머스 제품(Mastercard Agent Pay, Visa Intelligent Commerce 및 Trusted Agent Protocol, Stripe의 Agentic Commerce Protocol, PayPal)은 이번 기간에도 날짜가 명시된 공식 발표를 전혀 내놓지 않았다. 이 지면이 여섯 호 연속으로 이 부분에서 빈손이다. AP2는 이번 기간 저장소 활동이 전혀 없었고, UCP의 유일한 머지는 한 줄짜리 문서 수정이었다. 이 지면이 원래 머릿기사로 다뤘을 DoorDash의 3분기 실적 발표 중 서드파티 에이전트 주문량 공개는 이미 10월 31일 호에서 다뤘다. 이번 호의 출처 다섯 건 모두 단일 저장소의 GitHub 풀 리퀘스트와 이슈이며, 핵심 발견 세 건 중 두 건은 메인테이너가 확인하지 않은, 아직 고쳐지지 않은 버그 리포트에 그친다. 즉 이번 호는 해결된 것이 아니라 발견된 것을 전한다.
