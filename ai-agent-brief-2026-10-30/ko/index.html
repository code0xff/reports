초록

이번 기간에는 세 개의 서로 다른 저장소에서 같은 패턴이 반복됐다. 한쪽의 결함을 메우자 바로 옆에서 틈이 벌어지거나 드러났다. mppx는 지난 2026-10-29일 브리프가 지적한 MPP 폴백 버그를 고쳤지만, 솔라나 재단 pay-kit 클라이언트의 동일한 버그는 수정 PR이 올라온 지 3주가 지나도록 병합되지 않은 채다[1][2]. x402 재단은 파이썬 SDK에 있던 JSON 파싱 방어 로직을 TypeScript로 옮겨 교차-SDK 격차 하나를 좁혔다[3][4]. 그리고 pay-kit의 파이썬·TypeScript SDK는 버전-1 트랜잭션에서 완전한 적합성에 도달했는데, 이 성과가 곧바로 Go·PHP·Ruby 검증기와의 간극을 넓혀 놓았다. 새로 적합성을 갖춘 SDK가 작성한 결과물을 기존 검증기가 읽지 못하게 된 것이다[5].

서론

이번 호는 2026-10-27일부터 2026-10-30일까지를 다룬다. 결제 레일 전반에 대한 배경은 사이트의 에이전트 커머스 프로토콜 비교에서 볼 수 있고, 역량 드리프트 흐름은 mppx/pay-kit 폴백 버그와 @coinbase/cdp-sdk에 아직 닿지 않은 zod CVE를 처음 보도한 2026-10-29일 호에서 이어진다.

이번 기간의 움직임

mppx는 폴백 버그를 고쳤고, pay-kit의 같은 버그는 3주째 그대로다

2026-10-29일 공개된 mppx@0.17.0에는 PR #1133이 들어갔다. 402 응답의 WWW-Authenticate 헤더가 Payment 스킴을 전혀 명시하지 않을 때 클라이언트가 No Payment schemes found.를 던지며 중단하던 문제를 고친 것이다. 이제는 이런 응답에서 챌린지를 아예 반환하지 않아, fetch가 x402든 서버가 실제로 쓰는 다른 프로토콜이든 넘어갈 수 있다. MPP가 문서로 약속한 폴백 체인이 2026-10-29일 호에서는 작동하지 않았는데, 이번에 그 약속대로 동작하게 됐다[1][2].

솔라나 재단의 pay-kit에도 SessionFetch에 똑같은 결함이 있다. 이를 고치는 PR #359는 2026-10-06일에 올라왔지만, 이번 조사 시점까지 24일째 병합되지 않았다[3]. 서로 독립적으로 구현한 두 팀이 똑같은 버그에 부딪혔는데, 수정 시점은 3주나 벌어진 셈이다. 오늘 mppx를 고르는 개발자는 문서대로 폴백을 받지만, pay-kit을 고르는 개발자는 아니다.

x402, 파이썬→TypeScript 드리프트를 하나 더 메우다

2026-10-29일 병합된 PR #4051은 파이썬 SDK의 HTTP 레이어에 있던 검증 로직을 TypeScript 코어 패키지로 옮겼다. decodePaymentSignatureHeader, decodePaymentRequiredHeader, decodePaymentResponseHeader는 원래 JSON.parse 결과를 그대로 결제 타입으로 캐스팅했기 때문에, 응답 바디가 null이나 배열, 문자열, 숫자, 불리언이어도 유효한 결제 데이터처럼 통과시켰다. 이제는 객체가 아니면 예외를 던진다[4]. 파이썬 PR #3917을 그대로 옮긴 것이고, 이슈 #4050에 추적돼 있다. 2026-10-28일과 10-29일 호가 다룬 zod CVE와 같은 패턴이다. 한 언어에 먼저 들어간 방어 로직이 몇 주 뒤에야 다른 언어로 건너간다. 이 변경이 실제로 npm 배포판에 반영됐는지는 아직 확인되지 않았다. 그날 올라온 TypeScript 버전 올림 PR은 PR #4051보다 여섯 시간 먼저 병합됐으므로, 이 수정은 아직 릴리스 태그가 확정되지 않은 채 main 브랜치에만 있다[5].

pay-kit SDK는 완전한 적합성에 도달했지만, 그만큼 못 읽는 검증기와의 간극이 벌어졌다

2026-10-28일 병합된 PR #404로 pay-kit의 파이썬·TypeScript SDK는 오프라인 적합성 벡터 813개를 전부 통과해 Rust 레퍼런스 키트와 같아졌고, 두 SDK 모두 버전-1 트랜잭션을 지원하게 됐다. 여기까지는 수정이다. 부작용도 있다. 같은 프로젝트의 Go·PHP·Ruby 검증기는 아직 버전-1 트랜잭션을 읽지 못해서, 이 PR 하나로 known_failing으로 분류된 교차-SDK 케이스 24개가 새로 생겼다. 새로 적합성을 갖춘 파이썬이나 TypeScript 클라이언트가 만든 트랜잭션을 다른 언어의 구형 검증기가 읽지 못하는 경우들이다[6]. 한 축(스펙 적합성)에서 맞춰 놓으니 다른 축(언어 간 상호운용성)에서 새 틈이, 같은 PR 안에서 생겨났다.

왜 중요한가

이번에 올라온 PR 세 건 중 어느 것도 퇴보는 아니다. 모두 실제 버그를 실제로 고친 정상적인 수정이다. 그런데 매번 "고쳤다"는 상태가 프로토콜 전체의 속성이 아니라 특정 SDK, 특정 클라이언트, 특정 언어 하나의 속성으로 끝났다. mppx는 맞고 pay-kit은 아직 틀린, 똑같은 버그를 두고. x402의 TypeScript SDK는 이번 검증 하나에 대해서만 파이썬만큼 엄격해졌는데, 배포 여부는 아직 확인 전이다. pay-kit은 다섯 언어 중 두 개가 나머지 세 개를 따라잡는 순간, 자기 적합성 스위트의 실패 케이스를 24개 늘렸다. 레퍼런스 구현들이 서로 벌어지는 속도가 하나를 고치는 속도보다 빠르다면, 먼저 발견한 곳부터 고친다고 해서 프로토콜 전체가 안전해지지는 않는다.

주시할 신호

  • pay-kit PR #359의 병합 여부. mppx가 2026-10-29일에 닫은 격차를 pay-kit도 닫는 시점이다.
  • 태그가 붙은 @x402/core 릴리스에 PR #4051이 들어가는 것. npm install로 받는 사용자에게 이 수정이 실제로 닿았다는 첫 확인이 된다.
  • Go·PHP·Ruby 검증기의 버전-1 트랜잭션 디코딩 지원, 그리고 다음 적합성 점검에서 known_failing 24건이 줄어드는지 아니면 더 늘어나는지.

한계

마스터카드 Agent Pay, 비자 Intelligent Commerce와 Trusted Agent Protocol, 스트라이프 Agentic Commerce Protocol, 페이팔 Agent Ready 등 카드 네트워크·PSP의 에이전트 커머스 제품은 이번 기간에도 날짜가 명시된 1차 발표가 없었다. 3개 호 연속이다. AP2와 비자 trusted-agent-protocol 저장소는 이번 기간 병합된 PR이나 릴리스가 전혀 없었다. 델라웨어 관련 의회 문서 제출 시한은 2026-11-09일이고, 2026-10-29일 호 이후 달라진 내용은 없다. 이번 기간 어떤 항목도 X나 링크드인 게시물에서 비롯되지 않았다. 여섯 개 소스 모두 GitHub의 PR, 이슈, 릴리스 노트다. 각 프로젝트가 무엇을 했는지에 대한 1차 자료이지, 그것이 실제 운영 환경에서 작동하는지에 대한 근거는 아니다.
