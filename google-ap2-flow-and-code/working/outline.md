# Outline — Google AP2: Protocol, End-to-End Processing Flow, and Code-Level Walkthrough

Scope note: a companion to the earlier overview report `google-ap2-protocol`
(2026-05-29). This report deliberately narrows to three questions:
(1) what the protocol's normative surface actually is, (2) what a transaction
does step by step on the wire, (3) what the reference implementation actually
executes. Ecosystem/partner narrative is out of scope except where it changes
the protocol.

## 2. Introduction
- What problem AP2 claims to solve, in the vendor's own framing.
- Versioning and governance state as of 2026-07 (v0.1 → v0.2, FIDO Alliance).
- What AP2 is *not*: not a commerce/catalog protocol, not a rail, not a
  transport. Boundary against A2A, MCP, UCP/ACP, x402.
- Method: which artefacts were read (spec docs, JSON Schemas, SDK source,
  runnable samples) and how flow claims were verified against code.

## 3. Protocol Surface and Data Model
- The role set and which roles are normatively constrained (non-agentic
  Trusted Surface).
- Mandate taxonomy: v0.1 Intent/Cart/Payment vs v0.2 Checkout/Payment.
- SD-JWT-VC envelope: `vct`, selective disclosure, holder binding, which
  fields are disclosable vs always-visible.
- The cryptographic linkage: `checkout_hash` → `transaction_id`, and the
  signature-scheme requirement that makes the linkage non-guessable.
- Agent authorization / delegation models (User Credential vs Trusted Agent
  Provider) and what each shifts in liability.
- What the JSON Schemas require vs what the prose spec asserts — schema is
  the machine-checkable subset.

## 4. End-to-End Processing Flows
- Human-Present card flow: message-by-message, who signs what, in what order,
  and which artefact each party retains for evidence.
- Human-Not-Present flow: pre-signed mandate with constraints, the
  constraint-evaluation step, and who performs it.
- The x402 / crypto-rail variant: where settlement replaces authorization and
  what disappears from the flow (OTP, step-up, network tokens).
- Transport bindings: how mandates ride A2A messages (extension URI,
  DataParts) vs MCP tool calls; what changes and what stays identical.
- Verification and failure paths: rejection, expiry, replay, dispute
  reconstruction from retained mandates.

## 5. Code-Level Walkthrough of the Reference Implementation
- Repository topology: `docs/`, `code/sdk/{schemas,python,go}`,
  `code/samples/python/…`, and how generated models relate to schemas.
- Mandate construction: concrete types, required fields, defaults.
- Signing and verification path: key type, curve, JWS serialization, and where
  in the sample it is invoked.
- Role servers: shopping agent, credential provider, merchant, processor — the
  actual endpoints/tools each exposes.
- Agent framework wiring: ADK agent + tools, A2A message construction.
- What the samples stub or fake (in-memory stores, mock rails) and therefore
  what the code does *not* prove.

## 6. Analysis and Discussion
- Spec-vs-code delta: normative MUSTs that the reference code does not
  enforce, and vice versa.
- Threat model as implemented: what the mandate chain actually makes
  non-repudiable, and the residual trust in the Credential Provider.
- Comparison of AP2's evidence-first design against ACP/UCP-style
  session/token designs on the same transaction.
- Migration cost for an existing PSP: which components are new code.
- Where AP2 competes vs composes with x402, L402, and Mastercard/Visa agent
  programmes.
